## The Loss Surface

Imagine plotting loss as a function of two weights. You get a 3D surface: hills, valleys, ridges. The goal of training is to find the lowest valley. In a real network with millions of weights, this surface exists in millions of dimensions, but the intuition from 3D holds.

<BridgeCallout bridge={frontmatter.concept.bridge} />

In a game engine, a character walks on terrain defined by a heightmap. Gradient descent is the same idea: you're standing on the loss surface, you look which direction goes downhill (the negative gradient), and you take a step that way.

<CodeBlock language="typescript" title="loss-surface.ts">
{`import * as tf from '@tensorflow/tfjs';

// A simple 2D loss function: L(w1, w2) = w1^2 + 3*w2^2
// This is a bowl: convex, one global minimum at (0, 0)
function convexLoss(w1: number, w2: number): number {
  return w1 * w1 + 3 * w2 * w2;
}

// Gradient: [dL/dw1, dL/dw2] = [2*w1, 6*w2]
// (dL/dw1 = how fast loss changes as w1 moves; lesson 2 of this module)
function convexGradient(w1: number, w2: number): [number, number] {
  return [2 * w1, 6 * w2];
}

// Vanilla gradient descent
let w1 = 5.0, w2 = 3.0;
const lr = 0.1;

for (let step = 0; step < 20; step++) {
  const [g1, g2] = convexGradient(w1, w2);
  w1 -= lr * g1;
  w2 -= lr * g2;
  console.log(\`Step \${step}: w=[\${w1.toFixed(3)}, \${w2.toFixed(3)}] loss=\${convexLoss(w1, w2).toFixed(4)}\`);
}
// Converges smoothly to (0, 0)`}
</CodeBlock>

## Convexity and Non-Convexity

A **convex** function is bowl-shaped: any line between two points on the surface stays above the surface. Two terms worth pinning down before going further: a **local minimum** is a point lower than everything nearby, and the **global minimum** is the lowest point on the whole surface. On a convex bowl they coincide: there is exactly one valley. Linear regression loss is convex, so gradient descent with a reasonable learning rate always finds the best answer, no matter where you start.

Neural network loss functions are **non-convex**. They have multiple valleys, ridges, and saddle points, and there's no guarantee you'll find the global minimum.

<CodeBlock language="typescript" title="non-convex.ts">
{`// A non-convex 1D loss function with multiple minima
function nonConvexLoss(w: number): number {
  return Math.sin(3 * w) + 0.5 * w * w - w;
}

function nonConvexGradient(w: number): number {
  return 3 * Math.cos(3 * w) + w - 1;
}

// Starting from different points leads to different minima
for (const start of [-2.0, 0.0, 2.0, 4.0]) {
  let w = start;
  const lr = 0.05;
  for (let i = 0; i < 100; i++) {
    w -= lr * nonConvexGradient(w);
  }
  console.log(\`Start=\${start.toFixed(1)} -> converged to w=\${w.toFixed(4)}, loss=\${nonConvexLoss(w).toFixed(4)}\`);
}
// Different starting points, different answers. This is non-convex optimization`}
</CodeBlock>

## Saddle Points

In high dimensions, local minima are rare. **Saddle points** are far more common: points where the gradient is zero but the surface curves up in some directions and down in others. Think of a mountain pass: it's the lowest point along the ridge but the highest point along the valley.

Why are saddles the common case? Recall lesson 2's Hessian rule: a zero-gradient point is a minimum only if the surface curves upward along every direction you could step. In a landscape with n weights there are n independent directions to check, and at a random zero-gradient point each one can curve up or down. If each direction were a fair coin flip, all n landing up would have probability 1 in 2^n; even a small network with 100 weights makes that roughly 1 in 10^30. Real loss surfaces are not fair coins, but the counting argument survives: every added dimension is one more chance for some direction to curve down, so almost every zero-gradient point you meet is a saddle, not a minimum.

<CodeBlock language="typescript" title="saddle-point.ts">
{`// Saddle point example: f(x, y) = x^2 - y^2
// At (0, 0): gradient is [0, 0] but it's NOT a minimum
// It curves up in x, down in y: a saddle

function saddleLoss(x: number, y: number): number {
  return x * x - y * y;
}

function saddleGradient(x: number, y: number): [number, number] {
  return [2 * x, -2 * y];
}

// Plain gradient descent stalls near the saddle: x decays toward it
// while y is pushed away (it would stick forever only when starting
// exactly on the y = 0 axis)
let x = 0.001, y = 0.001;
const lr = 0.1;
for (let i = 0; i < 10; i++) {
  const [gx, gy] = saddleGradient(x, y);
  x -= lr * gx;
  y -= lr * gy;
  console.log(\`Step \${i}: (\${x.toFixed(6)}, \${y.toFixed(6)}) loss=\${saddleLoss(x, y).toFixed(6)}\`);
}
// y escapes (gradient pushes it away): 6.19x growth in these 10 steps
// while x shrinks to 0.8 of its value each step. Slow drift out, not a trap`}
</CodeBlock>

## SGD with Momentum

SGD (stochastic gradient descent) is gradient descent where each step uses the gradient from a random mini-batch, so the steps are noisy. The toy examples below use the exact gradient; the momentum mechanics are the same. Momentum solves two problems: it helps escape saddle points and accelerates through flat regions. The physics analogy is unusually tight here: a ball rolling downhill accumulates velocity.

<CodeBlock language="typescript" title="sgd-momentum.ts">
{`import * as tf from '@tensorflow/tfjs';

// SGD with momentum: the ball-rolling-downhill optimizer
function sgdMomentum(
  lossGradFn: (w: number[]) => number[],
  initialWeights: number[],
  lr: number,
  momentum: number,
  steps: number
) {
  const weights = [...initialWeights];
  const velocity = new Array(weights.length).fill(0);

  for (let step = 0; step < steps; step++) {
    const grads = lossGradFn(weights);

    for (let i = 0; i < weights.length; i++) {
      // Physics: v = momentum * v - lr * gradient
      velocity[i] = momentum * velocity[i] - lr * grads[i];
      // Physics: position += velocity
      weights[i] += velocity[i];
    }
  }
  return weights;
}

// Compare: plain SGD vs momentum on a narrow valley
// L(w1, w2) = 0.5 * w1^2 + 50 * w2^2
// This is like a long, narrow canyon (hard for plain SGD)
const lossGrad = (w: number[]): number[] => [w[0], 100 * w[1]];

const plainResult = sgdMomentum(lossGrad, [10, 1], 0.005, 0, 200);
const momentumResult = sgdMomentum(lossGrad, [10, 1], 0.005, 0.9, 200);

console.log('Plain SGD:', plainResult.map(v => v.toFixed(4)));
console.log('Momentum:', momentumResult.map(v => v.toFixed(4)));
// Momentum converges much faster in the narrow valley`}
</CodeBlock>

## Learning Rate Schedules

A fixed learning rate is one compromise applied to the whole journey: large steps cross plateaus quickly but orbit the valley floor without ever settling, while small steps settle precisely but crawl across every flat region. A schedule changes the rate as training progresses, so you spend large steps where the landscape is flat and small ones where it narrows. Warmup covers the other end of the run: the first updates are computed from raw random weights (and adaptive optimizers like Adam size each step from running averages of recent gradients, averages that are pure noise until enough steps have accumulated), so ramping the rate up over a few epochs keeps those first steps from launching the weights somewhere unrecoverable.

<CodeBlock language="typescript" title="lr-schedules.ts">
{`// Step decay: cut the rate at fixed milestones
function stepDecay(baseLr: number, epoch: number): number {
  return baseLr * Math.pow(0.5, Math.floor(epoch / 30));  // halve every 30 epochs
}

// Warmup then cosine decay: ramp up for 5 epochs, glide down to zero
function warmupCosine(baseLr: number, epoch: number, warmup: number, total: number): number {
  if (epoch < warmup) return baseLr * (epoch + 1) / warmup;  // linear warmup
  const t = (epoch - warmup) / (total - warmup);
  return baseLr * 0.5 * (1 + Math.cos(Math.PI * t));         // cosine decay
}

for (const epoch of [0, 4, 29, 30, 60, 89]) {
  console.log(\`epoch \${epoch}: step=\${stepDecay(0.01, epoch).toFixed(4)}, warm+cos=\${warmupCosine(0.01, epoch, 5, 90).toFixed(4)}\`);
}
// epoch 0:  step=0.0100, warm+cos=0.0020
// epoch 4:  step=0.0100, warm+cos=0.0100
// epoch 29: step=0.0100, warm+cos=0.0082
// epoch 30: step=0.0050, warm+cos=0.0080
// epoch 60: step=0.0025, warm+cos=0.0028
// epoch 89: step=0.0025, warm+cos=0.0000`}
</CodeBlock>

The geometry of this lesson says why a schedule beats any single fixed rate: early training happens in wide, nearly flat basins where only a large step makes progress, and late training happens inside a narrow valley where that same step bounces between the walls instead of descending. Momentum carries you through the flats, but only a shrinking learning rate lets the optimizer stop orbiting the minimum and actually land on it.
