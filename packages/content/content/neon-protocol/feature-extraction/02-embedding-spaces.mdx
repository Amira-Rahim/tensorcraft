<Dialogue speaker="NEON">
When I was Meridian's surveillance AI, I processed features in a 512-dimensional space. Every image had a coordinate — a position in that space. The remarkable property: images of the same object clustered together. Not because anyone told them to. Because the network learned that similar visual patterns should map to nearby points.
</Dialogue>

<Dialogue speaker="Noor">
So it is like a scatter plot, but with 512 axes instead of 2. Points that are close together represent images that look alike.
</Dialogue>

On a 2D scatter plot, position encodes meaning: points near each other share similar data values. An embedding space works the same way, but in hundreds of dimensions. Each feature vector is a coordinate. Distance between coordinates equals semantic distance between images. This is not a metaphor. It is literal geometry.

## The Geometry of Similarity

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="embedding-space.ts">
{`import * as tf from '@tensorflow/tfjs';

// Each image becomes a point in 512-dimensional space
// Distance between points = visual difference

// Two drone images will have nearby feature vectors
const droneA = tf.randomNormal([512]); // feature vector for drone image A
const droneB = droneA.add(tf.randomNormal([512]).mul(0.1)); // similar drone

// A car image will be far away
const car = tf.randomNormal([512]); // very different feature vector

// Cosine similarity: measures angle between vectors
// 1.0 = identical direction, 0.0 = orthogonal, -1.0 = opposite
function cosineSimilarity(a: tf.Tensor1D, b: tf.Tensor1D): number {
  const dotProduct = a.mul(b).sum();
  const normA = a.norm();
  const normB = b.norm();
  return dotProduct.div(normA.mul(normB)).dataSync()[0];
}

console.log(cosineSimilarity(droneA, droneB)); // ~0.95 (very similar)
console.log(cosineSimilarity(droneA, car));    // ~0.02 (very different)`}
</CodeBlock>

## Distance Metrics

<CodeBlock language="typescript" title="distance-metrics.ts">
{`// Euclidean distance: straight-line distance in embedding space
function euclideanDistance(a: tf.Tensor1D, b: tf.Tensor1D): number {
  return a.sub(b).norm().dataSync()[0];
}

// Which metric to use?
// Cosine similarity: measures angle (direction), ignores magnitude
//   Good for: comparing image content regardless of brightness
// Euclidean distance: measures absolute distance
//   Good for: when magnitude matters

// In practice, cosine similarity is more common for image features
// because feature extractors can produce vectors of varying magnitude,
// and we care about *what* is in the image, not *how bright* it is

// Think of it like CSS units:
// Cosine = percentage-based (relative)
// Euclidean = pixel-based (absolute)`}
</CodeBlock>

<DerivationDrawer summary="Cosine vs Euclidean: when each makes sense">
**Cosine similarity:** `cos(a, b) = (a · b) / (||a|| · ||b||)`. Range [-1, 1]. Sensitive to direction, ignores magnitude.

**Euclidean distance:** `d(a, b) = ||a − b||`. Range [0, ∞). Sensitive to both magnitude and direction.

**When cosine wins:** text + image embeddings where vector magnitude is an artifact of training (frequency, etc) not meaning. CLIP, BERT, word2vec all use cosine.

**When Euclidean wins:** explicit distance-preserving embeddings (UMAP, t-SNE projections) where you want closeness to be metric. Recommendation systems where magnitude encodes engagement strength.

**Equivalent under L2 normalization:** if all vectors are L2-normalized to unit length, `||a − b||² = 2 − 2 · cos(a, b)`. Cosine similarity and Euclidean distance become monotonic transforms: same ranking, different scale. Most production embedding systems pre-normalize, then use either interchangeably.
</DerivationDrawer>
