## The Load Balancing Parallel

You have already shipped this fix. Four Node processes behind a load balancer, and the router keeps handing 88% of requests to two of them: the idle pair contributes nothing and the busy pair sets your p99. You change the routing, not the servers.

<BridgeCallout bridge={frontmatter.concept.bridge} />

ML class balancing uses the same strategies:

| Load Balancing | Class Balancing | Strategy |
|---|---|---|
| Duplicate requests to idle servers | Oversample minority class | Add copies of rare examples |
| Throttle busy servers | Undersample majority class | Remove excess common examples |
| Weighted routing | Class weights | Make the model pay more attention to rare classes |

## Measuring Imbalance

Before balancing, you need to diagnose the problem. This is like monitoring server health before adjusting load balancer rules.

<CodeBlock language="typescript" title="imbalance-analysis.ts">
{`interface ClassDistribution {
  label: string;
  count: number;
  percentage: number;
}

function analyzeBalance(labels: string[]): ClassDistribution[] {
  const counts: Record<string, number> = {};
  for (const label of labels) {
    counts[label] = (counts[label] || 0) + 1;
  }

  const total = labels.length;
  return Object.entries(counts)
    .map(([label, count]) => ({
      label,
      count,
      percentage: (count / total) * 100,
    }))
    .sort((a, b) => b.count - a.count);
}

function getImbalanceRatio(distribution: ClassDistribution[]): number {
  // Ratio of largest class to smallest class
  // > 10 is considered severely imbalanced
  const maxCount = distribution[0].count;
  const minCount = distribution[distribution.length - 1].count;
  return minCount === 0 ? Infinity : maxCount / minCount;
}

// Example: Neon City surveillance dataset
// dome-camera:    4200 (51.2%)  <-- majority
// bullet-camera:  3000 (36.6%)
// ptz-camera:      820 (10.0%)
// hidden-camera:   180 ( 2.2%)  <-- minority
// Imbalance ratio: 4200 / 180 = 23.3x (severely imbalanced)`}
</CodeBlock>

<Dialogue speaker="Dilan">
An imbalance ratio above 10 means your model is essentially blind to the minority class. At 23 to 1, the Sentinel would learn to say "dome camera" to almost everything and still score 51% accuracy. Useless.
</Dialogue>

## Oversampling: Duplicating Minority Requests

The simplest fix: duplicate minority class samples until all classes have equal representation. It's like a load balancer replicating requests to underutilized servers.

<CodeBlock language="typescript" title="oversampling.ts">
{`interface Sample {
  id: string;
  label: string;
}

function oversample(samples: Sample[]): Sample[] {
  // Find the majority class count
  const counts: Record<string, Sample[]> = {};
  for (const sample of samples) {
    if (!counts[sample.label]) counts[sample.label] = [];
    counts[sample.label].push(sample);
  }

  const maxCount = Math.max(
    ...Object.values(counts).map(arr => arr.length)
  );

  // Repeat minority class samples to match majority count
  const balanced: Sample[] = [];
  for (const [label, classSamples] of Object.entries(counts)) {
    for (let i = 0; i < maxCount; i++) {
      balanced.push({
        ...classSamples[i % classSamples.length],
        id: i < classSamples.length
          ? classSamples[i % classSamples.length].id
          : classSamples[i % classSamples.length].id + "-dup-" + i,
      });
    }
  }

  return balanced;
}`}
</CodeBlock>

Oversampling is safe and preserves all original data, but duplicated samples add no new information. Combining it with augmentation (from the previous lesson) is Dilan's answer: each duplicate arrives flipped, cropped, or relit, so 180 hidden cameras become 4,200 samples instead of 23 copies of the same 180 photographs.

## Undersampling: Throttling the Majority

The opposite approach: reduce the majority class to match the minority. Like throttling a busy server, this can discard useful data.

<CodeBlock language="typescript" title="undersampling.ts">
{`function undersample(samples: Sample[]): Sample[] {
  const counts: Record<string, Sample[]> = {};
  for (const sample of samples) {
    if (!counts[sample.label]) counts[sample.label] = [];
    counts[sample.label].push(sample);
  }

  const minCount = Math.min(
    ...Object.values(counts).map(arr => arr.length)
  );

  // Take only minCount samples from each class
  const balanced: Sample[] = [];
  for (const classSamples of Object.values(counts)) {
    // Shuffle and take first minCount.
    // A random sort comparator is not a uniform shuffle. Fisher-Yates is.
    const shuffled = [...classSamples];
    for (let i = shuffled.length - 1; i > 0; i--) {
      const j = Math.floor(Math.random() * (i + 1));
      [shuffled[i], shuffled[j]] = [shuffled[j], shuffled[i]];
    }
    balanced.push(...shuffled.slice(0, minCount));
  }

  return balanced;
}

// Warning: undersampling our dataset from 8,200 to 720 total samples
// (180 per class x 4 classes) throws away 91% of our data!`}
</CodeBlock>

## Class Weights: The Software Solution

Instead of changing the data, change how much the model cares about each class. Class weights multiply the loss for rare classes, making errors on them more expensive, like prioritizing critical API endpoints in your monitoring dashboard.

<CodeBlock language="typescript" title="class-weights.ts">
{`function calculateClassWeights(
  labels: string[]
): Record<string, number> {
  const counts: Record<string, number> = {};
  for (const label of labels) {
    counts[label] = (counts[label] || 0) + 1;
  }

  const total = labels.length;
  const numClasses = Object.keys(counts).length;
  const weights: Record<string, number> = {};

  // Formula: total / (numClasses * classCount)
  // Rare classes get higher weights
  for (const [label, count] of Object.entries(counts)) {
    weights[label] = total / (numClasses * count);
  }

  return weights;
}

// Example output for our surveillance dataset:
// dome-camera:   8200 / (4 * 4200) = 0.49 (downweighted)
// bullet-camera: 8200 / (4 * 3000) = 0.68
// ptz-camera:    8200 / (4 * 820)  = 2.50
// hidden-camera: 8200 / (4 * 180)  = 11.39 (heavily upweighted)`}
</CodeBlock>

<Dialogue speaker="Noor">
So a miss on a hidden camera costs 11.39 in the loss and a miss on a dome camera costs 0.49. That is 23 times the penalty, which is exactly the imbalance ratio. The model has to care about the rare class even though it only appears 2% of the time.
</Dialogue>
