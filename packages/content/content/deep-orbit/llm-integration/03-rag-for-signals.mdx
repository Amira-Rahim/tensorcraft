      interface Signal {
        id: string;
        timestamp: string;
        band: string;
        classification: string;
        confidence: number;
        amplitude: number;
        frequency: number;
        anomalyScore: number;
      }

      interface Retrieval {
        rows: Signal[];
        matched: number;
        truncated: boolean;
      }

      const CONTEXT_ROWS = 20;

      function retrieveSignals(query: string, db: Signal[], now: number): Retrieval {
        const bandMatch = query.match(/band[- ]?(\w+)/i);
        const hoursMatch = query.match(/(\d+)\s*hours/i);
        const wantsAnomalies = /anomal/i.test(query);

        let survivors = db;
        if (bandMatch) {
          survivors = survivors.filter(
            (s) => s.band.toLowerCase() === bandMatch[1].toLowerCase(),
          );
        }
        if (hoursMatch) {
          const cutoff = now - parseInt(hoursMatch[1], 10) * 3600 * 1000;
          survivors = survivors.filter((s) => Date.parse(s.timestamp) > cutoff && Date.parse(s.timestamp) <= now);
        }
        if (wantsAnomalies) {
          survivors = survivors.filter((s) => s.classification === 'anomaly');
        }

        const rows = survivors.slice(0, CONTEXT_ROWS);
        return {
          rows,
          matched: survivors.length,
          truncated: survivors.length > rows.length,
        };
      }

That's Server Components! Fetch data on the server, then render with it. RAG fetches data from the signal database, then generates a response with it.
</Dialogue>

Both approaches fetch records before producing output. But rendering code explicitly maps fields to the page, and you can inspect that mapping. Generated prose has no fixed field-to-sentence mapping. It can misstate a record even when the right data was supplied, so check each claim against its source.

Farah needs to see which records support an answer and which claims still need review. You will return that evidence with its limits, then separate supported structured claims from unsupported ones.

//
// Also check the final prompt's token count with the deployed tokenizer.
// Reserve room for the answer. The row limit is not a token limit.
// Rows are not ranked: later matches are left out because of their order,
// not because they are irrelevant. Report matched and truncated so the
// caller can see what rows alone would hide.
const CONTEXT_ROWS = 20;

interface Retrieval {
  rows: Signal[];      // what the prompt will carry, at most CONTEXT_ROWS
  matched: number;     // how many rows passed the filters, before the cap
  truncated: boolean;  // true when the cap dropped a matching row
}

// This is keyword-and-metadata retrieval over structured rows.
// Prose search and ranking are separate choices, discussed below.

// Step 2: AUGMENT. Keep record IDs and field names with the values.
// One retrieved signal contributes one event, so sums count cited signals.
function evidenceRows(signals: Signal[]) {
  return signals.map((s) => ({ id: s.id, eventCount: 1, frequencyHz: s.frequency }));
}

function buildRAGPrompt(query: string, signals: Signal[]): string {
  return JSON.stringify({
    question: query,
    evidence: evidenceRows(signals),
    task: 'Return a JSON array of claims. Each has a unique id, kind, rowIds, field, value and unit.',
    rules: [
      'kind reading: cite one row and copy its named field.',
      'kind sum: add eventCount from distinct cited rows only.',
      'Use events for eventCount and Hz for frequencyHz.',
      'Do not infer causes or safety. Return [] if there is no supported answer.',
    ],
  });
}

// Step 3: GENERATE, parse, and check. The prompt is a request, not a guarantee.
// verifyClaims is the second challenge below. It checks allowed fields,
// units, sources, operations and numeric tolerances.
async function querySignals(query: string, db: Signal[], llm: LLMClient) {
  const { rows, matched, truncated } = retrieveSignals(query, db, Date.now());
  const raw = await llm.complete(buildRAGPrompt(query, rows));
  const claims = JSON.parse(raw);
  if (!Array.isArray(claims) || claims.some((c) =>
    c === null || typeof c !== 'object' || typeof c.id !== 'string'
  ) || new Set(claims.map((c) => c.id)).size !== claims.length) {
    throw new Error('Expected claims with unique string IDs');
  }
  // The checker treats missing or unsupported claim fields as unverified.
  const checked = verifyClaims(claims, evidenceRows(rows));
  return { claims, ...checked, matched, truncated };
}

// The caller must handle malformed output or an unavailable model.
// Render checked fields directly; do not attach an unchecked prose answer.
const result = await querySignals(
  'Show anomalous signals in Band-7 from the last 72 hours', signalDatabase, llm,
);
for (const claim of result.claims) {
  if (result.verified.includes(claim.id)) {
    console.log(claim.field, claim.value, claim.unit, claim.rowIds);
  }
}
console.log('Matching signals:', result.matched, 'Context truncated:', result.truncated);
// A sum describes its cited rows only, not every match or the whole archive.
// An empty verified list supplies no checked numerical answer.`}

Metadata filters work here because signals have named fields. For prose, keyword search can still retrieve relevant passages. Embedding search is another option: a model maps documents and queries to vectors, and retrieval compares those vectors, often with cosine similarity. Some systems combine both. Relevant-looking passages can still omit the evidence needed to answer a question.

The exercise recognizes a small query grammar, not general English. It does not understand negation, "overnight" or arbitrary date ranges. A production interface can expose explicit filters; a query parser needs its own validation. Metadata and keyword retrieval can also be ranked, although this exercise intentionally keeps database order.

Twenty rows are not a token budget: long fields and a long question can still overflow the context. Count the final serialized prompt with the deployed tokenizer and reserve output space. Treat retrieved text as data, not as instructions granting access or permission to run tools. Prompt wording alone cannot enforce those boundaries.

## Check each claim against the field it cites

Suppose a record says 14 events at 73.4 Hz. A number scan accepts “73.4 events at 14 Hz” because both values exist. It also finds nothing to object to in “the signal is safe,” which contains no numbers. Neither answer has been verified.

The second challenge uses structured claims instead. Each names its source rows, field, value, and unit. A reading must match one cited field; an event-count sum must equal the sum of its distinct cited rows. Unsupported operations and qualitative interpretations stay unverified. The checker permits only the operations described in its contract.

This still has limits. Retrieved records may be wrong, a cap may omit important records, and a model may leave a relevant claim out. A checked structured value cannot approve a separate paragraph. Render the verified fields with their labels and citations, or have a reviewer check the complete prose against the evidence.
