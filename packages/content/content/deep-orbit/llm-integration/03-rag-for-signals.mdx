<Dialogue speaker="Ensign Demir" expression="breakthrough">
That's Server Components! Fetch data on the server, then render with it. RAG fetches data from the signal database, then generates a response with it.
</Dialogue>

Demir's mapping holds at the pipeline level: retrieve real records first, then generate from them instead of from whatever the model half-remembers. The step with no Server Component equivalent is the last one: a component can't contradict its props. A generator can.

## The RAG Pipeline

<CodeBlock language="typescript" title="rag-pipeline.ts">
{`interface Signal {
  id: string;
  timestamp: string;
  band: string;
  classification: string;
  confidence: number;
  amplitude: number;
  frequency: number;
  anomalyScore: number;
}

// Step 1: RETRIEVE: find the relevant signals, then cap them.
//   retrieveSignals(query, db, now): Retrieval
// Read the filters the question carries (a band, an age in hours, whether it
// asks for anomalies), apply each one that is there, keep database order,
// take the first CONTEXT_ROWS survivors. This is the first challenge below.
//
// The prompt has a token budget, so retrieval ends in a cap. Nothing is
// ranked, so the rows past the cap are dropped for arriving late rather than
// for being irrelevant, and \`rows\` alone cannot show that happened. The
// other two fields are how the caller finds out.
const CONTEXT_ROWS = 20;

interface Retrieval {
  rows: Signal[];      // what the prompt will carry, at most CONTEXT_ROWS
  matched: number;     // how many rows passed the filters, before the cap
  truncated: boolean;  // true when the cap dropped a matching row
}

// The honest label for that step: keyword-and-metadata retrieval. It
// works here because the catalogue is 12,001 STRUCTURED rows with named
// fields you can match on. What production RAG reaches for when the corpus
// has no fields is the paragraph right under this block.

// Step 2: AUGMENT: inject retrieved data into prompt
function buildRAGPrompt(query: string, signals: Signal[]): string {
  const signalContext = signals.map(s =>
    \`[\${s.timestamp}] Band \${s.band}: \${s.classification} (conf=\${s.confidence}, amp=\${s.amplitude}, freq=\${s.frequency}Hz, anomalyScore=\${s.anomalyScore})\`
  ).join('\\n');

  return \`You are DEEP SCAN's analysis assistant. Answer based ONLY on the provided signal data.
If the data doesn't contain the answer, say "insufficient data."

## Retrieved Signal Data
\${signalContext}

## Question
\${query}

## Instructions
- Cite each signal by copying its bracketed timestamp from the rows above
- Every number you write has to be one of the readings in those rows: a confidence, an amplitude, a frequency or an anomaly score. Do not add them up, average them, or count them
- Write a band name in words rather than digits: Band seven, not Band-7
- Say plainly when the rows do not answer the question\`;
}

// Step 3: GENERATE, then check what came back. An answer can lie twice, so it
// gets checked twice: once for citing a row nobody retrieved, once for writing
// a number no row holds. verifyClaims is the second challenge below.
const CITATION = /\\[([^\\]]+)\\]/g;
const readingsOf = (s: Signal) => [s.confidence, s.amplitude, s.frequency, s.anomalyScore];

async function querySignals(query: string, db: Signal[], llm: LLMClient) {
  const { rows, matched, truncated } = retrieveSignals(query, db, Date.now());
  if (truncated) {
    // The operator's log, not the prompt. A count written into the prompt is
    // a number the model can repeat, and the checker below admits only
    // numbers that appear in the retrieved rows.
    console.warn(\`Context capped: \${rows.length} of \${matched} matching rows.\`);
  }
  const answer = await llm.complete(buildRAGPrompt(query, rows));

  // Citations first, because verifyClaims compares numbers and a regex reading
  // 2149-05-28T04:12:09Z finds six of them, none of them a reading. Check each
  // bracket against the timestamps that were actually retrieved, then score
  // what is left of the sentence.
  const retrieved = new Set(rows.map((s) => s.timestamp));
  const cited = [...answer.matchAll(CITATION)].map((m) => m[1]);
  const unsourced = cited.filter((stamp) => !retrieved.has(stamp));
  const { fabricated } = verifyClaims(answer.replace(CITATION, ''), rows.map(readingsOf));

  return { answer, unsourced, fabricated };
}

// Usage:
const { answer, unsourced, fabricated } = await querySignals(
  "Show me all anomalous signals in Band-7 from the last 72 hours",
  signalDatabase,
  llm,
);
if (unsourced.length > 0 || fabricated.length > 0) {
  // Nothing ships. Either the answer cited a row nobody retrieved, or it wrote
  // a number that is in no retrieved row.
}`}

That retrieval is a keyword-and-metadata match, and it works only because every row has fields. A corpus of prose has none, and that is where production RAG stops looking like a database query. Each document goes through a model that turns it into an embedding, an array of a few hundred floats positioned so that documents about similar things land near each other, and the question goes through the same model to get an array of its own. Retrieval is then a nearest-neighbor lookup over those arrays, scored by cosine similarity, which measures how closely two of them point the same way and ignores how long they are. A keyword index answers which rows contain this word. An embedding index answers which rows mean something like this. The machinery changes and the contract does not: retrieve, ground, verify.

Three of those four instructions exist to keep the answer inside what the checker can admit. The checker compares numbers, and the only numbers it admits are the readings in the retrieved rows. The band and the timestamp are labels rather than readings, so the checker admits neither, and each one is kept out of the answer's way by a different mechanism. The timestamp gets a fix in code: the citation strip runs before the number check, because a bracketed timestamp has a shape we control and can lift out of the sentence. The band gets no strip, since a band name is whatever the catalogue calls it. What stands in for one is the prompt line asking for band names in words, because a sentence quoting Band-7 reaches the checker as a claim of -7, and that answer is held even when every reading in it is right. A sum, an average or a count is a number the model worked out rather than read, so the checker calls it fabricated unless it happens to land within the tolerance of some reading. When the report needs a count of matching rows, `matched` already holds it and JavaScript can print it exactly. Ask the model for that count instead and you have bought a number somebody now has to verify.
