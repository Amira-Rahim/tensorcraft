## LLMs as Developer Tools

<CodeBlock language="typescript" title="llm-client.ts">
{`// An LLM client is a typed fetch wrapper. Nothing here is new except
// what comes back: a string with no schema and no guarantees.
interface LLMClient {
  complete(prompt: string, options?: { system?: string; temperature?: number; maxTokens?: number }): Promise<string>;
}

// In production, this calls an API (OpenAI, Anthropic, etc.). Most
// providers expose a messages-shaped chat API, each with its own
// dialect (Anthropic, for one, takes system as a top-level field,
// not a message role). Anything in a browser bundle is readable by
// anyone who opens devtools, so the provider key never ships there:
// run this client on a server, or point baseUrl at a same-origin
// route that holds the key and forwards the call. For DEEP SCAN, we
// point it at the ship's onboard model: the Archimedes is eleven
// light-minutes from any provider, so the language model runs
// in-process on the bridge dashboard behind a loopback route, and its
// weights ride in the dashboard's own bundle. That is the 340 MB
// module 10 audits and cuts to 85. The key rule above is for a
// provider you reach over a network; here the key is a formality and
// the weight is the cost.
async function createLLMClient(apiKey: string, baseUrl: string): Promise<LLMClient> {
  return {
    async complete(prompt, options = {}) {
      const response = await fetch(\`\${baseUrl}/v1/chat/completions\`, {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': \`Bearer \${apiKey}\`,
        },
        body: JSON.stringify({
          messages: [
            { role: 'system', content: options.system ?? 'You are the Archimedes signal-analysis assistant. Report only what the provided data supports.' },
            { role: 'user', content: prompt },
          ],
          temperature: options.temperature ?? 0.3,  // low temp for factual analysis
          max_tokens: options.maxTokens ?? 1024,
        }),
      });
      const data = await response.json();
      return data.choices[0].message.content;
    },
  };
}

// Usage: draft a signal analysis report
const llm = await createLLMClient(API_KEY, BASE_URL);
const report = await llm.complete(\`
Summarize the following signal classification results:
- Total signals analyzed: 12,001
- Normal signals: 11,847 (98.7%)
- Anomalous signals: 153 (1.3%)
- Unclassified: 1 (0.008%)

Focus on the single unclassified signal and its significance.
\`);`}
</CodeBlock>

## What You Are Actually Calling

Strip the HTTP away and a language model is something you have already built the parts of. It is a classifier. Given a sequence of tokens (word pieces, roughly three quarters of a word each), it emits one score per token in its vocabulary, softmax turns the scores into a probability distribution, and one token is sampled from it. Append the sample, run again, repeat until a stop token. Six hundred words of report is about eight hundred forward passes, one per token. Each one is the shape of module 6's next-value prediction, with one difference: the output is a choice among the tens of thousands of tokens in the vocabulary rather than three continuous numbers. That difference is what makes it classification.

## What a Transformer Does With the Prompt

Inside each pass, the mechanism that reads the prompt is attention, stacked dozens of layers deep and run with many heads at once. Module 8's scorer emitted one score per step against a single query, then pooled the whole window into one summary vector. A transformer gives every token its own query, so the scores form a T-by-T matrix: 80 steps means 6,400 scores rather than 80. Double the prompt and that matrix quadruples, 160 steps for 25,600 scores, which is why a long context costs what it does rather than simply holding more.

The heads are the second multiplier. Each one runs the same T-by-T calculation over its own slice of every token's vector, so each learns its own question about which tokens matter to which, and their outputs are concatenated before the next layer reads them. Stack that block dozens of times and that is the architecture on the other end of a completions call. That is the self-attention module 8 named and left to the transformers. Softmax still spends the budget, and the weighted sum still becomes the next layer's input. The prompt is the window. The context limit is the sequence length, the same T you windowed at 80.

`temperature` is a knob on the last softmax, the one over the whole vocabulary that picks the next token. Divide each token's score by it before the exponentials. A low value sharpens the distribution toward the single likeliest token, and a high value flattens it toward picking any token at random. Zero is not a value you can divide by. As the temperature approaches zero the distribution collapses onto the single likeliest token, which is why providers read a request for zero as an instruction to take that token directly. The attention scores inside the stack are never divided by temperature. That is why the client above sets 0.3 for a factual draft, and why lesson 4 insists that a sharpened distribution is a more repeatable one, not a more truthful one.

What is new is only scale. The weights were trained on more text than any crew could read, which is why the model writes fluent paragraphs about instruments the Archimedes does not carry. Fluency is what next-token prediction optimizes. Truth was never in the loss.

## The Human-AI Workflow

<CodeBlock language="typescript" title="workflow.ts">
{`// The workflow mirrors Copilot usage:
// 1. CONTEXT: provide data and instructions
// 2. GENERATE: LLM produces a draft
// 3. REVIEW: expert checks for accuracy
// 4. CORRECT: fix any errors or hallucinations
// 5. APPROVE: human signs off on final output

interface AnalysisWorkflow {
  context: string;      // raw data and instructions
  draft: string;        // LLM-generated output
  corrections: string[];// expert corrections
  approved: boolean;    // human sign-off
  approvedBy: string;   // who verified
}

// CRITICAL: LLMs can hallucinate, generating plausible but false statements
// Always verify claims against actual data
// Like reviewing Copilot suggestions: accept what's correct, fix what's not

function validateClaims(
  draft: string,
  actualData: Record<string, number>,
): { valid: string[]; invalid: string[] } {
  // Every number in the draft is a claim. Extract them in reading
  // order (commas stripped so "12,001" parses), then ask whether SOME
  // value in the data sits within tolerance. A claim does not care
  // which field it came from; a fabricated one matches none.
  const claims = draft.replace(/(\\d),(?=\\d)/g, '$1').match(/-?\\d+(?:\\.\\d+)?/g) ?? [];
  const values = Object.values(actualData);
  const valid: number[] = [];
  const invalid: number[] = [];

  for (const claim of claims) {
    const n = parseFloat(claim);   // keep the number, not the matched text
    if (values.some((v) => Math.abs(v - n) <= 0.05)) valid.push(n);
    else invalid.push(n);
  }
  return { valid, invalid };
}

// Run it on a draft with one invented figure:
const check = validateClaims(
  'Across 12,001 catalogued events, 153 were anomalous and 1 resists ' +
  'classification. A cluster of 9 anomalies repeats hourly.',
  { totalEvents: 12001, anomalous: 153, unclassified: 1 },
);
console.log(check.valid);    // [12001, 153, 1]
console.log(check.invalid);  // [9]  ← no such cluster in the data
// Lesson 3 of this module rebuilds this checker as verifyClaims, against
// retrieved RAG rows rather than a flat record; the contract is already
// here: extract, compare, refuse to trust prose.`}
</CodeBlock>

## Challenge

The client above is typed all the way to its edge. What comes back over that edge is not: a string with no schema and no guarantees. Turn one reply into a typed analysis, or into a thrown error.
