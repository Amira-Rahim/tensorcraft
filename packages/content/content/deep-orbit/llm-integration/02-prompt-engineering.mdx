<Dialogue speaker="Dr. Farah">
My first prompt was 'Analyze this signal data.' The output was useless: generic, vague, no structure. When I added role, context, data, and format instructions, the draft became specific enough to review against the readings. I still checked its claims before using them. Format matters when code needs to parse the reply; asking for JSON does not guarantee valid JSON.

A more specific search query can narrow retrieved results. A prompt instead asks a model to generate an answer. Both benefit from a clear task and relevant context, but precise wording guarantees neither a useful result nor a true claim.

One word does double duty across these two lessons. Lesson 1's client set a `role` on every message it sent, which is the API's label for whose turn it is: the system message that stands behind the whole call, then the user's. The role in Farah's four parts is a line of English inside that user message, naming who the model should answer as. It is the same word at two different layers.

const vaguePrompt = "Analyze this signal data.";
// Output: generic paragraph about signals (useless)

// Level 2: Specific role + context
const betterPrompt = \`You are a deep space signal analyst aboard a research vessel.
Analyze the following signal reading and classify it as noise or anomaly.
Signal: amplitude=1024 counts, frequency=73.4Hz, phase=0.23rad\`;
// Illustrative response in this scene: more specific, still unstructured

// Level 3: Structured with format instructions
const structuredPrompt = \`You are a deep space signal analyst. Respond in JSON only.

Signal reading (archive sample 7741):
- Amplitude: 1024 counts (normal band: 570-1560)
- Frequency: 73.4 Hz (known natural: 5, 12, 23, 47 Hz)
- Phase: 0.23 rad

Classify this signal using noise, anomaly or unknown.
Confidence is a self-reported score from 0 to 1, not a calibrated probability.
Use this JSON shape:
{
  "classification": "unknown",
  "confidence": 0.0,
  "reasoning": "brief explanation",
  "anomalous_features": ["list of unusual features"]
}\`;
// Requested shape, not a guaranteed response. Parse and validate it.`}
</CodeBlock>

None of those three signal lines quotes a model input. The classifier reads amplitude, frequency and phase after module 4 min-max normalizes all three to 0 to 1, and the prompt reports what the instruments logged instead. Amplitude is the hull sensor's own count against its 2048-count full scale, so the 0.50 the classifier saw goes into the prompt as 1024. Frequency is the line the transform found, in hertz, rather than the model's zero-crossing count. That count is taken over a 64-sample window, which is a quarter second of tape at the array's 256 Hz rate. Phase is radians rather than the normalized angle. Those are the numbers a scientist reading the draft can check against an instrument, and this prompt is written for that reader.

<DerivationDrawer summary="Checking the instrument units in this example">
These are supplied mission measurements, not reproduced experimental results. The fictional normal period has normalized mean 0.52, standard deviation 0.15, p5 0.28 and p95 0.76. Multiplying the percentile endpoints by 2048 gives roughly 570 to 1560 counts. This is the central 90% reference band, not the 3-sigma decision threshold.

1024 counts becomes 0.50, about 0.13 standard deviations below that mean. A clean 73.4 Hz sinusoid spans about 18.35 cycles in a quarter second, so roughly 36 or 37 zero crossings might be observed. The exact count depends on phase, sampling and noise; frequency does not uniquely determine it. A measured count of 37 normalizes to 37/63, about 0.59. Phase 0.23 rad maps to about 0.54 across the minus-pi-to-pi range.

The story's classifier score of 51.8% does not establish a calibrated probability. The listed natural frequencies are a limited local catalogue. Absence from it is a reason to investigate, not proof of an unnatural source.
</DerivationDrawer>

## Prompt Templates

<CodeBlock language="typescript" title="templates.ts">
{`// Reusable prompt templates, like React component templates.
// This is Farah's v8, the last version her red pen still marked up: all
// four parts are here, and the epilogue names the one line v9 added.

interface SignalData {
  amplitude: number;   // hull counts against the sensor's 2048-count full scale
  frequency: number;   // the FFT line under review, in Hz, not the zero-crossing count
  phase: number;       // radians
}

function classificationPrompt(signal: SignalData): string {
  return \`You are DEEP SCAN, an AI signal classification system.

## Context
You are analyzing signals from deep space Sector 7-G.
Normal amplitude range: 570 to 1560 counts.

## Signal Data
- Amplitude: \${signal.amplitude} counts
- Frequency: \${signal.frequency} Hz
- Phase: \${signal.phase} rad

## Task
Classify this signal and explain your reasoning.

Allowed classes: noise, anomaly, unknown. Risk: low, medium, high.
Confidence is a self-reported score from 0 to 1, not measured calibration.
## Output Format (example JSON)
{
  "classification": "unknown",
  "confidence": 0.0,
  "reasoning": "Evidence is insufficient to classify this reading.",
  "risk_level": "low"
}\`;
}

// Teaching contract: one JSON object, with no other braces in the reply.
// For general responses, use a strict structured-output contract and schema.
// Even schema-valid output still needs factual review.
// Parse the response
function parseClassification(response: string) {
  const jsonMatch = response.match(/\\{[\\s\\S]*\\}/);
  if (!jsonMatch) throw new Error('No JSON found in response');
  const value = JSON.parse(jsonMatch[0]);
  if (!['noise', 'anomaly', 'unknown'].includes(value.classification) ||
      !Number.isFinite(value.confidence) || value.confidence < 0 || value.confidence > 1 ||
      typeof value.reasoning !== 'string' || !value.reasoning.trim() ||
      !['low', 'medium', 'high'].includes(value.risk_level)) {
    throw new Error('Invalid classification fields');
  }
  return value;
}`}
</CodeBlock>
