## The Learning Loop

In frontend animation, `requestAnimationFrame` creates a loop that updates state and re-renders until the target is reached. Training is the same pattern: update weights and re-evaluate until the loss is minimized.

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="training-loop.ts">
{`import * as tf from '@tensorflow/tfjs';

// Prepare the model (from previous lesson)
const model = tf.sequential();
model.add(tf.layers.dense({ units: 32, activation: 'relu', inputShape: [3] }));
model.add(tf.layers.dense({ units: 16, activation: 'relu' }));
model.add(tf.layers.dense({ units: 1, activation: 'sigmoid' }));
model.compile({ optimizer: 'adam', loss: 'binaryCrossentropy', metrics: ['accuracy'] });

// Training data: 100 labeled readings, three features each:
// [band energy, spectral stability, phase coherence]. Flagged windows
// run hot on energy and coherence and LOW on stability; calm periods
// are the mirror image. The seeds make the DATA reproducible; a net
// trained on pure noise would sit at loss 0.693 forever, and deserve to.
const calm = tf.concat([
  tf.randomNormal([50, 1], 0.17, 0.10, 'float32', 7),
  tf.randomNormal([50, 1], 0.81, 0.10, 'float32', 8),
  tf.randomNormal([50, 1], 0.23, 0.10, 'float32', 9),
], 1);
const flagged = tf.concat([
  tf.randomNormal([50, 1], 0.84, 0.10, 'float32', 41),
  tf.randomNormal([50, 1], 0.18, 0.10, 'float32', 42),
  tf.randomNormal([50, 1], 0.78, 0.10, 'float32', 43),
], 1);
const xs = tf.concat([calm, flagged]);
const ys = tf.concat([tf.zeros([50, 1]), tf.ones([50, 1])]);

// Shuffle once: validationSplit takes the LAST rows, and a validation
// set that is all flagged windows validates nothing.
const order = Array.from(tf.util.createShuffledIndices(100));
const trainX = xs.gather(order);
const trainY = ys.gather(order);

// THE TRAINING LOOP: model.fit() handles everything
const history = await model.fit(trainX, trainY, {
  epochs: 50,             // iterate over dataset 50 times
  batchSize: 32,          // process 32 samples at a time
  validationSplit: 0.2,   // hold out 20% for validation
  callbacks: {
    onEpochEnd: (epoch, logs) => {
      if (epoch % 10 === 0) {
        console.log(\`Epoch \${epoch}: loss=\${logs?.loss.toFixed(4)}, acc=\${logs?.acc.toFixed(4)}\`);
      }
    },
  },
});

// One real run. Weight init is random, so reruns differ: across 400
// reruns of this block, epoch-10 accuracy bounced anywhere from 0.46 to
// 1.00 before settling by epoch 30, and epoch-40 loss landed anywhere
// from 0.10 to 0.50.
// Epoch 0:  loss=0.7382, acc=0.4875
// Epoch 10: loss=0.6330, acc=0.9875
// Epoch 20: loss=0.5376, acc=1.0000
// Epoch 30: loss=0.4084, acc=1.0000
// Epoch 40: loss=0.2672, acc=1.0000
// Accuracy tops out before loss finishes falling: the net finds the
// boundary first, then spends the remaining epochs getting confident
// about it.`}
</CodeBlock>

**Key parameters:**
- **epochs**: How many times to iterate over the full dataset. More epochs = more learning (up to a point).
- **batchSize**: How many samples to process before updating weights. 32 is a good default.
- **validationSplit**: Fraction of data held out to check for overfitting.

"Up to a point" has a body count. Demir's first run was not the clean curve above: reasoning from animation loops, where more frames always means smoother easing, he set `epochs: 500` to be safe and went for coffee. He came back to a training loss of 0.0004, a validation loss that had been climbing since epoch 60, and a model worse on real signals than the four-minute version. It had stopped learning the pattern and started memorizing the dataset. An animation that runs longer gets closer to its target; a network that trains longer gets closer to its training data, which is not the same place.

The fix is a callback that watches the validation loss and halts when it stops improving, so the loop stops itself instead of trusting your epoch guess:

<CodeBlock language="typescript" title="early-stopping.ts">
{`// Two setup notes, both load-bearing. First, a FRESH network: \`model\`
// is already trained, so re-fitting it would start at the bottom of the
// loss curve and trip the callback almost immediately.
const rerun = tf.sequential();
rerun.add(tf.layers.dense({ units: 32, activation: 'relu', inputShape: [3] }));
rerun.add(tf.layers.dense({ units: 16, activation: 'relu' }));
rerun.add(tf.layers.dense({ units: 1, activation: 'sigmoid' }));
rerun.compile({ optimizer: 'adam', loss: 'binaryCrossentropy', metrics: ['accuracy'] });

// Second, something to overfit TO. On the clean synthetic clusters above,
// validation loss just keeps creeping down and a 500-epoch run never
// halts. The archive is not that clean: its labels come from the flag
// log, and a few are wrong. Flip six of the first eighty labels to
// simulate that (validationSplit takes the LAST 20 rows, which stay
// clean, so what you watch is pure memorization of the bad rows).
const labels = trainY.arraySync();
for (const i of [3, 17, 29, 41, 52, 68]) labels[i] = [1 - labels[i][0]];

await rerun.fit(trainX, tf.tensor2d(labels), {
  epochs: 500,            // an upper bound now, not a target
  validationSplit: 0.2,
  callbacks: tf.callbacks.earlyStopping({
    monitor: 'val_loss',  // stop when the HELD-OUT loss stops falling
    patience: 5,          // give it 5 epochs of no improvement first
  }),
});
// The halt epoch is data- and init-dependent. Thirteen runs of this
// block halted anywhere from epoch 71 to 164, most between 70 and 125,
// each with validation loss in the 0.07-0.11 band and turning upward.
// The archive rerun stopped at epoch 102 on val_loss 0.081. One warning:
// with only 20 validation rows, patience: 5 can also trip in the first
// few epochs, while the model is still at chance, if the early curve
// happens to stall. A halt in single-digit epochs is a small-split
// artifact, not convergence: seed the shuffle or enlarge the split
// before trusting it.`}
</CodeBlock>

<DerivationDrawer summary="The 7-step SGD loop that fit() hides">
**`model.fit()` is a wrapper around this loop**, repeated `epochs × (datasetSize / batchSize)` times:

```
for epoch in 1..N:
  shuffle(trainX, trainY)
  for batch in chunks(trainX, batchSize):
      // 1. Forward pass: predictions for this batch
      ŷ = model.forward(batch.x)

      // 2. Loss: how wrong on this batch
      L = lossFn(ŷ, batch.y)

      // 3. Backward pass: gradients via chain rule
      ∇w = backward(L, model.params)

      // 4. Update: step opposite to gradient
      for w in model.params:
          w := w - learningRate * ∇w[w]

      // 5. Log batch metrics
  // 6. End-of-epoch: validate on heldout set
  if val_loss not improving for K epochs:   // K = patience, typically 5-10
      // 7. Stop early
      break
```

**Why mini-batch (not full-batch or single-sample)?** Full-batch is exact but uses too much memory and takes one step per epoch. Single-sample (true SGD) is noisy and underuses GPU parallelism. Mini-batches of 32-512 are the empirical sweet spot: enough samples for a smooth gradient estimate, small enough to fit in memory, large enough to saturate the GPU.

**Why shuffle each epoch?** Without shuffling, the model sees batches in the same order every epoch, which biases learning toward whatever pattern is in the file order. Shuffle breaks the correlation between adjacent batches.
</DerivationDrawer>
