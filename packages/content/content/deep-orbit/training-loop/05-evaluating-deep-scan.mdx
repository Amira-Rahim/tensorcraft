## The Final Test

Ninety-five percent training accuracy, sixty percent on signals the network has never seen. That gap is the most common failure in ML, and nothing in the training logs warns you about it: the model memorized its homework instead of learning the subject. Evaluation on held-out data exists to catch exactly this, the way E2E tests catch what unit tests can't: code that passes against fixtures and fails against reality.

<CodeBlock language="typescript" title="evaluation.ts">
{`import * as tf from '@tensorflow/tfjs';

// Assume model is trained from previous lesson

// Test data: a 50-row held-out slice of the archive, labeled, and NEVER
// seen during training. It must be real readings with real labels: random
// tensors cannot measure anything, because random labels contain no
// pattern to be right about.
const testX = tf.concat([
  // Eight rows of the slice, annotated, for a feel of the data:
  tf.tensor2d([
    [0.82, 0.14, 0.77],  // flagged window, confirmed anomalous
    [0.11, 0.86, 0.19],  // calm-period reading
    [0.74, 0.22, 0.68],  // flagged window
    [0.15, 0.79, 0.24],  // calm-period reading
    [0.68, 0.31, 0.66],  // flagged window
    [0.09, 0.91, 0.13],  // calm-period reading
    [0.71, 0.18, 0.72],  // flagged window
    [0.21, 0.74, 0.28],  // calm-period reading
  ]),
  // The next 39 rows, drawn from the same archive distributions under
  // FRESH seeds (the model has never seen any of them):
  tf.concat([
    tf.randomNormal([19, 1], 0.84, 0.10, 'float32', 201),  // flagged
    tf.randomNormal([19, 1], 0.18, 0.10, 'float32', 202),
    tf.randomNormal([19, 1], 0.78, 0.10, 'float32', 203),
  ], 1),
  tf.concat([
    tf.randomNormal([20, 1], 0.17, 0.10, 'float32', 204),  // calm
    tf.randomNormal([20, 1], 0.81, 0.10, 'float32', 205),
    tf.randomNormal([20, 1], 0.23, 0.10, 'float32', 206),
  ], 1),
  // ...plus three flagged rows the crew only confirmed on spectrogram
  // review. In these three features they read almost calm. Watch what
  // they do to the score.
  tf.tensor2d([
    [0.30, 0.68, 0.34],
    [0.26, 0.75, 0.29],
    [0.33, 0.71, 0.36],
  ]),
]);
const testY = tf.concat([
  tf.tensor2d([[1], [0], [1], [0], [1], [0], [1], [0]]),
  tf.ones([19, 1]),
  tf.zeros([20, 1]),
  tf.ones([3, 1]),
]);

// Evaluate: returns [loss, accuracy] (matches compile metrics)
const [testLoss, testAccuracy] = model.evaluate(testX, testY) as tf.Tensor[];
console.log('Test Loss:', testLoss.dataSync()[0].toFixed(4));
console.log('Test Accuracy:', (testAccuracy.dataSync()[0] * 100).toFixed(1) + '%');
// The crew's run printed 94.0% (test loss 0.2439) on this slice: 47 of
// 50, and the three misses are exactly the spectrogram-confirmed rows
// above. Training starts from random weights, so reruns differ: across
// 400 reruns of this pipeline, 393 printed 94.0% and the rest landed
// between 88.0 and 98.0. The loss moves run to run; the story the gap
// tells must not.

// Make predictions on new signals
const newSignals = tf.tensor2d([
  [0.9, 0.1, 0.8],   // possibly anomalous
  [0.1, 0.9, 0.2],   // probably normal
  [0.5, 0.5, 0.5],   // an unlabeled archive sample nobody has bet on
]);

const predictions = model.predict(newSignals) as tf.Tensor;
const results = predictions.dataSync();
results.forEach((prob, i) => {
  console.log(\`Signal \${i + 1}: \${(prob * 100).toFixed(1)}% anomalous\`);
});
// The bridge run printed:
//   Signal 1: 88.0% anomalous
//   Signal 2: 11.7% anomalous
//   Signal 3: 51.8% anomalous  ← neither normal nor alarm.
// Same tolerance rule as the evaluate above: across 400 reruns, signals
// 1 and 2 stay decisive in nearly every run (medians 92 and 12), while
// signal 3 never settles, landing anywhere from the high 20s to the mid
// 70s and centering on the fence. That refusal to commit is the finding.`}

One entry for the strangest page in the ship's records: back before this network had seen a single label, an untrained build scored sample 7741 at 0.998, and a brand-new reinitialization, fresh random numbers and all, scored it 0.997. Nobody explained it then and nobody explains it now. But notice what training did: the certain machine became an uncertain one. Untrained, it had an opinion; trained, it refuses to commit at 51.8 on the one reading the crew cannot label.

**Interpreting results:**
- **Training accuracy > Test accuracy** → The model is memorizing (overfitting). You need more data, less complexity, or regularization.
- **Both accuracies low** → The model can't learn the pattern (underfitting). You need more layers, more units, or more training.
- **Both accuracies high** → Ship it.

<DerivationDrawer summary="Why accuracy alone is not enough: precision, recall, F1">
**Accuracy** = `(TP + TN) / (TP + TN + FP + FN)`. This breaks under class imbalance: if 99% of signals are normal, predicting "normal" for everything scores 99% accuracy and zero useful detections.

**Precision** = `TP / (TP + FP)`: of all signals you flagged as anomalous, what fraction actually were?

**Recall** (sensitivity) = `TP / (TP + FN)`: of all true anomalies, what fraction did you catch?

**The crew's run, as a confusion matrix.** The 94.0% above came from the 50-row held-out slice: 26 anomalous rows, 24 calm ones.

|  | Predicted anomalous | Predicted calm |
|---|---|---|
| **Actually anomalous (26)** | TP = 23 | FN = 3 |
| **Actually calm (24)** | FP = 0 | TN = 24 |

Accuracy = (23 + 24) / 50 = 94.0%. Precision = 23 / 23 = 1.000. Recall = 23 / 26 = 0.885. One aggregate number became three, and the three disagree: perfect precision, and a recall hole exactly where the spectrogram-confirmed disguised anomalies live. That is what "aggregate accuracy hides failure modes" looks like in practice.

**Tradeoff:** lowering the decision threshold (default 0.5) increases recall (catch more anomalies) but lowers precision (more false alarms). Raising it does the opposite. There is no free lunch. Pick based on the cost asymmetry of false positives vs false negatives in your domain.

**F1 score** = `2 · (precision · recall) / (precision + recall)`: harmonic mean. Use when you need a single number that punishes either extreme. For DEEP SCAN, missing a true anomaly might cost a ship. False alarms cost crew time. The right metric depends on which cost you're willing to absorb.

**ROC and PR curves** plot precision-recall (or TPR-FPR) across all thresholds. Reporting one accuracy number from one threshold hides this entire surface.
</DerivationDrawer>

One number in that table deserves suspicion before anyone celebrates: precision 1.000 was measured on a slice where half the rows are anomalous, because the crew built the slice that way. The live stream is not that slice.

<DerivationDrawer summary="What an alarm is worth: Bayes' theorem and base rates" companionSlug="probability-and-bayes">
**Precision belongs to the detector plus the world it runs in.** Sensitivity and false-positive rate are properties of the model alone. Precision also depends on how common anomalies are in the data you run it on, and the held-out slice (26 anomalous, 24 calm) was assembled to be near balanced. Live hull telemetry is overwhelmingly calm.

**Bayes' theorem converts between the two.** The number the bridge actually needs is P(anomaly | alarm), and an alarm can happen two ways, a caught anomaly or a false positive:

`P(anomaly | alarm) = (sens · prior) / (sens · prior + FPR · (1 - prior))`

**First, honesty about the false-positive rate.** FP = 0 on 24 calm rows says less than it seems: a detector with a true 4% FPR would still print a clean 24-for-24 run about 38% of the time (0.96²⁴ ≈ 0.38). Zero observed false positives bounds the FPR loosely; it does not make it zero.

**Worked example.** Take sens = 0.885 (the recall above), assume FPR = 2%, and suppose 1 reading in 1,000 on the live stream is genuinely anomalous (prior = 0.001):

`(0.885 × 0.001) / (0.885 × 0.001 + 0.02 × 0.999) = 0.000885 / 0.020865 ≈ 0.042`

An alarm on the live stream is about a 4% bet that something is really there, from the same detector whose test-slice precision printed 1.000. Nothing about the model changed; the base rate did. Every percentage point of FPR is 10 false alarms per 1,000 calm readings, and each one costs crew time.

**Raising the posterior means changing one of the three inputs:** a lower FPR (better detector), a higher prior (alarm only on readings that already passed a cheaper filter), or better sensitivity. Production monitoring stacks detectors in exactly that order: cheap filter first, expensive model on the survivors.
</DerivationDrawer>
