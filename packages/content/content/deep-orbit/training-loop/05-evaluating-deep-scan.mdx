## The mistakes behind the score

Start with case 3 in the activity's twelve supplied teaching cases. Its score
is 0.41 and its supplied label is 1, meaning anomaly. At cutoff 0.5, the rule
`score > cutoff` predicts 0. That is a **false negative**, a missed anomaly.
Lower the cutoff below 0.41 and this case becomes a true positive. At exactly
0.41 it still predicts 0 because the comparison is strict.

Each case contributes to one cell in a **confusion matrix**:

| Supplied label | Predict 1: alert | Predict 0: no alert |
|---|---|---|
| 1: anomaly | True positive (TP), caught anomaly | False negative (FN), missed anomaly |
| 0: normal | False positive (FP), false alarm | True negative (TN), correct quiet case |

Now count the cells. **Accuracy** is `(TP + TN) / all cases`. **Precision** is
`TP / (TP + FP)`, the share of alerts whose supplied label is anomaly.
**Recall** is `TP / (TP + FN)`, the share of labeled anomalies caught. If a
denominator is zero, report that metric as undefined or state your tool's
convention. A missed anomaly and a false alarm have different costs even when
both reduce accuracy by the same amount.

The activity also compares a declared constant rule: always predict 0. It
gets seven of the twelve cases correct and misses all five anomalies. A
useful comparison needs both the score and the errors behind it.

Mirza's coding task uses a separate synthetic fixture. Its 100 generated
training rows have 50 labels of each class. Its 43 evaluation rows contain
20 generated label-0 cases, 20 generated label-1 cases, and three authored
label-1 cases. The three inputs are dimensionless practice features. These
labels come from the fixture's construction. They do not establish the
origin or correct classification of a ship reading. In particular, cases
40-42 are not sample 7741.

Keep all 43 evaluation rows and labels out of training. Their measured
scores describe this fixture. Evaluating a live spacecraft system would
require representative measurements.

## Training and held-out evaluation

The exercise supplies a compiled model and tensors. Fit only the training pair, then
evaluate the separate pair:

<CodeBlock language="typescript" title="measure-the-gap.ts">
{`const history = await model.fit(trainX, trainY, {
  epochs: 30, batchSize: 16,
});
const evalResult = model.evaluate(testX, testY); // [loss, accuracy]
const trainAcc = history.history.acc.at(-1);
const testAcc = evalResult[1].dataSync()[0];
const gap = trainAcc - testAcc;`}
</CodeBlock>

`evaluate()` returns loss followed by the metrics configured at compile time.
This model was compiled with one metric, accuracy, so read it from the second
tensor. Loss measures how the scores disagree with labels. Accuracy counts
correct decisions at the model's strict 0.5 cutoff. They answer different
questions, so keep both.

The final `history.history.acc` entry is the accuracy logged across the last
training epoch. `evalResult[1]` measures the final model on the separate
evaluation rows. The training log is not a fresh evaluation of the final
model on `trainX`. Keep these roles visible when reading the gap.

The exercise retains `evalResult` for inspection. Release result tensors
after their final use in an application. Report your measured scores. The
story's 0.518 and 94% belong to the crew's fictional run and are not targets
for this exercise.

For `diagnose`, check the gap first: greater than 0.15 returns `large-gap`.
Otherwise, if both scores are below 0.7, return `low-scores`. All other cases
return `no-gap-warning`. Set `verdict` from the measured values. These labels
describe results without identifying a cause or approving deployment.

The order matters. Scores 0.68 and 0.40 satisfy both warnings, but the gap
rule wins and returns `large-gap`. A gap equal to 0.15 does not pass `> 0.15`.
A score equal to 0.7 is not below 0.7. Check these boundaries separately
from the numbers your training run happens to produce.

## Compare with a declared baseline

The training labels tie at 50 of each class, so there is no unique majority
label. Before looking at evaluation results, choose this simple baseline:
always predict 0, including when the training counts tie. Then score it
against the same 43 labels as the model:

<CodeBlock language="typescript" title="constant-baseline.ts">
{`const baselineClass = 0; // Declared before inspecting evaluation results.
const heldOutLabels = Array.from(testY.dataSync());
const baselineCorrect = heldOutLabels.filter(label => label === baselineClass).length;
const baselineAccuracy = baselineCorrect / heldOutLabels.length;
console.log('Constant-0 baseline accuracy:', baselineAccuracy);
console.log('Measured model accuracy:', testAcc);`}
</CodeBlock>

This rule gets the 20 label-0 cases right: `20 / 43`, about 46.5%. It misses
all 23 label-1 cases. Compare your measured model accuracy and its missed
anomalies with those results. Choosing class 1 after seeing the held-out
labels would change the comparison policy using the test set.

## What the evaluation supports

A **validation set** supports choices such as when to stop or which threshold
to keep. Reserve a **test set** until you finish those choices.
Repeatedly tuning on test results turns that set into another validation set.
For a real time-ordered archive, assign earlier and later groups before
shuffling. Separately shuffled `take()` and `skip()` calls can overlap.

A large gap can come from overfitting, changed data, incorrect labels or
mismatched preprocessing. Low scores on both sets can reflect weak inputs,
underfitting, label noise or a training problem. Inspect cases and compare a
baseline before choosing a remedy. A small gap can also occur when both
scores are poor.

How often anomalies occur also matters. When they are rare, most alerts can
be false even if the detector catches a high share of anomalies. You can
reuse the measured detection and false-alarm rates only if the threshold and
the kinds of examples within each class stay the same. A new sensor or
threshold needs new measurements.

The fictional crew scored 94.0% on 50 test rows. Here is what happened:

- Caught 23 of 26 anomalies and missed 3.
- Left all 24 calm rows alone, with no false alarms.

The crew later confirmed the three missed anomalies. Their three features looked almost calm. These counts form the **confusion matrix**. The reference below uses them to calculate precision, recall, and F1.

<DerivationDrawer summary="Why accuracy alone is not enough: precision, recall, F1">
**Every prediction lands in one of four buckets:** true positive (TP: real anomaly, flagged), false positive (FP: calm reading, flagged anyway), true negative (TN: calm reading, left alone), false negative (FN: real anomaly, missed). Every metric below is a ratio of these four counts.

**Accuracy** = `(TP + TN) / (TP + TN + FP + FN)`. Accuracy remains defined under class imbalance, but can be misleading: if 99% of signals are normal, predicting "normal" for everything scores 99% accuracy and zero useful detections.

**Precision** = `TP / (TP + FP)`: of all signals you flagged as anomalous, what fraction actually were?

**Recall** (sensitivity) = `TP / (TP + FN)`: of all true anomalies, what fraction did you catch?

**The crew's run, as a confusion matrix.** The 94.0% above came from the 50-row held-out slice: 26 anomalous rows, 24 calm ones.

|  | Predicted anomalous | Predicted calm |
|---|---|---|
| **Actually anomalous (26)** | TP = 23 | FN = 3 |
| **Actually calm (24)** | FP = 0 | TN = 24 |

Accuracy = (23 + 24) / 50 = 94.0%. Precision = 23 / 23 = 1.000. Recall = 23 / 26 = 0.885. Perfect precision coexists with three missed anomalies. Recall makes those misses visible.

**Tradeoff:** on a fixed dataset, lowering the threshold cannot reduce recall or the false-positive rate. Precision can rise or fall because the newly flagged rows can contain both true and false positives. Measure the tradeoff, then choose a cutoff for the error costs in your domain.

When a denominator is zero, report the metric as undefined or state the convention your tool uses. Do not silently present it as evidence of good performance.

**F1 score** = `2 · (precision · recall) / (precision + recall)`: harmonic mean. Use when you need a single number that punishes either extreme. For DEEP SCAN, missing a true anomaly might cost a ship. False alarms cost crew time. The right metric depends on which cost you're willing to absorb.

**ROC and PR curves.** Sweep the threshold and plot the results: a precision-recall (PR) curve shows precision against recall, and an ROC (receiver operating characteristic) curve shows the true-positive rate (the recall you just computed) against the false-positive rate, the fraction of calm rows falsely flagged. One accuracy number from one threshold hides both curves.
</DerivationDrawer>

The crew chose a test set with almost equal numbers of calm and anomalous rows. That helps inspect both classes, but does not match the live stream, where anomalies are rare.

Its precision of 1.000 and overall accuracy may not apply to live data. To estimate those values, use a representative sample or explain and justify weights that account for the different class proportions.

<DerivationDrawer summary="What an alarm is worth: Bayes' theorem and base rates">
**Precision depends on how often anomalies occur.** The crew's test set had 26 anomalous rows and 24 calm rows. Live sensor data is mostly calm.

The calculation below changes only the anomaly frequency. It assumes the threshold and the kinds of examples within each class stay fixed. If sensors, class patterns, or the threshold change, measure sensitivity and false-positive rate again.

**Bayes' theorem converts between the two.** The bridge needs the probability of an actual anomaly among the readings that trigger an alarm. An alarm can happen two ways, a caught anomaly or a false positive:

`P(anomaly | alarm) = (sens · prior) / (sens · prior + FPR · (1 - prior))`

Here sens is the sensitivity (the recall from the drawer above), FPR is the false-positive rate (the share of calm readings falsely flagged), and the prior is how common anomalies are before any alarm fires.

**No false alarms on a small sample.** FP = 0 on 24 calm rows says less than it seems: on 24 independent calm trials with the same true 4% FPR, a detector would still print a clean 24-for-24 run about 38% of the time (0.96²⁴ ≈ 0.38). Zero observed false positives bounds the FPR loosely. It does not make the FPR zero.

**Worked example.** Take sens = 0.885 (the recall above), assume FPR = 2%, and suppose 1 reading in 1,000 on the live stream is genuinely anomalous (prior = 0.001):

`(0.885 × 0.001) / (0.885 × 0.001 + 0.02 × 0.999) = 0.000885 / 0.020865 ≈ 0.042`

Under those assumed rates, about 4% of live alarms would be true positives. This projection assumes a 2% FPR. The small test slice provides too little evidence to establish that rate. Every percentage point of FPR is 10 false alarms per 1,000 calm readings, and each one costs crew time.

A cheaper filter can reduce the number of readings reaching an expensive model. It also changes which examples that model sees. Remeasure sensitivity and FPR on the filtered population. Raising its anomaly prevalence does not by itself establish the combined system's performance.
</DerivationDrawer>
