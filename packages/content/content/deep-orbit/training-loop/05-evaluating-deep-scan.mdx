## Read the mistakes behind the score

The visual's twelve cases show why one accuracy number is not enough. A
missed anomaly and a false alarm have different costs. **Precision** is the
share of alerts that were true anomalies; **recall** is the share of actual
anomalies caught. Inspect these alongside accuracy and individual errors.

Mirza's next request is a separate evaluation. The challenge supplies 100
synthetic training rows and 43 evaluation rows: 40 generated examples and
three hand-written story cases. Keep those evaluation rows and labels out of
training. Their scores describe this fixture, not a live spacecraft system.

## Train, then measure separate rows

The compiled model and tensors are supplied. Fit only the training pair, then
evaluate the separate pair:

<CodeBlock language="typescript" title="measure-the-gap.ts">
{`const history = await model.fit(trainX, trainY, {
  epochs: 30, batchSize: 16,
});
const evalResult = model.evaluate(testX, testY); // [loss, accuracy]
const trainAcc = history.history.acc.at(-1);
const testAcc = evalResult[1].dataSync()[0];
const gap = trainAcc - testAcc;`}
</CodeBlock>

`evaluate()` returns loss followed by the metrics configured at compile time.
Read accuracy from the second tensor here. The exercise retains `evalResult`
for inspection; release result tensors after their final use in an application.
Report your measured scores. The story's 0.518 and 94% belong to the crew's
fictional run and are not targets for this exercise.

For `diagnose`, check the gap first: greater than 0.15 returns `large-gap`.
Otherwise, if both scores are below 0.7, return `low-scores`; all other cases
return `no-gap-warning`. Set `verdict` from the measured values. These labels
describe results without identifying a cause or approving deployment.

## Decide what the evidence can support

A **validation set** supports choices such as when to stop or which threshold
to keep. A **test set** stays untouched until those choices are fixed.
Repeatedly tuning on test results turns that set into another validation set.
For a real time-ordered archive, assign earlier and later groups before
shuffling; separately shuffled `take()` and `skip()` calls can overlap.

Compare the network with a simple baseline on the same held-out rows. For
example, predict the training set's most common class. A large gap can come
from overfitting, changed data, incorrect labels or mismatched preprocessing.
Investigate those before choosing a remedy.

How often anomalies occur also matters. When they are rare, most alerts can
be false even if the detector catches a high share of anomalies. You can
reuse the measured detection and false-alarm rates only if the threshold and
the kinds of examples within each class stay the same. A new sensor or
threshold needs new measurements.

Choose a **baseline**, a simple method to compare with the network. For classification, try always predicting the most common training label. Find that label using only training data, then score both methods on the same held-out rows.

If 90% of test builds succeed, always predicting success scores 90% accuracy but catches no failures. The confusion matrix below shows that problem. Check whether the network improves the results that matter before accepting its extra complexity.

The story keeps sample 7741 at a score of 0.518 in the crew's run. That number is a fictional plot result, not a reproducible property of the fixture. The earlier untrained scores had no earned interpretation, and this trained score does not prove that the reading is alien, unknowable or uniquely ambiguous. It is a reason to inspect the data and the model's coverage.

**Interpreting results:**
- Training accuracy far above validation accuracy can suggest overfitting. Check distribution changes, labels and preprocessing too. If overfitting is the cause, compare early stopping, simpler models or regularization on validation data.
- Low scores on both sets can reflect underfitting, poor inputs, label noise or a training problem. Compare a baseline and inspect errors before adding layers.
- High aggregate scores still need inspection by class and operating condition. The exercise reports a large gap, low scores or no gap warning. None of these labels certifies model health.

While you are still changing the model, measure the gap against the validation score instead of the test score. The test slice is scored once, after the settings are frozen.

The fictional crew scored 94.0% on 50 test rows. Here is what happened:

- Caught 23 of 26 anomalies and missed 3.
- Left all 24 calm rows alone, with no false alarms.

The three misses were confirmed later. Their three features looked almost calm. These counts form the **confusion matrix**. The reference below uses them to calculate precision, recall, and F1.

<DerivationDrawer summary="Why accuracy alone is not enough: precision, recall, F1">
**Every prediction lands in one of four buckets:** true positive (TP: real anomaly, flagged), false positive (FP: calm reading, flagged anyway), true negative (TN: calm reading, left alone), false negative (FN: real anomaly, missed). Every metric below is a ratio of these four counts.

**Accuracy** = `(TP + TN) / (TP + TN + FP + FN)`. Accuracy remains defined under class imbalance, but can be misleading: if 99% of signals are normal, predicting "normal" for everything scores 99% accuracy and zero useful detections.

**Precision** = `TP / (TP + FP)`: of all signals you flagged as anomalous, what fraction actually were?

**Recall** (sensitivity) = `TP / (TP + FN)`: of all true anomalies, what fraction did you catch?

**The crew's run, as a confusion matrix.** The 94.0% above came from the 50-row held-out slice: 26 anomalous rows, 24 calm ones.

|  | Predicted anomalous | Predicted calm |
|---|---|---|
| **Actually anomalous (26)** | TP = 23 | FN = 3 |
| **Actually calm (24)** | FP = 0 | TN = 24 |

Accuracy = (23 + 24) / 50 = 94.0%. Precision = 23 / 23 = 1.000. Recall = 23 / 26 = 0.885. One aggregate number became three, and the three disagree: perfect precision, and a recall hole exactly where the late-confirmed, disguised anomalies live. That is what "aggregate accuracy hides failure modes" looks like in practice.

**Tradeoff:** on a fixed dataset, lowering the threshold cannot reduce recall or the false-positive rate. Precision can rise or fall because the newly flagged rows can contain both true and false positives. Measure the tradeoff, then choose a cutoff for the error costs in your domain.

When a denominator is zero, report the metric as undefined or state the convention your tool uses; do not silently present it as evidence of good performance.

**F1 score** = `2 · (precision · recall) / (precision + recall)`: harmonic mean. Use when you need a single number that punishes either extreme. For DEEP SCAN, missing a true anomaly might cost a ship. False alarms cost crew time. The right metric depends on which cost you're willing to absorb.

**ROC and PR curves.** Sweep the threshold and plot the results: a precision-recall (PR) curve shows precision against recall, and an ROC (receiver operating characteristic) curve shows the true-positive rate (the recall you just computed) against the false-positive rate, the fraction of calm rows falsely flagged. One accuracy number from one threshold hides both curves.
</DerivationDrawer>

The crew chose a test set with almost equal numbers of calm and anomalous rows. That helps inspect both classes, but does not match the live stream, where anomalies are rare.

Its precision of 1.000 and overall accuracy may not apply to live data. To estimate those values, use a representative sample or explain and justify weights that account for the different class proportions.

<DerivationDrawer summary="What an alarm is worth: Bayes' theorem and base rates">
**Precision depends on how often anomalies occur.** The crew's test set had 26 anomalous rows and 24 calm rows. Live sensor data is mostly calm.

The calculation below changes only the anomaly frequency. It assumes the threshold and the kinds of examples within each class stay fixed. If sensors, class patterns, or the threshold change, measure sensitivity and false-positive rate again.

**Bayes' theorem converts between the two.** The number the bridge actually needs is P(anomaly | alarm), read as: the probability an anomaly is really there, given that the alarm fired. The bar means "given that", not "or". An alarm can happen two ways, a caught anomaly or a false positive:

`P(anomaly | alarm) = (sens · prior) / (sens · prior + FPR · (1 - prior))`

Here sens is the sensitivity (the recall from the drawer above), FPR is the false-positive rate (the share of calm readings falsely flagged), and the prior is how common anomalies are before any alarm fires.

**First, honesty about the false-positive rate.** FP = 0 on 24 calm rows says less than it seems: on 24 independent calm trials with the same true 4% FPR, a detector would still print a clean 24-for-24 run about 38% of the time (0.96²⁴ ≈ 0.38). Zero observed false positives bounds the FPR loosely; it does not make the FPR zero.

**Worked example.** Take sens = 0.885 (the recall above), assume FPR = 2%, and suppose 1 reading in 1,000 on the live stream is genuinely anomalous (prior = 0.001):

`(0.885 × 0.001) / (0.885 × 0.001 + 0.02 × 0.999) = 0.000885 / 0.020865 ≈ 0.042`

Under those assumed rates, about 4% of live alarms would be true positives. This is a projection using an assumed 2% FPR, not an estimate established by the small test slice. Every percentage point of FPR is 10 false alarms per 1,000 calm readings, and each one costs crew time.

A cheaper filter can reduce the number of readings reaching an expensive model. It also changes which examples that model sees. Remeasure sensitivity and FPR on the filtered population; raising its anomaly prevalence does not by itself establish the combined system's performance.
</DerivationDrawer>
