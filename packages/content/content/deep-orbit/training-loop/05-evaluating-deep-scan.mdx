## The Final Test

A model can post ninety-five percent training accuracy and sixty percent on signals it has never seen, and if the run held nothing back, nothing in its logs will warn you. Lesson 4's validation curve is the first warning. This lesson adds the second, measured on rows no decision ever touched. Mirza wants that gap investigated. Overfitting is one possible cause; changed data, poor labels or mismatched preprocessing can also lower the held-out score. Like an E2E test, an evaluation checks selected cases. The cases must represent the conditions you intend to deploy into.

<BridgeCallout bridge={frontmatter.concept.bridge} />

A validation set is data the training loop is allowed to read so it can make decisions. Those decisions include when to stop in lesson 4, where to put a threshold later, and which settings to keep. Because those decisions were made to look good on it, its score is slightly flattered and is no longer a clean estimate. A test set is data no decision ever touched, scored once and reported. Lesson 4's val_loss of 0.081 was spent on the stopping decision, which is exactly why this lesson holds out a fresh slice the loop never saw. That run split coarsely: `validationSplit: 0.2` carved one twenty percent slice and no test slice at all. The capstone's model card records the three-way version, an 80/10/10 split of the archive.

Before scoring the network, choose a **baseline**: a simple method it needs to improve on. For a classifier, start by predicting the training set's most common class for every held-out row. Compute that class from training labels only, then evaluate the baseline and network on the same rows. If 90% of test builds succeed, always predicting success scores 90% accuracy while catching no failures. The confusion matrix below makes that limitation visible. A more complex model earns its place through a useful improvement, not simply because it trained.

One entry for the strangest page in the ship's records: back before this network had seen a single label, an untrained build scored sample 7741 at 0.998, and a brand-new reinitialization, fresh random numbers and all, scored it 0.997. Untrained networks of this shape do not do that. Build this same 3-32-16-1 stack 20,000 times without training it and ask each build about a reading that sits mid-scale on all three features. The answers pile onto the fence: the median is 0.500 and nine in ten land inside 0.45 to 0.55. Around one build in four hundred gets past 0.60, and none of the 20,000 reached 0.75, let alone 0.99. Nobody explained 7741 then and nobody explains it now. Trained, the network still will not commit on it, at 51.8 on the one reading the crew cannot label.

**Interpreting results:**
- Training accuracy far above validation accuracy can suggest overfitting. Check distribution changes, labels and preprocessing too. If overfitting is the cause, compare early stopping, simpler models or regularization on validation data.
- Low scores on both sets can reflect underfitting, poor inputs, label noise or a training problem. Compare a baseline and inspect errors before adding layers.
- High aggregate scores still need inspection by class and operating condition. The exercise's gap rule is a simplified diagnostic convention, not proof of model health.

While you are still changing the model, measure the gap against the validation score instead of the test score. The test slice is scored once, after the settings are frozen.

Accuracy hides the shape of the error. The crew's 94.0% splits into four counts on that 50-row slice: 23 of the 26 anomalous rows caught, 3 missed, all 24 calm rows left alone, no false alarms. The three misses are exactly the late-confirmed rows, the ones that read almost calm in these three features. Those four counts are the confusion matrix, and the drawer below turns them into precision, recall and F1.

<DerivationDrawer summary="Why accuracy alone is not enough: precision, recall, F1">
**Every prediction lands in one of four buckets:** true positive (TP: real anomaly, flagged), false positive (FP: calm reading, flagged anyway), true negative (TN: calm reading, left alone), false negative (FN: real anomaly, missed). Every metric below is a ratio of these four counts.

**Accuracy** = `(TP + TN) / (TP + TN + FP + FN)`. This breaks under class imbalance: if 99% of signals are normal, predicting "normal" for everything scores 99% accuracy and zero useful detections.

**Precision** = `TP / (TP + FP)`: of all signals you flagged as anomalous, what fraction actually were?

**Recall** (sensitivity) = `TP / (TP + FN)`: of all true anomalies, what fraction did you catch?

**The crew's run, as a confusion matrix.** The 94.0% above came from the 50-row held-out slice: 26 anomalous rows, 24 calm ones.

|  | Predicted anomalous | Predicted calm |
|---|---|---|
| **Actually anomalous (26)** | TP = 23 | FN = 3 |
| **Actually calm (24)** | FP = 0 | TN = 24 |

Accuracy = (23 + 24) / 50 = 94.0%. Precision = 23 / 23 = 1.000. Recall = 23 / 26 = 0.885. One aggregate number became three, and the three disagree: perfect precision, and a recall hole exactly where the late-confirmed, disguised anomalies live. That is what "aggregate accuracy hides failure modes" looks like in practice.

**Tradeoff:** on a fixed dataset, lowering the threshold cannot reduce recall or the false-positive rate. Precision can rise or fall because the newly flagged rows can contain both true and false positives. Measure the tradeoff, then choose a cutoff for the error costs in your domain.

**F1 score** = `2 · (precision · recall) / (precision + recall)`: harmonic mean. Use when you need a single number that punishes either extreme. For DEEP SCAN, missing a true anomaly might cost a ship. False alarms cost crew time. The right metric depends on which cost you're willing to absorb.

**ROC and PR curves.** Sweep the threshold and plot the results: a precision-recall (PR) curve shows precision against recall, and an ROC (receiver operating characteristic) curve shows the true-positive rate (the recall you just computed) against the false-positive rate, the fraction of calm rows falsely flagged. One accuracy number from one threshold hides both curves.
</DerivationDrawer>

One of those four counts deserves suspicion before anyone celebrates: the empty false-alarm cell (precision 1.000, in the drawer above) was measured on a slice where half the rows are anomalous, because the crew built the slice that way. The live stream is not that slice. An eval set built to be balanced instead of drawn from production is selection bias in miniature.

<DerivationDrawer summary="What an alarm is worth: Bayes' theorem and base rates">
**Precision depends on how common anomalies are.** Sensitivity and false-positive rate also depend on the decision threshold and the distribution of examples within each class. The calculation below assumes those stay fixed while only the anomaly frequency changes. If sensors, class patterns, or the threshold change, remeasure those rates. The held-out slice (26 anomalous, 24 calm) was assembled to be near balanced; live hull telemetry is overwhelmingly calm.

**Bayes' theorem converts between the two.** The number the bridge actually needs is P(anomaly | alarm), read as: the probability an anomaly is really there, given that the alarm fired. The bar means "given that", not "or". An alarm can happen two ways, a caught anomaly or a false positive:

`P(anomaly | alarm) = (sens · prior) / (sens · prior + FPR · (1 - prior))`

Here sens is the sensitivity (the recall from the drawer above), FPR is the false-positive rate (the share of calm readings falsely flagged), and the prior is how common anomalies are before any alarm fires.

**First, honesty about the false-positive rate.** FP = 0 on 24 calm rows says less than it seems: a detector with a true 4% FPR would still print a clean 24-for-24 run about 38% of the time (0.96²⁴ ≈ 0.38). Zero observed false positives bounds the FPR loosely; it does not make the FPR zero.

**Worked example.** Take sens = 0.885 (the recall above), assume FPR = 2%, and suppose 1 reading in 1,000 on the live stream is genuinely anomalous (prior = 0.001):

`(0.885 × 0.001) / (0.885 × 0.001 + 0.02 × 0.999) = 0.000885 / 0.020865 ≈ 0.042`

Under those assumed rates, about 4% of live alarms would be true positives. This is a projection using an assumed 2% FPR, not an estimate established by the small test slice. Every percentage point of FPR is 10 false alarms per 1,000 calm readings, and each one costs crew time.

A cheaper filter can reduce the number of readings reaching an expensive model. It also changes which examples that model sees. Remeasure sensitivity and FPR on the filtered population; raising its anomaly prevalence does not by itself establish the combined system's performance.
</DerivationDrawer>
