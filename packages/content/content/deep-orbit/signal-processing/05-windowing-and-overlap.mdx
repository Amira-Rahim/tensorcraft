## The Spectral Leakage Problem

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="spectral-leakage.ts">
{`import * as tf from '@tensorflow/tfjs';

// Generate a 10.5 Hz sine wave: ten and a half cycles per 1-second window.
// A 10 Hz tone would fit exactly and leak nothing; the half cycle is the problem.
const sampleRate = 128;
const signal: number[] = [];
for (let i = 0; i < 128; i++) {
  signal.push(Math.sin(2 * Math.PI * 10.5 * i / sampleRate));
}

// Problem: the window doesn't capture exact whole periods.
// The last sample sits at 0.49; the wrapped-around start is 0.0.
// The FFT treats the window as one period of a repeating signal,
// sees that jump at the seam, and invents frequencies to explain it.
const rawFFT = tf.tidy(() => {
  const fft = tf.spectral.rfft(tf.tensor1d(signal));
  return tf.abs(fft).arraySync() as number[];
});

// Expected: energy at 10.5 Hz only (between bins 10 and 11)
// Actual: the peak smears across the whole spectrum
console.log('Bin 10:', rawFFT[10].toFixed(1));            // ~41.7
console.log('Bin 11:', rawFFT[11].toFixed(1));            // ~39.9
console.log('Bin 9 (leakage):', rawFFT[9].toFixed(1));    // ~14.5, should be ~0
console.log('Bin 20 (leakage):', rawFFT[20].toFixed(1));  // ~1.6, ten bins from the tone`}
</CodeBlock>

## The Fix: Window Functions

<CodeBlock language="typescript" title="window-functions.ts">
{`// A window function smoothly tapers the signal to zero at the edges
// Like CSS opacity fading at the edges of a virtual scroll viewport

// Hann window: the most common choice (good all-around)
function hannWindow(n: number): number[] {
  return Array.from({ length: n }, (_, i) =>
    0.5 * (1 - Math.cos(2 * Math.PI * i / (n - 1)))
  );
}

// Hamming window: slightly less leakage, slightly wider main lobe
function hammingWindow(n: number): number[] {
  return Array.from({ length: n }, (_, i) =>
    0.54 - 0.46 * Math.cos(2 * Math.PI * i / (n - 1))
  );
}

// Apply window: multiply element-wise
function applyWindow(signal: number[], window: number[]): number[] {
  return signal.map((s, i) => s * window[i]);
}

// Compare: raw FFT vs windowed FFT
const hann = hannWindow(128);
const windowedSignal = applyWindow(signal, hann);

const windowedFFT = tf.tidy(() => {
  const fft = tf.spectral.rfft(tf.tensor1d(windowedSignal));
  return tf.abs(fft).arraySync() as number[];
});

console.log('--- Without windowing ---');
console.log('Bin 9:', rawFFT[9].toFixed(1));    // ~14.5
console.log('Bin 20:', rawFFT[20].toFixed(1));  // ~1.6
console.log('Bin 30:', rawFFT[30].toFixed(1));  // ~0.6, leakage all the way out

console.log('--- With Hann window ---');
console.log('Bin 9:', windowedFFT[9].toFixed(1));    // ~5.6, main lobe slightly wider
console.log('Bin 20:', windowedFFT[20].toFixed(1));  // ~0.0
console.log('Bin 30:', windowedFFT[30].toFixed(1));  // ~0.0, far leakage gone
// The trade: Hann spreads the peak over a slightly wider main lobe
// (bins 10-11 read ~27.0 instead of ~41.7) but crushes the sidelobe
// leakage that was smearing across the entire spectrum.`}
</CodeBlock>

## Overlapping Windows

Windowing tapers the signal to zero at the edges, which means you lose information there. The solution: overlap your windows so every sample gets full weight in at least one window.

<CodeBlock language="typescript" title="overlap.ts">
{`// Without overlap: gaps in information at window boundaries
// With 50% overlap: every sample is fully weighted in at least one window
// Like virtual scrolling with overscan: rendering extra items beyond the viewport

function stftWithWindowing(
  signal: number[],
  windowSize: number,
  hopSize: number,      // hopSize = windowSize/2 for 50% overlap
  windowFn: (n: number) => number[],
): number[][] {
  const window = windowFn(windowSize);
  const spectrogram: number[][] = [];
  const numWindows = Math.floor((signal.length - windowSize) / hopSize) + 1;

  for (let i = 0; i < numWindows; i++) {
    const start = i * hopSize;
    const chunk = signal.slice(start, start + windowSize);
    const windowed = applyWindow(chunk, window);

    const magnitudes = tf.tidy(() => {
      const fft = tf.spectral.rfft(tf.tensor1d(windowed));
      return tf.abs(fft).arraySync() as number[];
    });

    spectrogram.push(magnitudes);
  }

  return spectrogram;
}

// 50% overlap is the standard: good balance of coverage and computation.
// Our demo signal is 128 samples, so use a 64-sample window with hop 32
const spec = stftWithWindowing(signal, 64, 32, hannWindow);
console.log('Windows:', spec.length);          // 3
console.log('Frequency bins:', spec[0].length); // 33`}
</CodeBlock>

<DerivationDrawer summary="Why window + overlap matters">
**Windowing:** multiplying the signal segment by a window function (Hann, Hamming, ...) before FFT reduces **spectral leakage**: energy from real frequencies smearing into adjacent FFT bins. Without windowing, a sinusoid that doesn't fit perfectly in the window produces a wide smeared response.

**Window math (Hann):**

`w[n] = 0.5 · (1 - cos(2π · n / (W - 1)))`

**Overlap:** consecutive FFT windows share data. With 50% overlap (hop = W/2), each sample appears in 2 windows. With 75% overlap (hop = W/4), each sample appears in 4. More overlap = smoother spectrogram, more compute.

**Constant-overlap-add (COLA) condition:** for perfect signal reconstruction from STFT, the shifted windows must sum to a constant: `Σ_k w[t - hop·k] = constant`. The window and hop must be chosen as a pair: Hann satisfies COLA at 50% or 75% overlap, while a Blackman window at 50% overlap does not.

For real-time inference: smaller hop = lower latency between input and STFT availability, at the cost of more FFTs per second.
</DerivationDrawer>
