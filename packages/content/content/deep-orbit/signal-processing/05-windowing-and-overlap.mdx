Demir has the shape of the fix right. The FFT treats your slice as one period of an infinitely repeating signal, so a hard edge is a real discontinuity in that repeating version, and that artificial boundary spreads the tone across frequency bins. Handling the boundary beats cutting through it, in a byte stream and in a capture. The price is where the two part company. A taper spends real signal to buy a clean spectrum, and the rest of this lesson is what it spends.

## The Spectral Leakage Problem

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="spectral-leakage.ts">
{`import * as tf from '@tensorflow/tfjs';

// Generate a 10.5 Hz sine wave: ten and a half cycles per 1-second window.
// A 10 Hz tone would fit exactly and leak nothing; the half cycle is the problem.
const sampleRate = 128;
const signal: number[] = [];
for (let i = 0; i < 128; i++) {
  signal.push(Math.sin(2 * Math.PI * 10.5 * i / sampleRate));
}

// Problem: the window doesn't capture exact whole periods.
// The last sample sits at 0.49; the wrapped-around start is 0.0.
// The FFT treats the window as one period of a repeating signal,
// sees that jump at the seam, and invents frequencies to explain it.
const rawFFT = tf.tidy(() => {
  const fft = tf.spectral.rfft(tf.tensor1d(signal));
  return tf.abs(fft).arraySync() as number[];
});

// Expected: energy at 10.5 Hz only (between bins 10 and 11)
// Actual: the peak smears across the whole spectrum
console.log('Bin 10:', rawFFT[10].toFixed(1));            // ~41.7
console.log('Bin 11:', rawFFT[11].toFixed(1));            // ~39.9
console.log('Bin 9 (leakage):', rawFFT[9].toFixed(1));    // ~14.5, should be ~0
console.log('Bin 20 (leakage):', rawFFT[20].toFixed(1));  // ~1.6, ten bins from the tone`}
</CodeBlock>

## The Fix: Window Functions

<CodeBlock language="typescript" title="window-functions.ts">
{`// A window function smoothly tapers the signal down at the edges, so the
// slice ends near the level it started at and the cut is never a cliff.
// Hann is the all-round default: one raised cosine spread over the slice.
// The challenge asks you for the symmetric form,
// w[i] = 0.5 * (1 - cos(2*pi*i / (n - 1))), which reaches exactly zero at
// both ends. tfjs ships the periodic variant:
const hann = tf.tidy(() => Array.from(tf.signal.hannWindow(128).dataSync()));
// One convention note. For an even n the built-in uses the periodic form,
// 2*pi*i / n, so at n = 128 its last weight is 0.0006 rather than 0, and it
// never differs from the n - 1 form by more than 0.019 per sample (0.038 at
// n = 64). The n - 1 form is the one the challenge asks you to write, and
// no number below moves by more than a quarter between the two.
// Hamming stops at 0.08 instead of zero, and that leftover step is why its
// far sidelobes fall off more slowly (see below).

// Terms for the comparison below. The main lobe is the cluster of bins the
// tone itself occupies. The sidelobes are the smaller ripples further out.
// dB is a log ratio: -31 dB is about 1/35 of the peak height, -43 dB about
// 1/141. A dB/octave figure says how fast the ripples shrink as you move
// away from the peak, per doubling of that distance.

// Hamming window: main lobe as narrow as Hann's or slightly narrower,
// and a lower FIRST sidelobe (about -43 dB vs Hann's -31), but its far
// sidelobes decay at only ~-6 dB/octave vs Hann's ~-18: much worse
// far-field leakage. Pick it for close-in resolution, not cleanliness.
function hammingWindow(n: number): number[] {
  return Array.from({ length: n }, (_, i) =>
    0.54 - 0.46 * Math.cos(2 * Math.PI * i / (n - 1))
  );
}

// Apply window: multiply element-wise
function applyWindow(signal: number[], window: number[]): number[] {
  return signal.map((s, i) => s * window[i]);
}

// Compare: raw FFT vs windowed FFT
const windowedSignal = applyWindow(signal, hann);

const windowedFFT = tf.tidy(() => {
  const fft = tf.spectral.rfft(tf.tensor1d(windowedSignal));
  return tf.abs(fft).arraySync() as number[];
});

console.log('--- Without windowing ---');
console.log('Bin 9:', rawFFT[9].toFixed(1));    // ~14.5
console.log('Bin 20:', rawFFT[20].toFixed(1));  // ~1.6
console.log('Bin 30:', rawFFT[30].toFixed(1));  // ~0.6, leakage all the way out

console.log('--- With Hann window ---');
console.log('Bin 9:', windowedFFT[9].toFixed(1));    // ~5.4, down from ~14.5
console.log('Bin 20:', windowedFFT[20].toFixed(1));  // ~0.0
console.log('Bin 30:', windowedFFT[30].toFixed(1));  // ~0.0, far leakage gone

// An on-bin 10 Hz unit sine has peak 64 before this periodic Hann and
// 32 after it. Its neighbors gain magnitude, reaching 16 at bins 9/11.
// At 10.5 Hz the peak is about 27.2 rather than 41.7. A window changes
// the whole spectral shape; multiplying by its mean does not describe
// each bin. Compare like windows or apply a task-appropriate correction.
`}
</CodeBlock>

## Overlapping Windows

A sample near one frame edge can sit near the center of an overlapping frame. This gives it a stronger contribution somewhere in the spectrogram. For an even window length, periodic Hann windows shifted by half a window sum to one in the fully covered interior. Capture boundaries still need handling. The exercise uses the symmetric Hann, whose sum varies slightly; the drawer explains why that does not by itself prevent reconstruction.

<CodeBlock language="typescript" title="overlap.ts">
{`// Without overlap: gaps in information at window boundaries
// With 50% overlap the tapers interlock

function stftWithWindowing(
  signal: number[],
  windowSize: number,
  hopSize: number,      // hopSize = windowSize/2 for 50% overlap
  windowFn: (n: number) => number[],
): number[][] {
  const window = windowFn(windowSize);
  const spectrogram: number[][] = [];
  const numWindows = Math.floor((signal.length - windowSize) / hopSize) + 1;

  for (let i = 0; i < numWindows; i++) {
    const start = i * hopSize;
    const chunk = signal.slice(start, start + windowSize);
    const windowed = applyWindow(chunk, window);

    const magnitudes = tf.tidy(() => {
      const fft = tf.spectral.rfft(tf.tensor1d(windowed));
      return tf.abs(fft).arraySync() as number[];
    });

    spectrogram.push(magnitudes);
  }

  return spectrogram;
}

// 50% overlap is the standard: good balance of coverage and computation.
// Our demo signal is 128 samples, so use a 64-sample window with hop 32
const spec = stftWithWindowing(signal, 64, 32, (n) => tf.tidy(() => Array.from(tf.signal.hannWindow(n).dataSync())));
console.log('Windows:', spec.length);          // 3
console.log('Frequency bins:', spec[0].length); // 33`}
</CodeBlock>

<DerivationDrawer summary="Why window + overlap matters">
**Windowing:** multiplying the signal segment by a window function (Hann, Hamming, ...) before FFT reduces **spectral leakage**: energy from real frequencies smearing into adjacent FFT bins. Without windowing, a sinusoid that doesn't fit perfectly in the window produces a wide smeared response.

**Window math (Hann):**

`w[n] = 0.5 · (1 - cos(2π · n / (W - 1)))`

**Overlap:** consecutive FFT windows share data. Away from capture boundaries, 50% overlap (hop = W/2) gives each sample 2 windows and 75% overlap (hop = W/4) gives it 4. The beginning and end need padding or separate boundary handling. More overlap = smoother spectrogram, more compute.

**Constant-overlap-add (COLA):** a convenient condition for overlap-add reconstruction is that shifted windows sum to a constant: `Σ_k w[t - hop·k] = constant`. The window and hop must be chosen as a pair: the periodic Hann satisfies COLA at 50% or 75% overlap, while a Blackman window at 50% overlap does not.

One form-of-the-formula subtlety: the Hann formula above is the **symmetric** form (denominator `W - 1`), which is what the challenge asks you to write; this lesson's code uses the periodic form tfjs ships. Exact COLA at `hop = W/2` holds for the **periodic** form, `w[n] = 0.5 · (1 - cos(2π · n / W))`. Measured at `W = 64, hop = 32`: the periodic window's shifted copies sum to exactly 1.0, while the symmetric form's sum ripples between 0.975 and 0.999. This ripple can affect feature scales. It does not make reconstruction impossible: normalized inverse STFT can use the weaker nonzero-overlap-add (NOLA) condition, where the sum of squared window weights is nonzero at every reconstructed sample. That normalization and complete boundary coverage matter.

For real-time inference: a smaller hop produces updates more frequently, at the cost of more FFTs. Waiting for enough samples to fill the analysis window remains a separate delay.
</DerivationDrawer>
