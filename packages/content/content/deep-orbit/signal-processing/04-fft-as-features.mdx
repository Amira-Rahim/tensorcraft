> **DEEP SCAN · EVALUATION LOG** · archive re-annotated against spectrogram ground truth · inputs: raw time-domain [3] · accuracy 78.0% · rerun with +8 FFT magnitude bins [11] · accuracy 87.0% · same archive, same labels, both runs.

Nine points of accuracy, and not one new byte of sensor data. That log line is the whole lesson; the rest is understanding why it isn't a trick.

The 78 is the deployment review's 94, re-scored against labels the spectrograms corrected. The old labels could not see a 73.4 Hz component, so the old scoreboard flattered the model. Labels are data too, and some of them were wrong.

<Dialogue speaker="Ensign Demir">
What if we feed the FFT magnitudes directly into the model? Instead of just raw amplitude, frequency, and phase, we also give it the spectral decomposition. More information, better decisions.
</Dialogue>

<Dialogue speaker="Dr. Farah">
Feature engineering: deriving new inputs from raw data. I used it to rebuild the signal analyzer on the Kepler mission. One correction, though: you said "more information." The FFT adds no information; the samples already contain everything it computes. What it adds is access. The model no longer has to discover the frequency basis on its own, and I trust a model more when I know which part of the work I did for it.

<Dialogue speaker="Chief Nazari">
Access is not free either. Eleven inputs instead of three means a bigger first weight matrix, more parameters, and a longer training run on my hardware. You are nearly quadrupling the input width on a hunch, Ensign. Write down the accuracy you expect before you spend the compute.

He writes 85 on the board and signs it. He's wrong, but in the direction nobody minds. Strip the story out and what he proposed is the move behind every `useMemo`: raw inputs arrive, and the sorted list, the filtered array, the aggregated count get computed once, because the derived form is what the consumer actually needs. Feature engineering is the same move, aimed at a model instead of a render.

<CodeBlock language="typescript" title="feature-engineering.ts">
{`import * as tf from '@tensorflow/tfjs';

// BEFORE: raw signal features only (3 values)
// The model sees: [amplitude, frequency, phase]
// Accuracy: 78%

// AFTER: raw + FFT features (3 + N frequency bins)
// The model sees: [amplitude, frequency, phase, fft_bin_0, fft_bin_1, ..., fft_bin_N]
// Accuracy: 87%

function extractFeatures(signal: number[], windowSize: number = 64): number[] {
  return tf.tidy(() => {
    // Raw features (the original 3). The "frequency" feature is a raw
    // zero-crossing count over the fixed window: proportional to the
    // dominant frequency, but a count, not hertz. Name it what it is.
    const amplitude = Math.max(...signal.map(Math.abs));
    const zeroCrossings = signal.reduce((sum, v, i) =>
      i > 0 && Math.sign(v) !== Math.sign(signal[i - 1]) ? sum + 1 : sum, 0
    );
    // "phase" is the angle of the first two samples, atan2(s1, s0): a crude
    // stand-in for where the waveform sits in its cycle when the window
    // opens. The trained model expects it, so it stays, under its real name.
    const phase = Math.atan2(signal[1], signal[0]);

    // FFT features (derived from the same signal)
    const windowSlice = signal.slice(0, windowSize);
    const fft = tf.spectral.rfft(tf.tensor1d(windowSlice));
    const magnitudes = tf.abs(fft).arraySync() as number[];

    // Eight FIXED bins, the same bins for every signal. Sorting by
    // magnitude would throw away frequency identity: "fft_3" would mean
    // a different frequency in every row, and no downstream model could
    // ever ask "what lives at 72 Hz?". At this window's 4 Hz resolution
    // (256 Hz / 64 samples), bins 13-20 have centers 52-80 Hz and cover
    // 50-82 Hz, the band that sits just above every catalogued natural
    // line; the sixth of the eight (bin 18) is the span that holds the
    // 73.4 Hz line.
    const fixedBins = magnitudes.slice(13, 21);

    // Combine: [raw features..., fixed-bin FFT magnitudes...]
    return [amplitude, zeroCrossings, phase, ...fixedBins];
  });
}

// Before: model input shape [null, 3]
// After:  model input shape [null, 11]  (3 raw + 8 FFT)
console.log('Feature vector:', extractFeatures(signalSamples));`}
</CodeBlock>

## Normalization Matters

FFT magnitudes can be far larger than raw signal values. Without normalization, the model will overweight frequency features and ignore the raw ones.

<CodeBlock language="typescript" title="normalization.ts">
{`import * as tf from '@tensorflow/tfjs';

// Module 1's rule at eleven features instead of two, plus one correction
// for the optimizer below. Under plain gradient descent, the step on a
// weight scales with the input that weight multiplies. An unscaled 60.0
// in an FFT bin then moves its weight 200x further per step than a 0.3
// amplitude moves its own. This model compiles with adam, which divides
// each step by that weight's own gradient history. Those two weights end
// up taking steps of the same size, so the 200x story does not apply.
//
// Scale still costs you. With Glorot weights and features on these two
// scales, roughly 97% of the first layer's pre-activation comes from the
// eight FFT bins. The three raw features barely move a hidden unit until
// training has reweighted them. Normalizing gives all eleven the same
// say from the first step.

function normalizeFeatures(features: number[][]): { normalized: number[][]; stats: { mean: number; std: number }[] } {
  // Z-score normalization: (value - mean) / std
  // After normalization: mean ≈ 0, std ≈ 1 for each feature
  const stats = features[0].map((_, colIdx) => {
    const column = features.map(row => row[colIdx]);
    const mean = column.reduce((a, b) => a + b, 0) / column.length;
    const std = Math.sqrt(
      column.reduce((sum, v) => sum + (v - mean) ** 2, 0) / column.length
    );
    return { mean, std: std || 1 };  // avoid division by zero
  });

  const normalized = features.map(row =>
    row.map((val, i) => (val - stats[i].mean) / stats[i].std)
  );

  return { normalized, stats };
}

// Save stats from training data; apply the SAME stats during inference
// This is critical: normalize test data with training statistics
const { normalized: trainNorm, stats } = normalizeFeatures(trainingFeatures);

// During inference:
function normalizeWithStats(features: number[], stats: { mean: number; std: number }[]): number[] {
  return features.map((val, i) => (val - stats[i].mean) / stats[i].std);
}`}
</CodeBlock>

## Building the Enhanced Model

<CodeBlock language="typescript" title="enhanced-model.ts">
{`import * as tf from '@tensorflow/tfjs';

// Original model: 3 inputs → 32 → 16 → 1 (78% accuracy)
// Enhanced model: 11 inputs → 32 → 16 → 1 (87% accuracy)
// Same hidden stack, same optimizer, same epoch count. It is still a
// bigger network, exactly as Nazari said: countParams() reports 673
// parameters for the 3-input stack and 929 for the 11-input one, 38%
// more. All 256 added weights sit in the first layer, one per new input
// per unit. Nothing was added behind it, so the nine points come from
// what the new inputs say and not from a deeper or wider stack.

const enhancedModel = tf.sequential();
enhancedModel.add(tf.layers.dense({
  units: 32,
  activation: 'relu',
  inputShape: [11],  // 3 raw + 8 FFT features
}));
enhancedModel.add(tf.layers.dense({ units: 16, activation: 'relu' }));
enhancedModel.add(tf.layers.dense({ units: 1, activation: 'sigmoid' }));

enhancedModel.compile({
  optimizer: 'adam',
  loss: 'binaryCrossentropy',
  metrics: ['accuracy'],
});

// Train with enhanced features
const history = await enhancedModel.fit(trainX, trainY, {
  epochs: 50,
  validationSplit: 0.2,
  callbacks: {
    onEpochEnd: (epoch, logs) => {
      if (epoch % 10 === 0) {
        console.log(\`Epoch \${epoch}: acc=\${logs?.acc.toFixed(3)}, val_acc=\${logs?.val_acc.toFixed(3)}\`);
      }
    },
  },
});
// Epoch 0:  acc=0.523, val_acc=0.510
// Epoch 10: acc=0.712, val_acc=0.698
// Epoch 30: acc=0.853, val_acc=0.841

// (epoch 40 is the last line the % 10 callback prints: epochs count

// Neither column is the 87.0% in the evaluation log. acc is scored on the
// rows the model just trained on. val_acc is scored on the 20% that

const [, testAcc] = enhancedModel.evaluate(testX, testY) as tf.Tensor[];
console.log('Held-out accuracy:', testAcc.dataSync()[0].toFixed(3));
