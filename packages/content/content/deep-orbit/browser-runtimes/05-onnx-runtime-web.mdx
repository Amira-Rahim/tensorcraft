<Dialogue speaker="Chief Nazari">
"Anywhere" is the brochure version. ONNX is a shared operator set. If your model uses an op the target runtime doesn't implement, it doesn't degrade gracefully. It fails to load. There is no polyfill for a missing op. You re-export at an opset the runtime supports, decompose the op, or change the layer as a last resort. Check the opset before you promise me portability. Then bring me the numbers.
</Dialogue>

ONNX (Open Neural Network Exchange) is ML's attempt at a web standard: a shared format any compliant runtime can execute, whatever framework did the training. The operator set is what scopes "compliant."
That set is versioned. Each opset number fixes which ops exist and how they behave. An export names an opset version, and a runtime implements up to some version. Export at a version the runtime supports, and where the exporter has a decomposition it emits older ops in place of the newer single one.

Demir runs the check before he writes a line of benchmark code. DEEP SCAN exports clean: dense layers and a sigmoid, the plain HTML of the operator world, implemented by every runtime that matters. The models that fail Nazari's check carry a researcher's favorite exotic op, one that mapped cleanly on export and landed in the graph. The target runtime never implemented it, so the failure surfaces when that runtime builds the session.

## TF.js vs ONNX Runtime: Head-to-Head

<CodeBlock language="typescript" title="benchmark-comparison.ts">
{`import * as tf from '@tensorflow/tfjs';
import '@tensorflow/tfjs-backend-wasm';
import * as ort from 'onnxruntime-web';

interface BenchmarkResult {
  runtime: string;
  coldStartMs: number;
  avgInferenceMs: number;
  weightKB: number;
}

// Both sides run on WASM. TF.js on WebGL against ONNX Runtime on WASM
// would measure the backend, and the backend is the bigger of the two
// effects, so the runtime difference would be buried under it.
async function benchmarkTFJS(): Promise<BenchmarkResult> {
  const t0 = performance.now();

  // Inside the clock on purpose. This pair fetches and instantiates the
  // WASM backend binary, and ORT Web does that same work inside
  // InferenceSession.create. Hoist it above t0 and TF.js reports a cold
  // start missing a cost the ONNX number still carries.
  await tf.setBackend('wasm');
  await tf.ready();
  const model = await tf.loadLayersModel('/models/deep-scan/model.json');

  // The first prediction is inside the clock too. A WebGL kernel compiles
  // its shader the first time it runs, not when the model loads, so a
  // cold start stopped at the load call would miss compilation entirely.
  // This call doubles as the warm-up for the loop below.
  const warmup = tf.tensor2d([[0.5, 0.3, 0.7]]);
  const first = model.predict(warmup) as tf.Tensor;
  await first.data();
  first.dispose();
  warmup.dispose();

  const coldStartMs = performance.now() - t0;

  // Sustained inference (100 iterations)
  const times: number[] = [];
  for (let i = 0; i < 100; i++) {
    const start = performance.now();
    const out = tf.tidy(() => {
      const input = tf.tensor2d([[Math.random(), Math.random(), Math.random()]]);
      return model.predict(input) as tf.Tensor;
    });
    // Read the result back INSIDE the timed region. On WASM the compute
    // is already done when predict returns, so this await costs nothing.
    // Leave it out and the clock starts measuring enqueue time the day
    // someone swaps in a GPU backend, because GPU kernels are queued.
    await out.data();
    out.dispose();
    times.push(performance.now() - start);
  }

  return {
    runtime: 'TF.js (WASM)',
    coldStartMs,
    avgInferenceMs: times.reduce((a, b) => a + b, 0) / times.length,
    // tf.memory().numBytes is a live-tensor ledger. With the loop's
    // tensors disposed it holds the 673 parameters and nothing else, which
    // is a figure the other runtime can match. What it does not hold is
    // the runtime's own footprint; that is the WASM binary you ship, a
    // bundle number rather than a bench number.
    weightKB: tf.memory().numBytes / 1024,
  };
}

// benchmarkONNX() is the SAME harness with five differences:
//
//   init:   the setBackend/ready pair has no ORT Web counterpart, because
//           InferenceSession.create fetches and compiles the ORT WASM
//           binary itself on first use. That is why the TF.js pair sits
//           below t0: the same cost is then inside both timed regions
//   load:   await ort.InferenceSession.create('/models/deep-scan.onnx',
//           { executionProviders: ['wasm'] }) replaces
//           tf.loadLayersModel(...)
//   input:  new ort.Tensor('float32', new Float32Array([...]), [1, 3])
//           replaces the tf.tensor2d call inside tf.tidy
//   run:    await session.run({ input }) replaces model.predict plus the
//           explicit readback await; session.run resolves when compute
//           finishes, and these CPU-located ort.Tensors are
//           garbage-collected, so the dispose bookkeeping goes too
//   memory: ORT Web keeps no tensor ledger, so weightKB comes off the
//           model's initializers instead of tf.memory().numBytes. Same
//           673 floats either way
//
// Everything else (the timed first call, the 100-iteration loop, the
// averaging, the result shape with runtime: 'ONNX Runtime Web (WASM)')
// stays byte-identical. In a benchmark, any difference outside the thing
// being measured contaminates the measurement.

// One laptop, one Chrome build, empty HTTP cache. Cold start runs from t0
// to the end of the first prediction, so runtime init is inside it on
// both sides. These are that machine's numbers, not a property of either
// runtime:
// TF.js (WASM):             inference=0.9ms, weights=2.6KB
// ONNX Runtime Web (WASM):  inference=0.7ms, weights=2.6KB
//
// Same model, same laptop, TF.js switched to WebGL:
// TF.js (WebGL):            inference=2.4ms, weights=2.6KB
//
// No cold-start milliseconds are printed here. On an empty cache that
// number is mostly one download, and the two downloads are nowhere near
// the same size: the table below has TF.js fetching about 2MB of runtime
// and ORT Web fetching tens of megabytes of WASM. ORT Web starts slower
// here for that reason, and by how much belongs to your link and your
// machine. Measure it there before you budget for it.
//
// 673 parameters is about six hundred multiply-adds per prediction.
// Getting the input onto the GPU and the answer back off it costs more
// than that, so the GPU loses the call it was supposed to win. Lesson 2
// of this module clocked WebGL six times faster than WASM, but that was
// a bare 256x256 matmul: tens of millions of multiply-adds, the work a
// GPU is built for. A WebGL cold start also pays something neither WASM
// run does: each WebGL kernel compiles a shader the first time it runs,
// and the first run is the prediction inside the clock above.`}

## When to Choose Which

| Factor | TF.js | ONNX Runtime Web |
|--------|-------|-------------------|
| **Ecosystem** | Largest, most tutorials | Growing fast |
| **GPU acceleration** | WebGL (mature) + WebGPU (the newer compute path) | WebGPU (its primary GPU path) |
| **Python interop** | Export from TF/Keras | Any framework via ONNX export |
| **Cold start on WASM, timed to the first prediction** | Shorter here: about 2MB of runtime to fetch | Longer here: tens of MB of WASM to fetch |
| **Sustained speed on WASM, 673 params** | 0.9ms per call | 0.7ms per call |
| **Memory management** | Manual (tf.tidy/dispose) | Split: CPU tensors are garbage-collected, the session and GPU tensors are freed by hand |
| **Bundle size, minified / gzipped at `gzip -6`** | 1.47MB / 368KB | 368KB / 98KB |

The memory row splits three ways. ORT Web's CPU-located tensors are garbage-collected, which is why the loop above carries no dispose bookkeeping. An `InferenceSession` holds its WASM heap allocation until you `await session.release()`. A tensor whose data sits on the GPU is freed by `tensor.dispose()`. So a dashboard that opens a session per model version and releases none leaks the same way lesson 4's pipeline did.

The bundle row counts shipped JavaScript only, and on both sides the binary it leaves out is the bigger half. TF.js is 1.47MB minified and 368KB gzipped (`dist/tf.min.js`, tfjs 4.22.0), and that build does not include the WASM backend: `@tensorflow/tfjs-backend-wasm` adds 150KB / 35KB of JavaScript and fetches its `tfjs-backend-wasm-simd.wasm` binary, 425KB / 136KB, on first use. ORT Web is 368KB / 98KB (`dist/ort.min.js`, onnxruntime-web 1.29.0) and fetches `ort-wasm-simd-threaded.jsep.wasm`, 27.8MB / 6.6MB. Its wasm-only build, `dist/ort.wasm.min.js` at 50KB / 16KB, fetches the 14.0MB / 3.6MB `ort-wasm-simd-threaded.wasm` instead.

Those binaries are the cold-start row. TF.js fetches and compiles about 2MB of runtime, then the model, then runs one call; ORT Web fetches and compiles tens of megabytes of WASM before the model loads. How much longer that takes is a property of the link, so time it on the network you ship to.

The two runtimes sit two tenths of a millisecond apart. Switching backends moved the same model by 1.5ms. So the backend is the decision here, and 673 parameters settles it: WASM, on all six bridge consoles.

A bigger workload answers it the other way. The arithmetic grows with the model; the input upload, the shader dispatch and the readback do not. What flips the ordering is how much work the GPU has queued per readback, and that is a question about batch size and the length of the op chain as much as about parameter count: lesson 2 read one result back per 100 matmuls, while the loop above pays a readback on every call. Where the crossover sits depends on all of that and on the machine, which is why the workload you benchmark has to be the workload you ship.

For a model nobody has benchmarked yet, Nazari's standing rule is a million multiply-adds per call. For a dense stack that is roughly its parameter count; for a convolutional one it is far more, because each filter runs at every position. Below the line, ship WASM. At or above it, benchmark the GPU before ruling it out. The two workloads this course has measured sit on either side of it: DEEP SCAN's 673 parameters are about six hundred multiply-adds, and they cost 1.5ms more per call on WebGL than on WASM; lesson 2's 256x256 matmul is 16,777,216 multiply-adds per call, and it ran six times faster there. The line is where to start on hardware you have no numbers for, not a property of either backend.
