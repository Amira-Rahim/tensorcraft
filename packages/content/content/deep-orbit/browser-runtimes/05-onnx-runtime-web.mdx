ONNX stands for Open Neural Network Exchange. It stores a graph of operations, their connections and the model's weights. An **opset** version specifies the operation definitions the graph uses. An **execution provider** is the implementation that runs those operations on a CPU, GPU or another device.

Compatibility depends on all three: the graph, the runtime version and the provider. An unsupported operation can prevent loading or execution. Options include using a supported provider, changing the export, decomposing an operation or supplying a supported custom implementation. An older opset is useful only if the exported graph still represents the intended computation.

Write a comparison that waits for both runtimes' outputs. The supplied
simulation checks that you prepare inputs, time completed predictions, and
release resources correctly. The downloadable lab runs the model in real browsers.

## One input and two completed outputs

The coding task gives `compareRuntimes(model, modelPath, signal)` an already
loaded TFJS model and three input values. Build both inputs from that same
`signal`, keeping their order. For example, `[0.5, 0.3, 0.7]` becomes one
float32 row with shape `[1, 3]` in either runtime. The values are a practice
input, with no supplied ground-truth label.

| Part of the call | TensorFlow.js | ONNX Runtime |
| --- | --- | --- |
| Input | One `[1, 3]` float32 tensor | One `[1, 3]` float32 tensor with the same values |
| Inference | `model.predict(batch)` | `await session.run({ input: feed })` for this export |
| Completed value | `await prediction.data()`, then read its first score | Read the first score from `results.output.data` after `run()` resolves |
| Owned cleanup | Dispose input and prediction, keep the caller's model | Release the session, including when inference fails |

Use the actual returned scores for `outputsAgree`. The rule is
`Math.abs(tfjsScore - onnxScore) <= 0.0001`. A difference exactly equal to
0.0001 passes. The activity supplies scores separately from its input arrays
so you can inspect that rule without running a model. For supplied scores
0.5 and 0.50005, the difference is about 0.00005 and the rule returns `true`.
Changing the second score to 0.5002 makes it `false`.

Agreement is evidence about this computation on this input. Different inputs
cannot test conversion parity, even if their scores happen to match.
Accuracy asks a separate question: whether predictions agree with trusted
labels. This comparison has no such labels.

The TFJS path waits for readback inside its timer:

<CodeBlock language="typescript" title="completed-tfjs-call.ts">
{`// model is already loaded and belongs to the caller.
const reading = [0.5, 0.3, 0.7];
const batch = tf.tensor2d([reading], [1, 3], 'float32');
let output: tf.Tensor | undefined;
let tfjsScore: number;
let tfjsMs: number;
try {
  const began = performance.now();
  output = model.predict(batch) as tf.Tensor;
  tfjsScore = (await output.data())[0];
  tfjsMs = performance.now() - began;
} finally {
  output?.dispose();
  batch.dispose();
}
console.log({ tfjsScore, tfjsMs });`}
</CodeBlock>

The input is ready before timing starts. `predict()` can return a tensor
while device work is still queued. Awaiting `data()` keeps that work and
readback inside the measured interval. The `finally` block releases owned
tensors on success or failure. The caller keeps its model for later inputs.

{`import * as ort from 'onnxruntime-web/wasm';

// Serve the runtime's matching WASM files beside your application.
ort.env.wasm.wasmPaths = '/ort-wasm/';
ort.env.wasm.numThreads = 1; // controlled single-thread comparison
const session = await ort.InferenceSession.create('/models/deep-scan.onnx', {
  executionProviders: ['wasm'],
});
try {
  console.log(session.inputNames, session.outputNames);
  // These names and shapes belong to this export. Inspect yours.
  const input = new ort.Tensor('float32', new Float32Array([0.5, 0.3, 0.7]), [1, 3]);
  let results;
  try {
    results = await session.run({ input });
    console.log(results.output.data[0]);
  } finally {
    input.dispose();
    if (results) Object.values(results).forEach(tensor => tensor.dispose());
  }
} finally {
  await session.release();
}`}
</CodeBlock>

The paths above are available when serving the runtime lab. For your own application, export and host the model and copy the WASM assets from the same installed runtime version. Session resources need explicit release. GPU tensors may also hold device resources after JavaScript loses its reference.

This export names its input `input` and its output `output`. A different
graph can use different names, shapes, types, or operations. Inspect that
contract before creating the feed. The coding task fixes the ONNX provider
to WASM. It supplies a simulated session, so no ONNX file downloads there.

## Workload and timing

A useful comparison states what it includes. For inference latency, load the model first, warm up the exact input shape, then time each call through output readback. Reading only the time for a GPU dispatch can miss the work still queued on the device.

The activity uses chosen costs: TFJS dispatch takes 2 illustrative ms and
readback adds 8. The ONNX path uses 3 plus 12, with a separate 40 for loading.
Stopping after dispatch hides unfinished work. Starting before session
loading adds startup work to the inference interval. Those changes explain
the timer's number. The invented costs cannot identify a faster runtime.

<CodeBlock language="typescript" title="measure-inference.ts">
{`async function measure(run: () => Promise<unknown>) {
  // run() must await output readback and release temporary tensors.
  for (let i = 0; i < 20; i++) await run();
  const samples: number[] = [];
  for (let i = 0; i < 200; i++) {
    const start = performance.now();
    await run();
    samples.push(performance.now() - start);
  }
  const sorted = [...samples].sort((a, b) => a - b);
  return {
    samples,
    medianMs: (sorted[99] + sorted[100]) / 2, // 200 samples
    p95Ms: sorted[Math.ceil(sorted.length * 0.95) - 1],
  };
}`}
</CodeBlock>

The **median** is the middle observed duration. **P95** is the duration at or below which 95% of these calls finished. Preserve the samples so someone can see variation and timer rounding. Repeat runs with the order reversed before treating a small difference as a useful advantage.

For a runtime comparison, start with the same backend family, thread count, weights, inputs and batch size. Different implementations can still do different work internally. Test output agreement first. A faster result from a different computation is not a runtime improvement.

For **cold start**, use a fresh browser context and time through the first usable prediction. List which parts you timed: library loading, WASM compilation, model download, and application startup. A warm browser cache is a separate experiment. `tf.memory()` counts TFJS tensors. It is not browser process memory or GPU memory usage.

## The runtime comparison lab

Download the [browser runtime lab](/assignments/browser-runtime-lab-v1.zip), unzip it and follow its README. From that folder, run:

The lab uses pinned TFJS and ONNX Runtime versions in Chromium. It checks 261 fixed inputs, runs 20 warmups and 200 measured calls per runtime, and records the environment. Those inputs check conversion parity. Classification accuracy requires ground-truth labels, which this test set lacks. The lab also tests real IndexedDB persistence and missing model files. Converter verification needs the separate CLI setup in the instructions.

Treat laptop results as a starting point. Repeat on the supported devices and browser builds with the model you intend to ship. Neither 673 parameters nor a million-parameter cutoff decides whether WASM beats a GPU. Input shape, operation support, batch size, readbacks and device implementation all matter.

| Question | What to check |
|---|---|
| Can this runtime execute the model? | Load the actual export on the intended provider and compare outputs |
| Does it meet the latency budget? | Warm latency distribution and first usable prediction on target hardware |
| What will users download? | The selected JS build, WASM files, model and tokenizer, with actual compression |
| Will the page fit in memory? | Whole-application measurements, including initialization and simultaneous models |
| Is a conversion worth maintaining? | Supported operations, numerical differences and the cost of keeping exports current |

The [ONNX Runtime performance guide](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html) explains why workload and provider matter. The [session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html) document thread count and matching WASM paths.
