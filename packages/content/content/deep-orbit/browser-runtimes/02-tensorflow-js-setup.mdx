## A preference request and a runtime report

The dashboard's startup check has two jobs: let the runtime finish starting, then report its actual backend and version. A **preference** asks for a backend. The runtime's response determines whether that request worked.

The Challenge supplies a controlled cold runtime. Its backend names and probe version change on each run. That makes the sequence inspectable without depending on this browser's GPU. The test deliberately keeps `getBackend()` unavailable until `ready()` resolves. Its output is a simulated startup report. A real installation reports its own available backend and package version.

| Startup case | Preference request | Required next step | Successful report |
| --- | --- | --- | --- |
| No preferred name | Skip `setBackend()` | Await `ready()` | Read the runtime's selected backend and version |
| Registered backend starts | `setBackend(name)` resolves `true` | Await `ready()` | Read the accepted backend from the runtime |
| Registered backend cannot start | The request resolves `false` | Await `ready()` so an available backend can start | Read that available backend from the runtime |
| Unregistered name | The request rejects with an error | Catch the request error, then await `ready()` | Read the backend the runtime selected |
| No backend can start | A preference may refuse | Let the `ready()` error reach the caller | Return no invented successful report |

In the activity, choose a scenario and move through the startup points. The fixed names are illustrative test inputs. Notice that the requested name and the reported backend can differ. The version must come from the same ready runtime.

## Installation and the awaited sequence

<BridgeCallout bridge={frontmatter.concept.bridge} />

The course pins TensorFlow.js `4.22.0`. A matching local installation uses `npm install @tensorflow/tfjs@4.22.0`. The editor already supplies the package, so its Challenge needs no install command.

This runnable example requests the registered CPU backend. It records whether the request worked, awaits readiness outside the request's `try` block, and reads the runtime metadata. The CPU choice makes this example usable without a GPU. Measure your workload before choosing a deployment backend.

<CodeBlock language="typescript" title="setup.ts">
{`import * as tf from '@tensorflow/tfjs';

const preferred = 'cpu'; // A supplied preference for this example.
let preferenceStatus = 'not requested';
if (preferred) {
  try {
    const accepted = await tf.setBackend(preferred);
    preferenceStatus = accepted ? 'accepted' : 'refused';
  } catch (error) {
    preferenceStatus = 'request rejected';
  }
}

// Keep this outside the request catch. A total startup failure must reject.
await tf.ready();
const activeBackend = tf.getBackend();
const activeVersion = tf.version.tfjs;
console.log({ preferenceStatus, backend: activeBackend, version: activeVersion });
// With this real CPU example: accepted, cpu, and the installed version.`}
</CodeBlock>

Your `initTF(preferred?)` receives its preference from the caller. If the caller omits it, make no `setBackend()` request. After readiness, return an object with the exact fields `backend` and `version`. Read those values from `tf.getBackend()` and `tf.version.tfjs`. A name copied from the preference can be wrong after refusal. A hardcoded version cannot describe the generated test runtime.

Catch only the preference-request error. An error from `ready()` means startup failed, and the caller needs it to show a failure state. A broad catch around the whole function would hide that failure. These checks establish startup behavior. They do not benchmark a model or prove a device meets the dashboard's budget.

## Backend choices and measurements

| Backend | Where supported operations run | Setup to verify |
| --- | --- | --- |
| `webgl` | GPU shaders | Backend registration, WebGL access, and operation support |
| `webgpu` | GPU compute | Separate backend package, browser support, and an available adapter |
| `wasm` | Compiled WebAssembly kernels on the CPU | Backend package and matching WASM binary paths |
| `cpu` | JavaScript on the CPU | Registered CPU backend and measured workload budget |

Importing an API does not establish GPU access. Backends can differ in operation support, precision, startup cost, memory use, and speed. A small model can favor a CPU path after transfer overhead. Benchmark the actual workload on the devices you support.

The story's `0.5`, `3.0`, and `110.0 ms` figures describe a fictional matrix multiplication at the story console. They supply no timing target for the Challenge or your device. A useful benchmark records the selected backend, installed version, input shape, warmup, individual samples, and completed output readback.

### Registration and an explicit fallback order

This separate application example registers additional packages and supplies matching WASM files. Its fallback ladder is an example order. Measure supported devices before choosing one. `navigator.gpu` signals an API's presence. Requesting a backend still needs to succeed.

<CodeBlock language="typescript" title="backends.ts">
{`import * as tf from '@tensorflow/tfjs';

// WebGL runs supported tensor operations using GPU shaders.
import '@tensorflow/tfjs-backend-webgl';

// WASM executes compiled kernels on the CPU. A small workload can favor it.
import { setWasmPaths } from '@tensorflow/tfjs-backend-wasm';
setWasmPaths('/wasm/'); // copy binaries from this installed package version

// The pure JavaScript CPU backend is a useful fallback. Measure whether
// it meets your application's budget. Production use is not forbidden.

// WebGPU provides a GPU compute API. Availability is not a speed result.
// Install this separate package if you want this branch of the example.
import '@tensorflow/tfjs-backend-webgpu';

// This is an example fallback order. Choose yours after measuring,
// and try the next backend if the requested one fails. A name that was never
// registered makes tf.setBackend throw. A registered backend that cannot
// START (a lost GPU context, a blocked WebGPU adapter) makes it resolve
// false without throwing. Ignore the boolean and the page runs
// somewhere else while your code believes it is on webgpu.
const ladder = navigator.gpu
  ? ['webgpu', 'webgl', 'wasm', 'cpu']
  : ['webgl', 'wasm', 'cpu'];
for (const name of ladder) {
  try {
    if (await tf.setBackend(name)) break;
  } catch {
    // not registered on this page: try the next backend
  }
}
await tf.ready();

// Or let TF.js choose. Its rule: the registered backend with the highest
// priority wins, webgpu (3) first, then webgl and wasm, which are BOTH
// registered at priority 2, so that tie goes to whichever package the page
// imported first, then cpu (1). The tie is why the fallback order above is worth
// writing: a page that imports the wasm backend before the webgl one gets
// wasm on a machine with a perfectly good GPU, and nothing warns you.`}
</CodeBlock>

### Completed matrix-multiplication samples

This function measures one completed matrix multiplication per call. It warms the same shape and readback path before collecting samples. It does not measure cold application startup or the latency of a whole model. Keep the samples and record the browser and device alongside them.

<CodeBlock language="typescript" title="benchmark.ts">
{`import * as tf from '@tensorflow/tfjs';

async function benchmarkBackend(backendName: string) {
  if (!await tf.setBackend(backendName)) throw new Error('Backend did not start');
  await tf.ready();
  const a = tf.randomNormal([256, 256], 0, 1, 'float32', 7);
  const b = tf.randomNormal([256, 256], 0, 1, 'float32', 11);
  const run = async () => {
    const result = tf.matMul(a, b);
    try { await result.data(); } finally { result.dispose(); }
  };
  try {
    // Warm the SAME shape and readback path that the timed loop will use.
    for (let i = 0; i < 20; i++) await run();
    const times: number[] = [];
    for (let i = 0; i < 100; i++) {
      const start = performance.now();
      await run();
      times.push(performance.now() - start);
    }
    return { backend: tf.getBackend(), times };
  } finally {
    a.dispose();
    b.dispose();
  }
}`}
</CodeBlock>

The independent runtime lab runs the real package in supported backends and records its own observations. Its report identifies headless or visible-browser mode and the renderer. A software renderer is not a physical GPU measurement.
