<Dialogue speaker="Chief Nazari" expression="skeptical">
And what happens to the tensors you create every second? If you don't dispose them, you'll leak memory until the tab crashes. This is not a lab experiment anymore.
</Dialogue>

One reading per second sounds gentle until you do the multiplication Nazari already did in the margin: 86,400 predictions a day, each allocating fresh tensors on the GPU. The loop itself is the event-handler pattern (event fires, handler processes, UI updates) with one addition no garbage collector will save you from: **memory management**. Leak two tensors per reading and the count climbs by 7,200 an hour. The bytes barely move: the escaped pair at this model's size is a [1, 3] input and a [1, 1] output, 16 bytes together, so a gigabyte of leaked tensor data is more than a year away at one reading a second. What you run out of first is the count. The incident exercise later in this lesson puts the dashboard's budget at 10,000 tensors, which is about an hour and a half of this leak.

## The Real-Time Inference Loop

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="inference-pipeline.ts">
{`import * as tf from '@tensorflow/tfjs';

// The model expects normalized 3-feature input: [amplitude, frequency, phase]
// Training used min-max to [0, 1]. Module 1's rule sends open-ended
// streams to z-score; amplitude and frequency are bounded by hardware,
// not by history: the hull sensors saturate at 2048 counts, and
// "frequency" is a zero-crossing count over the 64-sample extraction
// window, so 63 sign flips is its physical ceiling. That window is 64
// SAMPLES, a quarter second of one channel at 256 Hz. Module 1's
// data-loading lesson keeps the two words apart: a CAPTURE is the
// 33-second archive block, 256 Hz across 64 CHANNELS, and the
// extraction window is the quarter second these three features come
// from. Two different 64s, and only the sample count sets this ceiling.
const FEATURE_RANGES = {
  amplitude: { min: 0, max: 2048 },
  frequency: { min: 0, max: 63 },
  phase: { min: -Math.PI, max: Math.PI },
};

function normalize(value: number, min: number, max: number): number {
  return (value - min) / (max - min);
}

// Preprocess raw signal → model input
function preprocess(raw: { amplitude: number; frequency: number; phase: number }): number[] {
  return [
    normalize(raw.amplitude, FEATURE_RANGES.amplitude.min, FEATURE_RANGES.amplitude.max),
    normalize(raw.frequency, FEATURE_RANGES.frequency.min, FEATURE_RANGES.frequency.max),
    normalize(raw.phase, FEATURE_RANGES.phase.min, FEATURE_RANGES.phase.max),
  ];
}

// Run inference: the core predict call
function classify(model: tf.LayersModel, rawSignal: { amplitude: number; frequency: number; phase: number }) {
  // tf.tidy() automatically disposes all intermediate tensors
  // Like a try/finally that cleans up resources; no manual dispose() needed
  return tf.tidy(() => {
    const normalized = preprocess(rawSignal);
    const input = tf.tensor2d([normalized]);        // shape: [1, 3]
    const output = model.predict(input) as tf.Tensor;
    const p = output.dataSync()[0];                  // sigmoid: P(anomaly)

    // Confidence is confidence IN THE VERDICT, not the raw sigmoid:
    // p = 0.12 is not "12% confident", it is "noise, 88% confident".
    return {
      class: p > 0.5 ? 'anomaly' : 'noise',
      confidence: Math.round((p > 0.5 ? p : 1 - p) * 1000) / 1000,
    };
  });
}`}
</CodeBlock>

Min-max fixes the range at both ends. 2048 counts is the ceiling FEATURE_RANGES declares and also the reading where the hull sensors stop responding, so a normalized amplitude reaches 1.00 and never passes it. Frequency has the same ceiling for a different reason: 63 sign flips is the most a 64-sample window can hold. A normalized feature above 1.00 further down the pipeline is a units bug, not a strong reading.

Phase is bounded too, but it is circular: it wraps at pi, so -pi and +pi are the same angle and min-max tears that seam, sending near-identical readings to 0 and 1. The clean encoding is two features, `sin(phase)` and `cos(phase)`. This model was trained on the 3-input min-max contract, so inference has to match training, seam included.

## Memory Management with tf.tidy()

Module 1 told you `tf.tidy()` is the same contract as a `useEffect` cleanup, and that still holds: you acquired a resource the runtime will not reclaim for you. What has no JS parallel is the *stakes*. A leaked event listener costs you a closure; a leaked GPU tensor is invisible to the garbage collector and stays allocated until the tab dies, and there is no devtools panel that will point at it.

<CodeBlock language="typescript" title="memory-management.ts">
{`import * as tf from '@tensorflow/tfjs';

// BAD: leaks memory every call; tensors accumulate on the GPU
function leakyPredict(model: tf.LayersModel, data: number[]) {
  const input = tf.tensor2d([data]);           // allocated on GPU
  const output = model.predict(input);          // allocated on GPU
  return (output as tf.Tensor).dataSync()[0];   // input and output NEVER freed
}

// GOOD: tf.tidy() cleans up all tensors created inside it
function cleanPredict(model: tf.LayersModel, data: number[]) {
  return tf.tidy(() => {
    const input = tf.tensor2d([data]);
    const output = model.predict(input) as tf.Tensor;
    return output.dataSync()[0];  // scalar return value (not a tensor) passes through
  });
  // input and output tensors automatically disposed here
}

// Monitor memory usage, like checking DevTools memory tab
console.log(tf.memory());
// { numTensors: 47, numDataBuffers: 47, numBytes: 12800, unreliable: false }`}
</CodeBlock>

If that `numTensors` figure climbs while the dashboard idles, something escaped a `tidy()`.

One more dial before the wiring: `dataSync()` blocks the JavaScript thread while the GPU read completes. At this model's scale that stall is invisible, which is why the code above uses it freely. On bigger outputs, or inside a loop that also has UI to paint, prefer `await tensor.data()`: it returns a Promise and yields to the event loop while the transfer happens. The catch is that `tf.tidy()` cannot wrap async code, so the async pattern splits in two: do the tensor math inside `tidy()` and return the tensor, then `await tensor.data()` outside and `dispose()` it yourself.

## Wiring It into the Dashboard

<CodeBlock language="typescript" title="dashboard-integration.ts">
{`import * as tf from '@tensorflow/tfjs';

interface SignalReading {
  timestamp: number;
  amplitude: number;
  frequency: number;
  phase: number;
}

interface Classification {
  class: 'anomaly' | 'noise';
  confidence: number;
  latencyMs: number;
}

// Real-time pipeline: process each signal as it arrives
function createInferencePipeline(model: tf.LayersModel) {
  return function processSignal(reading: SignalReading): Classification {
    const start = performance.now();

    const result = tf.tidy(() => {
      const normalized = preprocess(reading);
      const input = tf.tensor2d([normalized]);
      const output = model.predict(input) as tf.Tensor;
      return output.dataSync()[0];   // raw sigmoid: P(anomaly)
    });

    return {
      class: result > 0.5 ? 'anomaly' : 'noise',
      // Same rule as classify() above: confidence belongs to the verdict.
      // A raw sigmoid of 0.12 means "noise" at 0.88 confidence.
      confidence: result > 0.5 ? result : 1 - result,
      latencyMs: performance.now() - start,
    };
  };
}

// Usage: exactly like setting up an event listener
const pipeline = createInferencePipeline(model);

// Process each signal reading as it arrives (1Hz)
signalFeed.addEventListener('reading', (event: CustomEvent<SignalReading>) => {
  const classification = pipeline(event.detail);
  updateDashboard(classification);
  // Typical: { class: 'noise', confidence: 0.88, latencyMs: 3.4 }
  // (raw sigmoid 0.12: an anomaly probability, inverted into noise confidence)
});`}
</CodeBlock>

That 3.4 ms is the whole handler, not the model. `performance.now()` brackets the normalization, the tensor allocation, the `predict` call and the `dataSync()` readback together. Most of it is the predict call: lesson 5 benchmarks this model at 2.4 ms on WebGL, which is the backend five of the six bridge consoles reported in lesson 2. The rest is the wiring around it.
