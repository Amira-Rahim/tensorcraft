## The Real-Time Inference Loop

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="inference-pipeline.ts">
{`import * as tf from '@tensorflow/tfjs';

// The model expects normalized 3-feature input: [amplitude, frequency, phase]
// This training contract uses fixed physical min-max bounds. Z-score
// is another option, not a general rule for all open-ended streams.
// Here amplitude and frequency are bounded by the declared hardware: the hull sensors saturate at 2048 counts, and
// "frequency" is a zero-crossing count over the 64-sample extraction
// window, so 63 sign flips is its physical ceiling. That window is 64
// SAMPLES, a quarter second of one channel at 256 Hz. Module 1's
// data-loading lesson keeps the two words apart: a CAPTURE is the
// 33-second archive block, 256 Hz across 64 CHANNELS, and the
// extraction window is the quarter second these three features come
// from. Two different 64s, and only the sample count sets this ceiling.
const FEATURE_RANGES = {
  amplitude: { min: 0, max: 2048 },
  frequency: { min: 0, max: 63 },
  phase: { min: -Math.PI, max: Math.PI },
};

function normalize(value: number, min: number, max: number): number {
  return (value - min) / (max - min);
}

// Preprocess raw signal → model input
function preprocess(raw: { amplitude: number; frequency: number; phase: number }): number[] {
  return [
    normalize(raw.amplitude, FEATURE_RANGES.amplitude.min, FEATURE_RANGES.amplitude.max),
    normalize(raw.frequency, FEATURE_RANGES.frequency.min, FEATURE_RANGES.frequency.max),
    normalize(raw.phase, FEATURE_RANGES.phase.min, FEATURE_RANGES.phase.max),
  ];
}

// This callback creates temporary tensors and returns plain numbers.
// It creates no variables and calls no tf.keep(), so tidy disposes all
// tensors created here. The model owns its existing weights.
// The return type pins the verdict to its two allowed words.
function classify(
  model: tf.LayersModel,
  rawSignal: { amplitude: number; frequency: number; phase: number },
): { class: 'anomaly' | 'noise'; confidence: number } {
  return tf.tidy(() => {
    const row = tf.tensor2d([preprocess(rawSignal)]);   // shape: [1, 3]
    const verdict = model.predict(row) as tf.Tensor;    // shape: [1, 1]
    const p = verdict.dataSync()[0];                    // sigmoid score, not a validated probability

    // The API calls this confidence; it is the chosen class's score.
    // Calibration must be measured before interpreting it as reliability.
    return {
      class: p > 0.5 ? 'anomaly' : 'noise',
      confidence: p > 0.5 ? p : 1 - p,
    };
  });
}`}
</CodeBlock>

The hull sensors stop increasing at 2048 counts, the maximum in FEATURE_RANGES. Scaling that amplitude gives 1.00. The feature named frequency counts sign flips: 64 samples can contain at most 63, so that is its declared maximum.

Under these sensor limits, a scaled value above 1.00 needs investigation. Check the units, preprocessing and whether the input is valid. This is a limit of these sensors, not of min-max scaling itself. In general, readings outside a fitted range produce scaled values outside [0, 1].

Phase wraps around: -pi and +pi describe the same angle. Min-max scaling sends them to opposite ends of [0, 1], making nearby angles look far apart. Representing phase with `sin(phase)` and `cos(phase)` avoids that boundary. That would change the inputs and require retraining. This model still expects its original three features, scaled exactly as they were during training.

## Memory Management with tf.tidy()

`tf.tidy()` manages synchronous tensor allocations. It disposes tensors created in its callback except returned tensors, variables and tensors explicitly retained with `tf.keep()`. Those survivors need an owner that disposes them later. JavaScript has similar ownership problems: an event listener can retain a large object graph until removed. Use `tf.memory()` to inspect tensors, alongside browser and backend diagnostics.

<CodeBlock language="typescript" title="memory-management.ts">
{`import * as tf from '@tensorflow/tfjs';

// BAD: leaks memory every call; tensors remain registered with the active backend
function leakyPredict(model: tf.LayersModel, data: number[]) {
  const input = tf.tensor2d([data]);           // caller-owned tensor
  const output = model.predict(input);          // caller-owned tensor
  return (output as tf.Tensor).dataSync()[0];   // input and output NEVER freed
}

// GOOD: tidy cleans up the temporary input and prediction tensors here
function cleanPredict(model: tf.LayersModel, data: number[]) {
  return tf.tidy(() => {
    const input = tf.tensor2d([data]);
    const output = model.predict(input) as tf.Tensor;
    return output.dataSync()[0];  // scalar return value (not a tensor) passes through
  });
  // input and output tensors automatically disposed here
}

// Monitor memory usage, like checking DevTools memory tab
console.log(tf.memory());
// { numTensors: 47, numDataBuffers: 47, numBytes: 12800, unreliable: false }`}
</CodeBlock>

Sustained growth after warmup is a reason to investigate. Lazy initialization or an intentional cache can also increase the count. Track bytes and backend memory as well; a flat tensor count alone does not rule out a leak.

`dataSync()` blocks the JavaScript thread while it waits for the result. Even a small output can wait for earlier GPU work, so measure its effect on the dashboard. The challenge uses this synchronous form inside `tf.tidy()`, which releases all temporary tensors before `classify()` returns.

For asynchronous reading, use `await tensor.data()`. This allows an asynchronous result read, but does not move all computation off the main thread or guarantee a screen update during the wait. `tf.tidy()` cannot run an async callback. Instead, return the prediction tensor from a synchronous tidy callback, await its data outside, then dispose that tensor in a finally block.

<CodeBlock language="typescript" title="classify-async.ts">
{`// The async variant: same verdict, one tensor deliberately kept alive
// across the await, then freed by hand. It earns its extra lines on
// outputs big enough for the transfer to show, or in a loop that also
// has UI to paint.
async function classifyAsync(
  model: tf.LayersModel,
  rawSignal: { amplitude: number; frequency: number; phase: number },
): Promise<{ class: 'anomaly' | 'noise'; confidence: number }> {
  const output = tf.tidy(() => {
    const row = tf.tensor2d([preprocess(rawSignal)]);
    return model.predict(row) as tf.Tensor;   // row freed, output kept
  });
  try {
    const p = (await output.data())[0];
    return { class: p > 0.5 ? 'anomaly' : 'noise', confidence: p > 0.5 ? p : 1 - p };
  } finally {
    output.dispose(); // also runs if readback fails
  }
}`}
</CodeBlock>

Both handlers release their temporary input and output tensors. The loaded model keeps its weights until its owner disposes it during teardown.

## Wiring It into the Dashboard

<CodeBlock language="typescript" title="dashboard-integration.ts">
{`import * as tf from '@tensorflow/tfjs';

interface SignalReading {
  timestamp: number;
  amplitude: number;
  frequency: number;
  phase: number;
}

interface Classification {
  class: 'anomaly' | 'noise';
  confidence: number;
  latencyMs: number;
}

// Real-time pipeline: process each signal as it arrives. One classify()
// does the work; the pipeline only adds the clock.
function createInferencePipeline(model: tf.LayersModel) {
  return function processSignal(reading: SignalReading): Classification {
    const start = performance.now();
    const verdict = classify(model, reading);
    return { ...verdict, latencyMs: performance.now() - start };
  };
}

// Integration sketch: your app supplies model, signalFeed and updateDashboard.
// Retain and remove the handler during teardown.
const pipeline = createInferencePipeline(model);

// Process each signal reading as it arrives (1Hz)
const onReading = (event: CustomEvent<SignalReading>) => {
  const classification = pipeline(event.detail);
  updateDashboard(classification);
  // Illustrative shape: { class: 'noise', confidence: 0.88, latencyMs: 3.4 }
  // confidence is a class score, not measured probability calibration.
};
signalFeed.addEventListener('reading', onReading);
// On teardown: signalFeed.removeEventListener('reading', onReading);`}
</CodeBlock>

The handler timer includes preprocessing, tensor allocation, prediction and readback. Compare it with the runtime lab's isolated measurement, but do not subtract results from different runs and treat the difference as a measured overhead. Dashboard rendering, warmup, backend scheduling and device load can all change timing. The 3.4ms in the story is fictional.

The return field is named `confidence` for this exercise's API. It contains the selected class score, p or 1-p. A sigmoid range alone does not show that a score of 0.88 means 88% of comparable predictions are correct. That requires calibration evidence on representative held-out data.
