The bridge crew needs real-time classification in their dashboard. I'm not routing signal data through a server on every reading. The model runs in the browser or it does not ship.

<Dialogue speaker="Ensign Demir">

Moving predictions from a server to the user’s device changes the network dependency, download size, and local compute cost. The bridge dashboard needs to keep classifying readings when the compute-bay link fails.

TensorFlow.js is not browser-only. `@tensorflow/tfjs-node` binds the same API to the native TensorFlow build and runs on a server, with performance depending on its hardware, model and backend. This module goes to the browser because that is where DEEP SCAN has to land: the bridge dashboard, on the consoles the crew already reads.

You will choose where a model should run using the console’s privacy, offline, and loading requirements.

## Where Inference Runs: Server or Client

<BridgeCallout bridge={frontmatter.concept.bridge} />

Inference means using a trained model to make a prediction. Here is how that work differs on a server and in a browser:

<CodeBlock language="typescript" title="inference-comparison.ts">
{`// Integration sketch: an application supplies /api/classify and model.
// SERVER-SIDE INFERENCE, like SSR
// Data leaves the device, hits a server, waits for response
// (the server can be Node running this same model via @tensorflow/tfjs-node)
async function serverInference(signalData: number[]) {
  const response = await fetch('/api/classify', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ signal: signalData }),
  });
  if (!response.ok) throw new Error('Classification request failed');
  return response.json(); // application response, for example { class: 'anomaly', score: 0.94 }
}

// CLIENT-SIDE INFERENCE, like CSR
// This prediction runs locally. Audit other uploads and telemetry separately.
async function clientInference(signalData: number[]) {
  const output = tf.tidy(() => model.predict(tf.tensor2d([signalData])) as tf.Tensor);
  try {
    const p = (await output.data())[0];
    return { class: p > 0.5 ? 'anomaly' : 'noise', score: p };
  } finally {
    output.dispose();
  }
}`}
</CodeBlock>

**When to choose client-side inference:**

| Factor | Server | Browser |
|--------|-------------|---------------|
| **Latency** | Network plus server queue/compute | Local preparation, compute and readback |
| **Privacy** | Inputs reach the service | Inference can stay local; audit uploads and telemetry too |
| **Offline** | Usually needs a connection | Needs cached app, runtime and model assets |
| **Model size** | Limited by server resources and cost | Limited by download, memory and device compatibility |
| **Compute** | Hardware chosen by the service | Hardware varies by learner/device |
| **Cold start** | May need process/model startup | May need downloads, initialization and kernel compilation |

Nazari is right, though not because one round-trip misses the budget: a 180-millisecond hop to the ship's compute bay fits inside a second easily. Her objection is that the dashboard would then depend on that link staying up, reading after reading, for every hour of every watch.

## The Cost of Client-Side ML

Running the model on the user’s device uses that device’s memory and processing power. It also adds files to download:

<CodeBlock language="typescript" title="browser-constraints.ts">
{`// Budget sketch: parameterCount and input are supplied by your app.
// Browser memory limits vary by device, backend and browser.
// A model with 10M parameters at float32 = 40MB just for weights:
// 10,000,000 x 4 bytes / 1e6 = 40 MB.
// Dividing by 1024*1024 instead gives 38.1 MiB, a different unit.
const modelSizeMB = (parameterCount * 4) / 1e6;
console.log(\`Model size: \${modelSizeMB}MB\`);

// Cold start: model must be downloaded and initialized
// This is like the "time to interactive" metric in the browser
const t0 = performance.now();
const model = await tf.loadLayersModel('/models/deep-scan/model.json');
const coldStartMs = performance.now() - t0;
console.log(\`Cold start: \${coldStartMs}ms\`);  // measured load time; cache state matters

// Inference budget: 60fps = 16ms per frame
// Signal processing at 1Hz = 1000ms budget (comfortable)
// 44.1kHz audio has 0.023ms between samples, but processing uses blocks.
// A 128-sample block spans about 2.9ms; model cadence and buffering
// determine the actual inference deadline.
const inferenceStart = performance.now();
const output = model.predict(input) as tf.Tensor;
await output.data();  // GPU kernels are queued; read a result back or you time the queue
const inferenceMs = performance.now() - inferenceStart;
output.dispose();
console.log(\`Inference: \${inferenceMs}ms\`);  // record the device, backend, warmup and sample distribution`}
</CodeBlock>

DEEP SCAN classifies one reading per second, leaving roughly 1000ms between predictions. Test the complete handler on supported devices while the dashboard is busy. Having that much time available does not tell you how long the work actually takes.
