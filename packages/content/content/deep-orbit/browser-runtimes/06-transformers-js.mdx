## Browser ML runtimes

Transformers.js adds task-specific preprocessing and output handling around pretrained models. Its browser inference uses ONNX Runtime. The tools overlap. Choose based on the model and application you need.

<BridgeCallout bridge={frontmatter.concept.bridge} />

| Tool | Useful when | Check before shipping |
|---|---|---|
| TensorFlow.js | You need its training APIs or a supported TFJS model | Backend support, model behavior and size |
| ONNX Runtime Web | You have a compatible ONNX graph and can supply preprocessing | Operators, input/output contract and numerical parity |
| Transformers.js | A supported pipeline fits your NLP, vision or audio task | Model license, domain performance, asset sizes and latency |

A custom task does not automatically require training from scratch. Check whether an existing model, adaptation or an ordinary rule meets the need. A convenient pipeline API does not establish that the model is suitable.

## Classification of the crew’s reports

The Challenge asks for `classifyReports(reports, pipelineFactory)`. Its
factory stands in for the real `pipeline()` loader. It returns a classifier
when you name the task. `sentiment-analysis` fits the required text-to-label
and score contract. `text-classification` is its accepted alias. A supported
task such as summarization returns a different kind of output.

There are two separate awaited calls. First, load one classifier from the
factory. Then pass the whole `reports` array to that classifier once. The
batch result preserves report order: prediction at index `i` belongs to
report at index `i`. For an empty array, return `[]` before calling the
factory. Loading has a cost even when model assets are cached.

After handling the empty case, these calls produce the positional predictions:

<CodeBlock language="typescript" title="batch-report-call.ts">
{`const task = 'sentiment-analysis';
const classifier = await pipelineFactory(task);
const predictions = await classifier(reports);`}
</CodeBlock>

The activity reuses this three-report probe from the coding task:

| Original index | Supplied report | Supplied prediction |
| --- | --- | --- |
| 0 | coupling nominal | POS, 0.50 |
| 1 | coolant loop warning | NEG, 0.99 |
| 2 | watch handover clean | POS, 0.70 |

Follow report 1. Its prediction is `NEG` with score `0.99`, so its complete
row goes first when sorting by descending score. This is the highest score
regardless of its label. Sorting predictions first and then attaching report
0 to prediction 0 would put that `NEG, 0.99` beside “coupling nominal”. The
numbers would be sorted while the report pairing was wrong.

This runnable reference starts after classification, with supplied results:

<CodeBlock language="javascript" title="report-pairing.js">
{`const reports = ['coupling nominal', 'coolant loop warning', 'watch handover clean'];
const predictions = [
  { label: 'POS', score: 0.5 },
  { label: 'NEG', score: 0.99 },
  { label: 'POS', score: 0.7 },
];
const queue = reports.map((text, index) => ({ text, ...predictions[index] }));
queue.sort((left, right) => right.score - left.score);
console.table(queue);`}
</CodeBlock>

The returned order is coolant warning, clean handover, then coupling nominal.
Each report keeps its original label and score. The supplied numbers teach
pairing and sorting. They are not measured model accuracy or report urgency.
Change the activity's loading strategy to compare one batch call with loading
once per report, then try the empty batch.

## The separate real-model call

The following block uses the real library and downloads a pinned model when
its assets are missing. Its four reports are a separate demonstration. Keep
its measured predictions distinct from the three supplied fixture scores.

<CodeBlock language="typescript" title="sentiment-pipeline.ts">
{`// The package moved from '@xenova/transformers' to the official
// '@huggingface/transformers' at v3. Old tutorials cite the former.
import { pipeline } from '@huggingface/transformers';

// Pin model, revision, dtype and device when reproducing results.
const classifier = await pipeline(
  'sentiment-analysis',
  'Xenova/distilbert-base-uncased-finetuned-sst-2-english',
  {
    revision: '0b6928efcb76139cae2c6881d49cda67fe119f42',
    dtype: 'q8',
    device: 'wasm',
  },
);
try {
  const reports = [
    'Starboard array cleared diagnostics ahead of schedule.',
    'Sensor array is functioning within tolerance.',
    'Catastrophic failure on the port-side coupling.',
    'Signal classification: anomalous.',
  ];
  const predictions = await classifier(reports);
  const queue = reports.map((text, index) => ({ text, ...predictions[index] }));
  queue.sort((left, right) => right.score - left.score);
  console.table(queue);
} finally {
  await classifier.dispose();
}`}
</CodeBlock>

The first load may download model weights, tokenizer assets and the runtime. Browser Cache Storage can retain model assets, but quota, eviction and browser settings affect it. A cache hit still needs asset reads, initialization and inference. TFJS's `indexeddb://` model storage uses a different browser API.

The real lab runs this revision with both `q8` and `fp32`, records exact asset sizes and scores, and reloads the q8 pipeline with the network disabled after initialization. Run `node scripts/check-runtime-lab.mjs --pretrained`. Setup and measurement limits are in the [browser runtime lab README](/assignments/browser-runtime-lab-v1.zip). Do not expect scores from different dtypes or runtimes to match exactly.

This model uses ONNX, so TensorFlow.js tools such as `model.layers` and `tensorflowjs_converter` do not apply. Use tools that support the ONNX model. A transformer needs a compatible architecture and conversion path to run as a TFJS LayersModel. The crew trained DEEP SCAN in TensorFlow.js and keeps it there.

Aboard the Archimedes the download comes from the ship's mirrored model archive, synced at the last relay pass. The live Hub is eleven light-minutes of latency away on a good day. A local mirror changes where the assets come from. It does not remove cache eviction, versioning or cold-start work.

## Model suitability

The model authors fine-tuned this sentiment classifier on SST-2 movie-review sentences. Crew status reports are operational text. Its labels are POSITIVE and NEGATIVE. It has no neutral or “needs human attention” label. A high softmax score expresses a preference among those trained labels. Reliable use on crew reports requires evaluation and calibration on representative reports.

Label representative reports before inspecting the model's predictions. Compare mistakes and the current manual process. Keep an untouched evaluation set if you use earlier examples to choose prompts, models or thresholds. Twenty reports can reveal an obvious mismatch. They cannot establish a reliable rare-error rate.

Mirza is trying out this way of sorting reports. Test whether it helps her find reports needing attention. It is not a measure of crew morale, severity or urgency.

Download size can make browser inference impractical for a target connection. Measure the selected files and startup on that connection. Prefetching may reduce waiting later, but cannot guarantee a cold-start deadline when assets are missing or the network is unavailable. Transformers.js runs inference in the browser. Fine-tuning needs separate tooling and a compatible export.
