`scrollIntoView()` steers a user's viewport to the content that matters. Temporal attention scores every step and combines the values under those weights. A high weight does not skip computation on other steps. Lesson 1 read its query off the sequence. Here the scorer's learned weights play that part, the same query on every window, and each step is both its own key and its own value.

You will add position information to an attention scorer and use its weights to summarize a sequence.

## Temporal Attention Layer

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="temporal-attention.ts">
{`import * as tf from '@tensorflow/tfjs';

// The scoring function is MODULE STATE, created once. Its weights come
// from training the surrounding model: an encoder, this scorer and a
// prediction head, updated together under one loss. That update runs as
// a manual optimizer.minimize loop over this whole forward pass. It
// cannot go through model.compile and model.fit as written. Inside a
// compiled graph scorer.apply hands back a SymbolicTensor, which carries
// no tensor methods, so the next line stops with "TypeError:
// scores.squeeze is not a function". Reach for tf.softmax or tf.sum on
// that same value and you get the refusal one step later, worded as an
// argument error. Everything below is the forward pass, so the weights it
// reads out mean something only after that training has happened. A
// fresh layer inside the function would score every call with brand-new
// random weights and never learn at all.
const scorer = tf.layers.dense({ units: 1 });

// Temporal attention: score each time step's importance
function temporalAttention(
  sequence: tf.Tensor3D,  // [batch, timeSteps, features]
): { attended: tf.Tensor2D; weights: tf.Tensor2D } {
  return tf.tidy(() => {
    // Project each step to a scalar importance score
    const scores = scorer.apply(sequence) as tf.Tensor;
    const squeezed = scores.squeeze([2]) as tf.Tensor2D;  // [batch, timeSteps]

    // Softmax over time axis: which steps take the weight?
    const weights = tf.softmax(squeezed, 1);  // [batch, timeSteps]

    // Weighted sum: combine time steps by importance
    const expanded = weights.expandDims(2);  // [batch, timeSteps, 1]
    const weighted = tf.mul(sequence, expanded);
    const attended = tf.sum(weighted, 1) as tf.Tensor2D;  // [batch, features]

    return { attended, weights };
  });
}

// The weights tell the story:
// weights = [0.01, 0.01, ..., 0.12, 0.01, ..., 0.15, ...]
//                                ^                 ^
//                             step 4            step 78
// The model focuses on the initial spike and the frequency shift,
// 74 steps apart inside the 80-step window`}
</CodeBlock>

Three counts run through this lesson and two of them carry the same number, so pin all three before reading a heatmap. A step is one reading, and the dashboard's readings land one per second, so the first and last timestamps in 80 readings are 79 seconds apart. The spike and the frequency shift sit 74 steps apart because the interval measured in module 5 is 73.4 s: on a one-per-second grid the shift lands four tenths of a second past reading 77, so reading 78 is the first one that carries it. Module 6 measured the same 74-step dependency and then sized its window at 80 to hold it, enough room for both sampled events. The 64-sample capture in the next block is not a step count. It is 64 samples of one channel at 256 Hz, a quarter of a second, and that is the stretch a single reading's three features are measured over. The 64 channels from module 1 are a different 64 again: that count says how many sensors report, not how long anything lasts.

## Interpreting Attention Weights

<CodeBlock language="typescript" title="interpret-attention.ts">
{`// Attention weights have an explicit time axis that is convenient to plot
// You can show the crew exactly WHERE the model put its weight.
// Why it decided is a separate question the weights do not settle.

interface AttentionInsight {
  timeStep: number;
  weight: number;
  reading: number[];
}

function topAttentionSteps(
  weights: number[],
  readings: number[][],
  topK: number = 5,
): AttentionInsight[] {
  return weights
    .map((weight, i) => ({ timeStep: i, weight, reading: readings[i] }))
    .sort((a, b) => b.weight - a.weight)
    .slice(0, topK);
}

// Fictional mission readings, not output from the untrained layer above. Readings are raw
// sensor values, not normalized ones: amplitude in hull counts (0 to
// 2048), frequency as a zero-crossing count over the 64-sample capture
// (0 to 63), phase in radians.
// Step 78: weight=0.15, reading=[635, 40, 1.57]   ← frequency shift
// Step 4:  weight=0.12, reading=[1980, 37, 0.23]  ← amplitude spike
// Step 40: weight=0.09, reading=[1065, 37, 0.89]  ← mid-pattern
// A crossing count does not identify a frequency exactly: phase, offset,
// mixtures, noise and the finite window all matter. Use the FFT and raw
// waveform to investigate the apparent shift. Blanking a step can measure
// model sensitivity, but may create unrealistic inputs; it does not prove
// the physical cause or fully explain a prediction.
`}
</CodeBlock>

## Applied: Attention Over a Live Ring Buffer

The heatmaps above assume the model gets the whole window. On the bridge array it gets whatever the capture buffer kept, and storage is tight enough that the tempting move is the browser one: virtualize. Keep the steps around the predicted event, drop the rest, let a viewport stand in for the sequence.

Attention has a failure mode built exactly for that trick, and one truncated buffer is enough to see it:

<CodeBlock language="typescript" title="ring-buffer-attention.ts">
{`// One full capture cycle from the ring buffer: 80 steps, 3 features.
const full = bufferWindow();                       // [1, 80, 3]
const { attended, weights } = temporalAttention(full);
console.log(full.shape, weights.shape, attended.shape);
// [1, 80, 3] [1, 80] [1, 3]
console.log(tf.tidy(() => weights.sum().dataSync()[0]).toFixed(3));
// 1.000

// The virtualized buffer: the same cycle, but only the 48 steps around
// the PREDICTED onset were kept. The real onset arrived early, at what
// used to be step 4, and fell off the leading edge.
const kept = full.slice([0, 32, 0], [1, 48, 3]);   // [1, 48, 3]
const clipped = temporalAttention(kept);
console.log(kept.shape, clipped.weights.shape, clipped.attended.shape);
// [1, 48, 3] [1, 48] [1, 3]
console.log(tf.tidy(() => clipped.weights.sum().dataSync()[0]).toFixed(3));
// 1.000
tf.dispose([full, attended, weights, kept, clipped.attended, clipped.weights]);
// Dispose scorer at the end of the workflow.`}
</CodeBlock>

Both weight sums are 1. That normalization says nothing about confidence or missing observations. The pooled outputs also have the same shape, [1, 3], although their values can differ. An output-shape check alone will not detect a truncated input. Validate window length, timestamps and capture metadata before inference, and preserve the missing-data status for the operator.

## Putting the Position Back

Lesson 1 left a debt. The scorer above reads feature values and nothing else, so two windows holding the same readings in a different order pool to the identical summary: each weight follows its own reading, and the sum does not care what order they arrived in. On this crew's data that is the difference between a spike that precedes a frequency shift and one that follows it, and the model cannot see it. Transformers commonly add position information through embeddings, relative scores or rotations. The cheapest honest version is one extra feature: the step's position, scaled to [0, 1], concatenated onto the readings before scoring.

<CodeBlock language="typescript" title="positional-feature.ts">
{`// [batch, T, 3] -> [batch, T, 4]: the fourth feature is position / (T - 1)
function withPosition(sequence: tf.Tensor3D): tf.Tensor3D {
  return tf.tidy(() => {
    const [batch, T] = sequence.shape;
    const pos = tf.linspace(0, 1, T).reshape([1, T, 1]).tile([batch, 1, 1]);
    return tf.concat([sequence, pos], 2) as tf.Tensor3D;
  });
}

// A dense layer builds its weight matrix on first call, so the 3-input
// scorer above cannot be handed 4 inputs. Positional attention gets its own.
const positionalScorer = tf.layers.dense({ units: 1 });

function positionalAttention(sequence: tf.Tensor3D): { attended: tf.Tensor2D; weights: tf.Tensor2D } {
  return tf.tidy(() => {
    // Position informs WHERE to look; the pooled value is still the readings.
    const scores = (positionalScorer.apply(withPosition(sequence)) as tf.Tensor).squeeze([2]) as tf.Tensor2D;
    const weights = tf.softmax(scores, 1);                                  // [batch, T]
    const attended = tf.sum(tf.mul(sequence, weights.expandDims(2)), 1) as tf.Tensor2D;  // [batch, 3]
    return { attended, weights };
  });
}

// Before: a window and its reversal pooled to the same summary.
// After: the scorer can learn "late steps matter more" (or early ones),
// because lateness is now a number it multiplies by a weight.`}
</CodeBlock>

Sinusoidal encodings are one approach used in the original Transformer. Learned positions and relative or rotary schemes are other choices. Our linear position column only lets the scorer favor earlier or later steps; it is not a full transformer position mechanism. Attention only knows what you hand it, and position is a feature like any other.
