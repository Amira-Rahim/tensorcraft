> **PULSE INTERVAL LOG · first cycle of each of the last eight days (seconds):** 73.1 · 72.9 · 73.0 · 72.6 · 72.7 · 72.3 · 72.4 · 72.0

Read the column both ways. The noise says the numbers wander; the trend says they only wander downhill. Before this lesson names its subject, try to track that drift with a tool you already know.

Demir's first move is the usual one when a value jitters: exponential moving average, `smoothed = alpha * new + (1 - alpha) * old`, the same trick as smoothing a scroll position. Run it on the log above with two different alphas and the problem introduces itself:

<CodeBlock language="typescript" title="ema-two-alphas.ts">
{`const log = [73.1, 72.9, 73.0, 72.6, 72.7, 72.3, 72.4, 72.0];

const smooth = (alpha: number) =>
  log.reduce((s, x) => alpha * x + (1 - alpha) * s);

smooth(0.2); // 72.57: beautifully smooth, but 0.57 s behind a signal
             // that has already reached 72.0. It lags the drift.
smooth(0.8); // 72.08: right on the drift, but the estimate now bounces
             // with every noisy reading it was supposed to absorb.`}
</CodeBlock>

A small alpha trusts history and lags the drift. A large alpha trusts the newest reading and inherits its noise. That tradeoff depends on the process and the cost of lag. A tuned EMA can be a useful baseline; a Kalman model makes the uncertainty assumptions explicit.

## Predict, Then Correct

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="kalman-filter.ts">
{`// Scalar random-walk state model: x(t) = x(t-1) + process noise.
// Measurement z(t) = x(t) + measurement noise. Q and R are VARIANCES.

interface KalmanState {
  estimate: number;      // current best guess
  variance: number;      // uncertainty in our estimate
}

class KalmanFilter {
  private state: KalmanState;
  private processNoise: number;      // variance of process noise per update
  private measurementNoise: number;  // variance of measurement noise

  constructor(initial: number, processNoise: number, measurementNoise: number) {
    if (![initial, processNoise, measurementNoise].every(Number.isFinite) || processNoise < 0 || measurementNoise <= 0) throw new Error('Invalid filter parameters');
    this.state = { estimate: initial, variance: 1 };
    this.processNoise = processNoise;
    this.measurementNoise = measurementNoise;
  }

  update(measurement: number): KalmanState {
    if (!Number.isFinite(measurement)) throw new Error('Invalid measurement');
    // PREDICT: where do we think the state is?
    const predicted = this.state.estimate;
    const predictedVariance = this.state.variance + this.processNoise;

    // UPDATE: how much to trust the new measurement?
    const gain = predictedVariance / (predictedVariance + this.measurementNoise);
    // gain ≈ 0: trust prediction (measurement is noisy)
    // gain ≈ 1: trust measurement (prediction is uncertain)

    // CORRECT: blend prediction with measurement
    this.state = {
      estimate: predicted + gain * (measurement - predicted),
      variance: (1 - gain) * predictedVariance,
    };

    return { ...this.state };
  }
}

// Track the anomaly timing interval, sampled once per day: each day's
// first cycle, eight days of log. Initialize from the first reading, then
// update on subsequent readings. The initial variance is a chosen prior.
const kf = new KalmanFilter(73.1, 0.1, 1.0);

const measurements = [73.1, 72.9, 73.0, 72.6, 72.7, 72.3, 72.4, 72.0];
for (const m of measurements.slice(1)) {
  const state = kf.update(m);
  console.log(\`Measurement: \${m.toFixed(1)}, Estimate: \${state.estimate.toFixed(2)}\`);
}
// Estimate walks 73.1 → 72.43 while the readings end at 72.0: the
// filter is absorbing the noise and trailing the trend, not following
// it. The per-day shrink gets read off the raw log, not off this line.`}
</CodeBlock>

The state here is one number with no term for change, so the gain settles and the estimate behaves like an EMA with a well-chosen alpha. It lags a steady trend for the same reason: the final estimate sits 0.43 behind the final reading. That is worse than the alpha-0.8 line Demir just dismissed, which ends 0.08 behind. Smoother output is not proof of greater accuracy: we do not know the noise-free state here. We chose process variance 0.1 and measurement variance 1, which determine the gain: by the eighth reading the gain is near its limiting value of 0.27, and the filter derived that for a state with no term for change in it. Tracking the trend itself takes a second state, the change per day. The drawer below derives the gain and works through that limit.

<DerivationDrawer summary="Where the gain formula comes from: minimize the posterior variance">
The update blends prediction and measurement: `estimate = prediction + K(z - prediction)`. Why THAT K and not a hand-picked alpha? Because K is the value that minimizes the variance of the blended estimate.

```
Prediction uncertainty:   P   (variance of the prediction)
Measurement uncertainty:  R   (variance of the sensor)

Blend:  x̂ = (1-K)·prediction + K·z
For unbiased prediction and measurement errors with zero covariance, the blend's error variance is
        V(K) = (1-K)²·P + K²·R
```

Minimize over K: differentiate and set to zero.

```
dV/dK = -2(1-K)·P + 2K·R = 0
      → K·(P + R) = P
      → K = P / (P + R)
```

That is line-for-line the `gain` in the code above: `predictedVariance / (predictedVariance + measurementNoise)`. Sanity-check the endpoints: a perfect sensor (R → 0) gives K → 1, trust the measurement; a useless sensor (R → ∞) gives K → 0, keep the prediction. Demir's "alpha that adjusts itself" is this quotient, recomputed every step as P shrinks with each correction. A steady-state Kalman gain can be constant when the model and noise statistics are constant; using that fixed gain is a legitimate design choice.

One honesty note the EMA bridge has earned. With a constant-state model like this one, P settles and the gain converges: about 0.27 at process noise 0.1 and measurement noise 1. After a handful of updates the filter behaves like an EMA with a well-chosen alpha, and it lags a steady drift the same way. What the adaptive gain buys is a clean burn-in, the gain falling 0.52, 0.38, 0.33 and on down to 0.27 while the estimate finds the level. It buys no immunity to trends. Tracking the drift itself takes a state with velocity in it: the 2-state constant-velocity Kalman, which is exactly this machinery run on `[interval, change-per-day]` instead of a single number. The crew's filter is the honest first rung, not the whole ladder.
</DerivationDrawer>
