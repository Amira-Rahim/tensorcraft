## Pin the Whole Artifact

<BridgeCallout bridge={frontmatter.concept.bridge} />

A model release includes its graph, weights, preprocessing configuration and output-label order. An application release also includes the code that reads them. A digest of `weights.bin` alone misses a changed activation, a new feature order or a swapped label map.

Record a cryptographic hash for every required file. A SHA-256 hash identifies bytes; it does not prove those bytes describe a good model. Keep the expected hashes in a trusted release record. Verify downloaded files against that record, then load the bytes you verified. Fetching the URL again creates a race if deployment changes the files between verification and inference.

The [downloadable browser runtime lab](/assignments/browser-runtime-lab-v1.zip) provides a runnable example. It fingerprints the JSON manifest and every named shard. It fetches them once, rejects HTTP errors or unexpected bytes, and passes those same bytes to `tf.io.fromMemory()`. This fixture has fixed preprocessing and one sigmoid output. A larger application must include its preprocessing and labels in the release record too.

<CodeBlock language="bash" title="verify-artifact.sh">
{`# From the downloaded browser runtime lab:
npm ci --ignore-scripts
node scripts/check-model-deployment.mjs

# Optional read-only verification of the current public teaching fixture:
node scripts/check-model-deployment.mjs --origin https://tensorcraft.app
# Report: test-results/model-deployment.json`}
</CodeBlock>

The local check rejects a changed graph, changed weights and a missing shard. It then restores the previous artifact and verifies its bytes and prediction. The hosted option fetches the public model over HTTPS and checks it against the pinned fixture. It does not deploy anything or rehearse a rollback on the production site.

## Gate Identity and Behavior Separately

Once identity is established, evaluate the candidate on data that matches the release question. Track baseline performance, per-class errors and the cost of mistakes. Choose an acceptance rule before inspecting this candidate's results. An accuracy floor can be one gate; it is rarely the entire release decision.

Reusing an evaluation set for many release decisions makes it a validation set. It is no longer an untouched final test. Keep a separate evaluation plan for a final claim, and monitor behavior after release because future data can change.

A latency gate also needs an environment: device, browser, backend, input shape, batch size, warmups and readback boundary. A CPU-only CI runner cannot certify a browser GPU latency budget. Use CI for reproducible correctness checks and a target-device run for the device budget. Weight bytes do not replace a whole-application memory measurement.

This workflow runs the downloaded lab's artifact checks when those files are in your repository root. It is a verification job; publication depends on your host and is a separate step.

<CodeBlock language="yaml" title="artifact-check.yml">
{`name: Model artifact checks
on: [pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci --ignore-scripts
      - run: node scripts/check-model-deployment.mjs`}
</CodeBlock>

A workflow file does not make a check mandatory. Configure the repository's merge rules to require the job, and verify the rule on a failing change. Publish only the artifact that passed. Rebuilding or retraining after the gate produces a new candidate that needs its own checks.

## Verify Publication and Rollback

A publish command can finish before every server or browser sees the new version. Deploy versioned, immutable directories when the host supports them, then switch the application to the verified release. Keep a complete known-good release available.

This is the release sequence, expressed as pseudocode because hosts have different publication APIs:

<CodeBlock language="text" title="release-sequence.txt">
{`1. Fetch the candidate by version; verify all expected hashes.
2. Load those exact bytes and run the pre-release behavior gates.
3. Preserve the complete current release, including app and preprocessing.
4. Publish the candidate and wait for its version and hashes to be served.
5. Run smoke checks on those served bytes.
6. On failure, restore the previous complete release.
7. Verify the restored version and smoke checks; alert if restoration fails.
8. Keep the attempted release marked failed, even after successful recovery.`}
</CodeBlock>

Bound the wait and treat a timeout as failure. A 200 response can still contain a stale artifact. Restoring only a manifest can leave it paired with incompatible weights; restoring only weights can leave newer preprocessing in place. Rollback also cannot undo decisions already made by the bad release or reverse a change in the incoming data.
