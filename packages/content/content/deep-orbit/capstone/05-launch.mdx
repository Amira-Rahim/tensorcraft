        if (!intervals.every(v => Number.isFinite(v) && v > 0)) throw new Error('Invalid intervals');
        const ratios = [];
        for (let i = 0; i < intervals.length - 1; i++) {
          const ratio = intervals[i + 1] / intervals[i];
          if (!Number.isFinite(ratio) || ratio <= 0) throw new Error('Unrepresentable ratio');
          ratios.push(ratio);

## Deploy and Verify

Two deployment shapes appear in this lesson. The helper below is one smoke gate after artifact verification. The other is the hot canary from the decision above: ship to ONE console, watch it against live data for a fixed interval, then roll fleet-wide only if it holds. Canaries trade a slice of your window for a bounded blast radius; the suite spends time on specified checks, which can still miss failures. Use pre-release checks before a canary, then define the conditions for wider rollout. Agreement with a shadow model is a regression check, not evidence that both are correct.

<CodeBlock language="typescript" title="deploy.ts">
{`interface DeployedPipeline {
  // Must resolve only after inference and readback have completed.
  classify(input: Float32Array, signal: AbortSignal): Promise<{ label: string }>;
  dispose(): void;
}
interface Probe { input: number[]; label: string; }

async function verifyHostedPipeline(
  baseUrl: string,
  // Application adapter: fetch the complete release, verify trusted hashes
  // as in lesson 2, and build a pipeline from those SAME bytes and scaler.
  loadVerifiedPipeline: (url: string, signal: AbortSignal) => Promise<DeployedPipeline>,
  probes: Probe[], // fixed labeled smoke set supplied with the release record
  budget: { minAccuracy: number; p95Ms: number },
  signal: AbortSignal,
): Promise<{ passed: boolean; accuracy: number; p95Ms: number }> {
  if (!probes.length || !probes.every(p => p.input.length === 64 && p.input.every(Number.isFinite) && typeof p.label === 'string' && p.label.trim()) ||
      !Number.isFinite(budget.minAccuracy) || budget.minAccuracy < 0 || budget.minAccuracy > 1 ||
      !Number.isFinite(budget.p95Ms) || budget.p95Ms <= 0) throw new Error('Invalid smoke configuration');
  signal.throwIfAborted();
  const pipeline = await loadVerifiedPipeline(baseUrl, signal);
  try {
    let correct = 0;
    for (const probe of probes) {
      signal.throwIfAborted();
      const result = await pipeline.classify(new Float32Array(probe.input), signal);
      if (typeof result?.label !== 'string' || !result.label.trim()) throw new Error('Invalid prediction');
      if (result.label === probe.label) correct++;
    }
    // Warmup and repeated timing on the same workload. These repetitions
    // measure latency; they are not additional independent accuracy cases.
    for (let i=0; i<10; i++) {
      signal.throwIfAborted();
      const result = await pipeline.classify(new Float32Array(probes[i%probes.length].input), signal);
      if (typeof result?.label !== 'string' || !result.label.trim()) throw new Error('Invalid prediction');
    }
    const times: number[] = [];
    for (let i=0; i<100; i++) {
      signal.throwIfAborted();
      const input = new Float32Array(probes[i%probes.length].input);
      const start = performance.now();
      const result = await pipeline.classify(input, signal);
      const elapsed = performance.now()-start;
      signal.throwIfAborted();
      if (typeof result?.label !== 'string' || !result.label.trim()) throw new Error('Invalid prediction');
      times.push(elapsed);
    }
    times.sort((a,b) => a-b);
    const accuracy = correct/probes.length;
    const p95Ms = times[Math.ceil(times.length*0.95)-1];
    return {passed:accuracy >= budget.minAccuracy && p95Ms <= budget.p95Ms, accuracy, p95Ms};
  } finally {
    pipeline.dispose();
  }
}
// Run under a deadline, as in the verify-deployment exercise. The loader and
// classifier must honor cancellation. Record device/backend and artifact
// identity beside this result. A rejected check fails the release gate.`}

## The Interval Train, in Ratios

Farah's decomposition handed the crew a sequence, not a test. The sequence is the sub-pulse gaps, 1, 1, 2, 3, 5, 8, 13, each gap the sum of the two before it. What a classifier can check is the sequence divided through: each gap over the gap before it, which drops the units and leaves six numbers.

<CodeBlock language="text" title="interval-ratios.txt">
{`gaps      1     1     2     3     5     8     13
divide          1/1   2/1   3/2   5/3   8/5   13/8
ratios          1.0   2.0   1.5   1.667 1.6   1.625`}
</CodeBlock>

Three properties of that list are what the finale exercise grades.

Dividing removes the scale. Farah's capture was in seconds and the sequence is unitless, and both decompose to the same six ratios. That is the reason the calibration overlay lined up at all.

Successive Fibonacci ratios approach the golden ratio, about 1.618. This exercise checks only the displayed finite template. It assumes every recording ends at the same final gap, so a shortened recording is a suffix of that template. General recordings can end elsewhere; they need alignment and a minimum evidence length. One matching ratio is weak evidence, not a unique identification of the Fibonacci sequence.

Measured seconds do not divide exactly. Even in the archive's rounded slice, 11.7 over 7.2 comes back as 1.6249999999999998, and a live capture misses by more than that, so a match is a band around each expected ratio rather than an equality. The width of that band is a false-alarm decision like every other cutoff in module 7: too tight and the real train is rejected by rounding, too loose and a metronome starts qualifying.

## Challenge

Write the runner under that verification script: every check in order, each one awaited before the next starts, and a deployment that passes only when all of them do.

A verifier also needs a deadline for each check. On timeout, report the failed check and skip its dependents. An abort signal requests cancellation, but the check must cooperate; a timeout alone cannot stop its work.

The transferable work is the engineering: define a prediction target, build features, preserve the preprocessing contract, evaluate errors, release a specific artifact and watch its behavior. Replacing the columns is not enough. A new dataset may need a different model, loss, split, threshold and validation plan.

For your own project, choose a labeled task and split by time, person or other relevant group before fitting preprocessing. Keep validation data for design choices and a separate final test. Train a small baseline, compare it with a simpler rule, and record error costs as well as aggregate metrics. Package the model with its scaler and label map. After deployment, monitor input validity, latency and output changes, then evaluate against outcomes when labels arrive.
