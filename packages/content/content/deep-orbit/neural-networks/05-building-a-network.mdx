## Assembly Required

Compile the network below, then call `model.predict()` immediately. It runs. It returns a probability. And the number is meaningless, because compilation wires up the optimizer and loss without ever touching the connection weights, which are still random. Assembly and training are separate steps, the way `http.createServer(handler)` and the `listen()` call that puts it to work are separate steps.

If every connection weight in a layer started at zero, every unit in that layer would compute the same output and receive the same gradient. They would update in lockstep and never come to represent different features. Random values break that symmetry. TensorFlow.js draws only the connection weights at random and starts every bias at zero, which is safe because the random weights already make the units differ. The scale of the draw matters too. A dense layer defaults to Glorot initialization, which sizes the random draw by the layer's input and output counts together. The signal then neither grows nor shrinks much as it passes through. The sigmoid output unit starts on the sloped middle of its curve rather than the flat tails lesson 2 called saturation, and TensorFlow.js applies the same default to the relu layers. TensorFlow.js calls a layer's weight matrix its kernel, and `kernelInitializer` is the option that controls the choice.

{`import * as tf from '@tensorflow/tfjs';

// 1. Create the model
const model = tf.sequential();

// 2. Add layers (like registering each stage of the pipeline)
model.add(tf.layers.dense({
  units: 32,
  activation: 'relu',
  inputShape: [3],     // 3 sensor inputs
}));
model.add(tf.layers.dense({ units: 16, activation: 'relu' }));
model.add(tf.layers.dense({ units: 1, activation: 'sigmoid' }));

// 3. Compile (like createServer(): wired up, not yet working)
model.compile({
  optimizer: 'adam',              // how to update weights
  loss: 'binaryCrossentropy',    // how to measure error
  metrics: ['accuracy'],          // what to track
});

// 4. Verify with summary. TFJS names layers className + counter
// (dense_Dense1, not dense_1) and prints four columns:
model.summary();
// __________________________________________________________________________________________
// Layer (type)                Input Shape               Output shape              Param #
// ==========================================================================================
// dense_Dense1 (Dense)        [[null,3]]                [null,32]                 128
// __________________________________________________________________________________________
// dense_Dense2 (Dense)        [[null,32]]               [null,16]                 528
// __________________________________________________________________________________________
// dense_Dense3 (Dense)        [[null,16]]               [null,1]                  17
// ==========================================================================================
// Total params: 673
// Trainable params: 673
// Non-trainable params: 0
// __________________________________________________________________________________________

// 5. Test with a prediction
const testInput = tf.tensor2d([[0.5, 0.8, 0.2]]);
const prediction = model.predict(testInput) as tf.Tensor;
console.log('Initial prediction:', prediction.dataSync());`}
</CodeBlock>

`optimizer: 'adam'` names the algorithm that adjusts weights during training, and Adam is the usual first pick because it adapts the learning rate as it goes. `loss: 'binaryCrossentropy'` sets how error gets measured. Binary crossentropy fits a yes/no output, and MSE fits continuous values. `metrics: ['accuracy']` only adds a number to the training log, the share of predictions that came out correct. It does not change what the model learns.

## Challenge

Assemble and compile the complete DEEP SCAN signal classifier, then measure what compiling bought. You build it twice, sweep both copies over the same 120 readings while both are still untrained, train one of them, and sweep that one again. The `fit()` call is written out for you in the instructions; module 3 is where it gets taken apart.

One difference from the bridge build above, and it is deliberate: the demo wired to the feed tonight reads the 3 normalized features and totals 673 parameters. Farah has specced a wider front door, 8 features per reading, which puts her build at 833 parameters. Same architecture, five more inputs. Build hers. Then note what happens to the spec: five of Farah's eight features have no source in the stream yet, so the front door gets cut back to the three that do. 673 is the count module 3 trains.
