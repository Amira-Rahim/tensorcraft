## Tree-Shaking Weights

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="pruning.ts">
{`import * as tf from '@tensorflow/tfjs';

function pruneWeights(weights: number[], sparsity: number): number[] {
  // Sort by absolute value to find the threshold
  const sorted = weights.map(Math.abs).sort((a, b) => a - b);
  const threshold = sorted[Math.floor(sorted.length * sparsity)];

  // Zero out weights below threshold
  return weights.map(w => Math.abs(w) < threshold ? 0 : w);
}

// Example: prune 60% of weights (keep the 40% with largest magnitude)
const original = [0.5, -0.01, 0.002, -0.8, 0.003, 0.7, -0.001, 0.6];
const pruned = pruneWeights(original, 0.6);
console.log(pruned);
// [0.5, 0, 0, -0.8, 0, 0.7, 0, 0.6]
// 4 of 8 weights remain (4 pruned, those closest to zero:
// 60% of 8 rounds down to a cut of 4)

// Hold the result to tree-shaking's promise: same probe input,
// both weight sets, "nobody notices the difference."
const probe = new Array(original.length).fill(1);
const dot = (ws: number[]) => ws.reduce((sum, w, i) => sum + w * probe[i], 0);
console.log(dot(original).toFixed(3));  // 0.994
console.log(dot(pruned).toFixed(3));    // 1.000

// Sparsity levels for DEEP SCAN:
// 30% pruned: 93.8% accuracy (vs 94.2% baseline), barely noticeable
// 60% pruned: 92.1% accuracy, good tradeoff
// 80% pruned: 87.5% accuracy
// 90% pruned: 71.2% accuracy, model is broken`}
</CodeBlock>

0.994 against 1.000. A tree-shaken bundle would print the same number both times; that is what "provably unreachable" buys, and it is the exact clause the console just struck from Demir's sign-off. The four weights that went to zero were contributing a combined -0.006 to this output, and now they contribute nothing. Pruning removes weights that contribute *almost* nothing, and "almost" is doing real work in that sentence: every pruned weight moves the output a little. The craft is in measuring how much all those littles add up to, which is what the sparsity ladder at the bottom of the block does at model scale.

He pushes it to the staging dashboard before dinner, without waiting for the replay suite to tell him what the missing 6.7 points actually contain.

He reverts. The "almost nothing" in those extra weights turned out to be the anomaly itself: rare signals live in small weights, and aggressive pruning deletes the model's memory of exactly the things it has seen least.

And the directive's second assumption resolves the unglamorous way: nothing was ever "removed." A dense weight matrix has no delete operation; pruning zeroes weights in place, and the megabytes only leave when the storage format encodes the sparsity instead of writing the zeros out longhand.

<DerivationDrawer summary="Why magnitude is the saliency proxy, and when the proxy lies">
What pruning actually wants to know is each weight's saliency: how much the loss moves if this weight becomes zero. Taylor-expand the loss around the trained weights:

```
ΔL ≈ Σᵢ  gᵢ·Δwᵢ  +  ½·Σᵢ hᵢ·Δwᵢ²        (gᵢ = ∂L/∂wᵢ, hᵢ = curvature)
```

Zeroing weight i means Δwᵢ = -wᵢ. At a trained minimum the gradients gᵢ are approximately zero (that is what "trained" means), so the first-order term vanishes and the damage is second-order:

```
ΔLᵢ ≈ ½·hᵢ·wᵢ²
```

Magnitude pruning keeps the |wᵢ| factor and quietly assumes the curvature hᵢ is roughly equal across weights. That assumption is the entire method, and it is usually good enough, which is why `sort by |w|, zero the smallest` works at all. It is also exactly where the 80% build failed: the weights encoding rare signals were small AND sat in high-curvature directions, so their true ΔL was large while their magnitude said "safe to cut." When the proxy lies, it lies about precisely the things the model has seen least.
</DerivationDrawer>

## Combined Optimization

<CodeBlock language="typescript" title="combined.ts">

// Step 1: Prune 60% of weights → 60% smaller (effective)
// Step 2: Quantize remaining to uint8 storage → 4x smaller

// Original: 85M params × 4 bytes = 340 MB
// After pruning: 34M non-zero params (60% zeros can be stored efficiently)

// Combined result: 340 MB → 42 MB (8x compression!)
