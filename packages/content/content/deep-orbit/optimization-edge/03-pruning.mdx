## Tree-Shaking Weights

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="pruning.ts">
{`import * as tf from '@tensorflow/tfjs';

function pruneWeights(weights: number[], sparsity: number): number[] {
  // Sort by absolute value to find the threshold
  const sorted = weights.map(Math.abs).sort((a, b) => a - b);
  const threshold = sorted[Math.floor(sorted.length * sparsity)];

  // Zero out weights below threshold
  return weights.map(w => Math.abs(w) < threshold ? 0 : w);
}

// Example: request 60% sparsity, then read what you actually got.
const original = [0.5, -0.01, 0.002, -0.8, 0.003, 0.7, -0.001, 0.6];
const pruned = pruneWeights(original, 0.6);
console.log(pruned);
// [0.5, 0, 0, -0.8, 0, 0.7, 0, 0.6]
// 4 of 8 weights remain (4 pruned, those closest to zero:
// 60% of 8 rounds down to a cut of 4)

// Hold the result to tree-shaking's promise: same probe input,
// both weight sets, "nobody notices the difference."
const probe = new Array(original.length).fill(1);
const dot = (ws: number[]) => ws.reduce((sum, w, i) => sum + w * probe[i], 0);
console.log(dot(original).toFixed(3));  // 0.994
console.log(dot(pruned).toFixed(3));    // 1.000

// Sparsity levels for DEEP SCAN, one accuracy per level, scored on the
// natural mix of captures:
// 30% pruned: 93.8% accuracy (vs 94.2% baseline), barely noticeable
// 60% pruned: 91.8% accuracy, good tradeoff
// 80% pruned: 91.6% accuracy, two tenths of a point below 60
// 90% pruned: 71.2% accuracy, model is broken`}
</CodeBlock>

0.994 against 1.000. A tree-shaken bundle would print the same number both times; that is what "provably unreachable" buys, and it is the exact clause the console just struck from Demir's sign-off. The four weights that went to zero were contributing a combined -0.006 to this output, and now they contribute nothing. Pruning zeros weights that contribute *almost* nothing, and "almost" is doing real work in that sentence: every pruned weight moves the output a little. The craft is in measuring how much all those littles add up to, which is what the sparsity ladder at the bottom of the block does at model scale. The rule the block runs is magnitude pruning, the unstructured kind: rank the weights by absolute value, zero the smallest, and leave every shape exactly as it was.

Two things change when that rule runs on a model instead of on an array. The ranking covers every kernel in the model at once rather than one layer at a time, so a layer whose weights are all small can lose most of them while a layer carrying larger ones keeps nearly all of its own. And the biases sit out of it. A dense layer holds one bias per unit against hundreds of kernel weights, so keeping them costs almost nothing, and zeroing one shifts everything that unit says instead of trimming a single connection.

Reading the result changes too, and the natural mix is why. The ladder is scored on held-out captures at the rate they arrive, which makes anomalies a sliver of it: 6 labelled anomalies against 500 of each ordinary class, so the rare class is 0.3 percent of the captures being scored. Those six are held out, and the six the retrain learned from are a different six. Do the arithmetic on that share before you read any row. A class at 0.3 percent can go from every capture right to every capture wrong and move the aggregate by 0.3 of a point. Whatever you can watch falling in that column is the common classes losing ground, and the rare class is invisible there either way. It also means a row where that column holds steady is not a row where nothing happened. Score the same pruned model on a slice with equal counts per class and the pass reads differently, which is the measurement the exercise below asks for.

Demir reads that ladder and gets ambitious anyway: at 80 percent sparsity the download would land near 25 MB, headroom to spare, and the accuracy column has almost stopped moving. Between 60 and 80 it gives up two tenths of a point for another fifth of the weights. He signs off on that. What he never asks for is the number the ladder cannot carry. He pushes the build to the staging dashboard before dinner without running the replay suite.

The 2.4 points he did read were an earlier cost and a different one: almost all of that fall was the common classes giving up ground between the baseline and 60. Rare signals live in small weights, magnitude pruning takes the small weights first, and no aggregate on this mix can show you that it happened.

And the directive's second assumption resolves the unglamorous way: nothing was ever "removed." A dense weight matrix has no delete operation, so magnitude pruning zeroes weights in place and the file keeps every slot. No sparse storage format in TensorFlow.js changes that. A weight entry in the manifest carries a name, a shape, a dtype, and for a quantized weight a scale and a min. There is no index list of nonzero positions anywhere in it, so all 51 million zeros get written out at full width and the file does not shrink by a byte. What this pass buys in this runtime is compressibility, and that shows up on the wire rather than on disk. The structured kind is the one that does shrink a file: drop a whole unit and the layer's shape changes with it, so the weights go and the arithmetic of every call goes with them. It costs more to get there, since the model has to be retrained once the units are gone, and it is not what this lesson does.

<DerivationDrawer summary="Why magnitude is the saliency proxy, and when the proxy lies">
What pruning actually wants to know is each weight's saliency: how much the loss moves if this weight becomes zero. Taylor-expand the loss around the trained weights:

```
ΔL ≈ Σᵢ  gᵢ·Δwᵢ  +  ½·Σᵢ hᵢ·Δwᵢ²        (gᵢ = ∂L/∂wᵢ, hᵢ = curvature)
```

Zeroing weight i means Δwᵢ = -wᵢ. At a trained minimum the gradients gᵢ are approximately zero (that is what "trained" means), so the first-order term vanishes and the damage is second-order:

```
ΔLᵢ ≈ ½·hᵢ·wᵢ²
```

Magnitude pruning keeps the |wᵢ| factor and quietly assumes the curvature hᵢ is roughly equal across weights. That assumption is the entire method, and it is usually good enough, which is why `sort by |w|, zero the smallest` works at all. It is also exactly where the 80% build failed: the weights encoding rare signals were small AND sat in high-curvature directions, so their true ΔL was large while their magnitude said "safe to cut."
</DerivationDrawer>

<DerivationDrawer summary="The third compression axis: low-rank structure and SVD">
A third compression axis exists and this module does not use it: rank. A weight matrix of shape [512, 512] holds 262,144 numbers, but if its rank is effectively 40, those numbers are redundant: the matrix is 40 independent directions dressed up as 512.

Singular Value Decomposition makes it precise. Any matrix factors as `W = U · Σ · Vᵀ`: rotate, scale along principal directions, rotate again. The scale factors (singular values) come out sorted, and in trained networks they usually decay fast: a few large directions carry the transformation, a long tail contributes noise. Truncate to the top k and the factors `U[:, :k] · Σ[:k] · V[:, :k]ᵀ` store `k · (512 + 512 + 1)` numbers instead of 262,144. At k = 40 that is 41,000 numbers, a 6.4x cut on that layer, with reconstruction error bounded by the singular values you dropped.

Why this works at all is the fact pruning exploits from a different angle: trained weight matrices concentrate their useful transformation in far fewer directions than their shape advertises. Magnitude pruning removes the smallest coordinates; SVD removes the smallest directions, which is more directly aligned with the transformation the matrix performs, though the two bets pay off on different matrices. That alignment is part of why low-rank factorization (LoRA and friends) became the default way to fine-tune large models on small hardware.
</DerivationDrawer>
