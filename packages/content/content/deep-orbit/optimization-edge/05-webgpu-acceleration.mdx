      async function initBestBackend(
        preference: BackendName[],
        runtime: Runtime
      ): Promise<BackendName> {
        for (const name of preference) {
          let started = false;
          try {
            started = await runtime.setBackend(name);
          } catch {
            started = false;

A WebGL backend can store tensor values in textures and calculate results with graphics shaders. WebGPU provides compute shaders for calculations such as matrix multiplication and sums. Both take time to start work, move data, and wait for results. The API name alone does not tell you which is faster.

Give the dashboard a startup path that can recover when a preferred backend fails. Then Nazari can measure the backend that actually starts.

## WebGPU Backend

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="webgpu-setup.ts">
{`import * as tf from '@tensorflow/tfjs';
// The bundled package registers only cpu and webgl. The two imports below
// are what put 'webgpu' and 'wasm' in the registry: drop one and setBackend
// throws on that name instead of resolving false. The 0249 dashboard had
// the wasm line and not the webgpu line, which is why its fallback landed
// on wasm at 45 ms and never on anything faster.
import '@tensorflow/tfjs-backend-webgpu';
import '@tensorflow/tfjs-backend-wasm';

async function initBestBackend(): Promise<string> {
  // tf.setBackend can resolve false for initialization failure and can
  // throw, for example when the name is unregistered.
  // Read the return value, or this function reports a backend that
  // is not running.
  const tryBackend = async (name: string) => {
    try {
      if (!(await tf.setBackend(name))) return false;
      await tf.ready();
      return tf.getBackend() === name;
    } catch {
      return false;
    }
  };

  if ('gpu' in navigator && await tryBackend('webgpu')) return 'webgpu';
  if (await tryBackend('webgl')) return 'webgl';
  if (await tryBackend('wasm')) return 'wasm';
  if (await tryBackend('cpu')) return 'cpu';
  throw new Error('No usable backend');
}

const backend = await initBestBackend();
console.log('Using backend:', backend);

// Fictional mission timings for the 85 MB uint8 build.
// They are not predictions for your hardware or the downloaded model. These time the whole bundle end to end,
// the same call lesson 1 profiled, and not the small classifier
// lesson 4 puts a cache in front of. That one runs in microseconds and
// none of these rows describe it:
// WebGPU:  ~5ms per inference   (3x faster than WebGL)
// WebGL:   ~15ms per inference  (GPU via graphics API)
// WASM:    ~45ms per inference  (CPU, SIMD optimized)
// CPU:     ~120ms per inference (pure JavaScript)
// The wasm row is the same 45 ms the 340 MB build profiled at in this
// module's first lesson. Quantization cut the bytes on disk and pruning
// cut the bytes on the wire. Neither reduced the dense operation count.
// The scenario keeps this timing fixed; real latency still needs measurement.
//
// The cached classifier's own pipeline lands on the same two GPU
// figures for a different reason: its 5 ms on WebGPU and 15 on WebGL
// cover feature extraction and readback around the classifier call
// lesson 4 caches, not the bundle matmuls these rows time. Module 11's
// model card keeps the two on separate lines.`}
</CodeBlock>

Check the returned value as well as errors. In TFJS 4.22, a registered backend can fail to start and resolve false. A backend that was never registered throws. A reported backend name after a failed attempt does not prove it can run operations.

The example checks readiness, tries CPU last, and throws if nothing starts. The exercise tests this selection logic with a controlled runtime. The downloadable lab tests real backends and predictions.

## Time the completed prediction

Demir's first bridge-console run reported 0.4 milliseconds on WebGPU, compared with 15 on WebGL. His timer had stopped before the GPU finished. Including output readback changed the WebGPU result to 5 milliseconds. These are fictional mission timings; compare the two measurement boundaries below.

<CodeBlock language="typescript" title="measure-inference.ts">
{`// First attempt: start the clock, call predict, stop the clock.
const t0 = performance.now();
const flattering = model.predict(warmInput) as tf.Tensor;
const naive = performance.now() - t0;
await flattering.data(); // finish this call before the separate comparison
flattering.dispose();
// Bridge console, webgpu backend: 0.4 ms. Too good, and it is: on a
// GPU backend, predict() SCHEDULES GPU kernels and returns. The clock
// stopped while the GPU was still working.

// Module 4's rule: the readback goes INSIDE the timed region, because
// inference is not over until the result is back where JS can read it.
const t1 = performance.now();
const output = model.predict(warmInput) as tf.Tensor;
await output.data();  // forces completion before the clock stops
const honest = performance.now() - t1;
output.dispose(); // warmInput belongs to the caller
// Bridge console, webgpu backend: 5 ms. That is the number in the
// table above and the one every claim in this lesson stands on.

// CPU kernels run synchronously, but readback, scheduling and measurement
// noise can still change timings. One pair of calls does not isolate GPU
// execution time; repeat trials and report distributions.`}
</CodeBlock>

These timings are fictional story values. The runtime lab records real measurements for a named backend, device, and model. Your results will differ. Keep the output readback inside the timed section so you measure a finished prediction. The crew has already paid for trusting a timer that stopped too soon.
