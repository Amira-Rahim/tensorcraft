<Dialogue speaker="Chief Nazari">
WebGL was designed for rendering triangles, not multiplying matrices. WebGPU is the real thing: direct GPU compute access. Set it up.
</Dialogue>

<Dialogue speaker="Ensign Demir">
So WebGPU is to WebGL what Web Workers are to the main thread: purpose-built for the actual workload instead of shoehorning into a different API?
</Dialogue>

Nazari isn't wrong about the triangles. WebGL runs tensor math by smuggling it through a graphics pipeline: data as textures, math as fragment shaders, overhead on every op. WebGPU's compute shaders run matrix multiplications and parallel reductions directly, which is most of what inference is.

## WebGPU Backend

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="webgpu-setup.ts">
{`import * as tf from '@tensorflow/tfjs';
// The bundled package registers only cpu and webgl. The two imports below
// are what put 'webgpu' and 'wasm' in the registry: drop one and setBackend
// throws on that name instead of resolving false. The 0249 dashboard had
// the wasm line and not the webgpu line, which is why its fallback landed
// on wasm at 45 ms and never on anything faster.
import '@tensorflow/tfjs-backend-webgpu';
import '@tensorflow/tfjs-backend-wasm';

async function initBestBackend(): Promise<string> {
  // tf.setBackend RESOLVES FALSE when a registered backend fails to
  // initialize. It throws only when the name is not registered at all.
  // Read the return value, or this function reports a backend that
  // is not running.
  const tryBackend = async (name: string) => {
    try {
      if (!(await tf.setBackend(name))) return false;
    } catch {
      return false;  // name not registered: its package was not imported
    }
    await tf.ready();
    return true;
  };

  if ('gpu' in navigator && await tryBackend('webgpu')) return 'webgpu';
  if (await tryBackend('webgl')) return 'webgl';
  if (await tryBackend('wasm')) return 'wasm';

  await tf.ready();
  return tf.getBackend();  // whatever the engine settled on, usually cpu
}

const backend = await initBestBackend();
console.log('Using backend:', backend);

// Benchmark results for DEEP SCAN (the 85 MB uint8 build), as measured
// at the bridge console with the readback pattern below; your hardware
// will print different absolutes. These time the whole bundle end to end,
// the same call lesson 1 profiled, and not the eleven-feature classifier
// lesson 4 puts a cache in front of. That one runs in microseconds and
// none of these rows describe it:
// WebGPU:  ~5ms per inference   (3x faster than WebGL)
// WebGL:   ~15ms per inference  (GPU via graphics API)
// WASM:    ~45ms per inference  (CPU, SIMD optimized)
// CPU:     ~120ms per inference (pure JavaScript)
// The wasm row is the same 45 ms the 340 MB build profiled at in this
// module's first lesson. Quantization cut the bytes on disk and pruning
// cut the bytes on the wire; neither changed how much arithmetic a call
// does, so the fallback time never moved.
//
// The eleven-feature classifier's own pipeline lands on the same two GPU
// figures for a different reason: its 5 ms on WebGPU and 15 on WebGL
// cover feature extraction and readback around the classifier call
// lesson 4 caches, not the bundle matmuls these rows time. Module 11's
// model card keeps the two on separate lines.`}
</CodeBlock>

The `if` around `setBackend` is the part people leave out, and leaving it out is how a fallback chain lies to you. `setBackend` resolves to a boolean. A backend that is registered but fails to initialize logs `Initialization of backend webgl failed` and resolves `false`; nothing is thrown, so a bare `try`/`catch` never fires. Only an unregistered name throws, which is what you get when you forgot the import at the top of the file. Skip the return value and this function reports `webgl` on the 0249 dashboard, the one with no working WebGL context. `tf.ready()` then settles the engine on the next registered backend that does initialize. The imports at the top of this file leave wasm registered, so the function says `webgl` while every inference runs at 45 ms. Drop the wasm import and there is nothing left but cpu, at 120 ms.

## Measure the Claim

That table did not come off a spec sheet, and its first draft was wrong. Demir's opening timing run at the bridge console put WebGPU at 0.4 milliseconds, a figure that would make it nearly forty times faster than WebGL's 15, not the 3x the table above reports. The figure survived until he applied module 4's own rule to it:

<CodeBlock language="typescript" title="measure-inference.ts">
{`// First attempt: start the clock, call predict, stop the clock.
const t0 = performance.now();
const flattering = model.predict(warmInput) as tf.Tensor;
const naive = performance.now() - t0;
// Bridge console, webgpu backend: 0.4 ms. Too good, and it is: on a
// GPU backend, predict() SCHEDULES GPU kernels and returns. The clock
// stopped while the GPU was still working.

// Module 4's rule: the readback goes INSIDE the timed region, because
// inference is not over until the result is back where JS can read it.
const t1 = performance.now();
const output = model.predict(warmInput) as tf.Tensor;
await output.data();  // forces completion before the clock stops
const honest = performance.now() - t1;
// Bridge console, webgpu backend: 5 ms. That is the number in the
// table above and the one every claim in this lesson stands on.

// On the cpu backend the two clocks agree to within a millisecond,
// because cpu kernels run synchronously. The gap between naive and
// honest is itself a measurement: it tells you how asynchronous your
// backend really is.`}
</CodeBlock>

The millisecond figures in this lesson are what the crew measured at that console, on that GPU, that night. Run the pattern yourself and the absolutes will move; the discipline is the part that transfers. A GPU benchmark without the readback inside the clock is timing how fast you can ask, and the crew has been burned by that number once already.

## The Complete Optimization Stack

<CodeBlock language="typescript" title="optimization-stack.ts">
{`// DEEP SCAN optimization stack.
//
// Both halves of the speed win are backend changes. The 45 ms baseline was
// profiled on the wasm fallback, since the dashboard had no working WebGL
// context that night; the context came back on its own once the smaller
// build stopped exhausting memory. So 45 to 15 is WebGL restored, and
// 15 to 5 is the WebGPU swap. Step 2 shrinks stored bytes, which is what
// buys a load peak the dashboard survives. Step 3 shrinks nothing on
// disk, because TF.js writes dense weights; its zeros only make the file
// compress, so it buys a smaller download. Neither touches the
// arithmetic a call does. Step 4 cuts how many calls happen, not what
// one call costs.
//
// 45 to 15 is 3x, and module 4 measured WebGL at 6x over wasm. Both hold.
// That 6x came off a bare 256x256 matmul, which is nothing but the kernel
// a GPU is built for. A real model also marshals inputs, walks layers,
// applies activations and reads one small result back per call, and none
// of that runs faster on a GPU, so the end-to-end gain comes in under
// the kernel gain. A GPU kernel benchmark is an upper bound on what a real
// model will see.

console.log('=== DEEP SCAN Optimization Stack ===');
console.log('');
console.log('1. PROFILING:      Identified bottleneck layers');
console.log('2. QUANTIZATION:   340 MB → 85 MB file (uint8)');
console.log('3. PRUNING:        85 MB file unchanged, 70 → 42 MB served');
console.log('4. CACHING:        40% fewer inference calls');
console.log('5. WebGPU:         15ms → 5ms inference');
console.log('');
console.log('Result:');
console.log('  File:     340 MB → 85 MB (4x smaller on disk)');
console.log('  Served:   315 MB → 42 MB gzipped (7.5x less to download)');
console.log('  Speed:    45ms → 5ms (9x, all of it from the backend)');
console.log('  Accuracy: 94.2% → 91.8% (2.4 points)');
console.log('  Fits in dashboard: YES ✓');
console.log('');
console.log('File, served and speed are the whole DEEP SCAN bundle.');
console.log('Accuracy is the five-class classifier inside it, the only');
console.log('part of the bundle carrying a scoreboard.');`}
