With **lazy loading**, the pipeline reads each record when the next stage requests it. Limit how much data waits in memory, and dispose of tensors after use. That keeps memory use from growing with the archive.

A **batch** is a small group of readings that the model processes together. `.batch(32)` makes groups of 32. The model processes one group, then requests the next. Unlike Demir's failed version, the pipeline does not keep the whole archive in memory.

Demir needs a loader he can trust before opening the full archive again.
Use traceable row IDs to check that it reads on demand, keeps features with
their labels, and leaves later readings out of training.

## Reading samples on demand

Use the exercise's 16-row archive stand-in. Each row has three **features**
(numbers the model reads): amplitude, zero-crossing count, and phase. Its
**label** is the target 0 or 1. These small values stand in for the ship's
28,800 archived readings and their much larger raw captures.

Keep the archive read inside the generator loop. Each request then reads one row without loading the full archive into an array.

<CodeBlock language="typescript" title="one-sample.ts">
{`function* rowsById(ids) {
  for (const id of ids) {
    const row = readSample(id);
    yield {
      xs: tf.tensor(row.features), // one sample: [3]
      ys: tf.tensor([row.label]),  // one label: [1]
    };
  }
}`}
</CodeBlock>

Wrap each label in an array, `[row.label]`. Four samples then make feature
shape `[4, 3]` and label shape `[4, 1]`: four rows, one label per row.

## Shuffling before batching

<CodeBlock language="typescript" title="batch-and-read.ts">
{`const ids = Array.from({ length: 16 }, (_, i) => i);
const source = tf.data.generator(() => rowsById(ids));
const batches = source.shuffle(10).batch(4);
await batches.forEachAsync((group) => {
  console.log(group.xs.shape); // [4, 3]
});`}
</CodeBlock>

Shuffle before batching so individual rows can move between groups. A buffer
of 10 holds ten rows to choose from. This mixes the ten rows currently in the buffer. A full shuffle would consider all 16 rows at once.

In the challenge, save each shape in `batchShapes`. Wait for `forEachAsync()`
to finish before reading that array. This example reads all 16 practice rows
to show batching. It does not train a model.

## Training and validation periods

To test predictions on later readings, assign the earlier 12 row IDs to training and the last
four to validation. Shuffle only inside the training set:

<CodeBlock language="typescript" title="split-membership.ts">
{`const trainIdx = Array.from(tf.util.createShuffledIndices(12));
const valIdx = Array.from({ length: 4 }, (_, i) => i + 12);`}
</CodeBlock>

A training pipeline would read only `trainIdx`. Validation would read only
`valIdx`. Neighboring records can share information, even for a model that
reads one row at a time. Keep shared captures together and leave a gap when
windows overlap. Fit preprocessing on training rows only.

### Loading data a page at a time

<BridgeCallout bridge={frontmatter.concept.bridge} />

A paginated fetch reads the next page when your code requests it. A `tf.data` generator also produces values on request. The request may come from the model, a shuffle buffer, or prefetching that prepares records before the model needs them.

A **feature** is one measurement the model reads about an example. A **label** is the answer you want it to learn, here 0 or 1 for whether to flag the reading. **Supervised learning** uses these labeled examples to train the model.

The `fitDataset` training API reads `xs` as features and `ys` as labels. Other `tf.data` pipelines can hold different structures. In module 7, the model will learn to reproduce its own input. That task uses the input itself as the target.

The model does not read the full two-megabyte capture. It reads three summary values: amplitude, a zero-crossing count, and phase. The course names the zero-crossing feature frequency. Its unit is a count of crossings. Measuring frequency in hertz requires a separate calculation.

These features come from 64 consecutive samples of one channel. At 256 samples per second, that covers a quarter of a second. This sample count is separate from the ship's 64 sensor channels. Module 5 shows the extraction code and adds frequency measurements from the same time window.

For now, `row.features` and `xs` hold three numbers per reading. Fetching the record still reads its large raw capture, so fetch one at a time.

This integration sketch assumes an async `readArchivedSample(id)` function supplied by your application. It returns one record with `features` and `label`. It must not load the entire archive internally. The exercise uses a synchronous in-memory stand-in.

<CodeBlock language="typescript" title="data-pipeline.ts">
{`import * as tf from '@tensorflow/tfjs';

// JS: paginated API fetch
// const page = await fetch('/api/data?page=1&limit=32');

// A generator pauses at yield and resumes when another value is requested.
// Read one record inside the loop. Do not build a full archive array first.
async function* sensorDataGenerator() {
  const TOTAL_READINGS = 28_800;  // 11 days of archive: one reading per 33-second capture

  for (let i = 0; i < TOTAL_READINGS; i++) {
    const row = await readArchivedSample(i); // your asynchronous archive reader
    yield {
      xs: tf.tensor(row.features),   // [3]: amplitude, frequency, phase
      ys: tf.tensor([row.label]),
    };
  }
}

// Create a dataset pipeline
const dataset = tf.data.generator(sensorDataGenerator)
  .shuffle(100)   // shuffle buffer of 100 items: local mixing only
  .batch(32);     // group into batches of 32

// Iterate through batches (like paginated API calls)
await dataset.forEachAsync((batch) => {
  console.log('Batch shape:', batch.xs.shape); // [32, 3]
});`}
</CodeBlock>

Shuffle independent training examples before batching. Otherwise, neighboring readings stay together, and each update uses a narrow slice of the archive.

A shuffle buffer picks from a small pool of records and replaces each one it sends out. This mixes the records currently in the buffer. Some full-archive orderings remain impossible with a small buffer. Some records wait longer than others. The buffer size of 100 here is an example setting.

A buffer large enough for all 28,800 readings would need to load them before sending out the first batch. For a live stream, use a limited buffer.

The archive reader accepts a record ID, giving you another option: shuffle the small list of IDs, then read the records in that order. You get a full shuffle without holding all the records in memory.

### How batch size changes training

Batch size also changes training. The model updates its weights once per batch. A batch of one can give noisy updates. The full archive gives one update per complete pass. A size such as 32 sits between those choices. Module 3 shows how to choose it in `model.fit()`.

### Splitting Without Leaking

The **training set** contains the examples the model learns from. The **validation set** contains separate examples used to check it. Keep those sets separate so the validation score tests something the model has not already seen.

<CodeBlock language="typescript" title="train-test-split.ts">
{`// Hold out the latest 20% of this time-ordered archive for validation
const TOTAL = 28_800;  // the whole archive, the same count the generator walks
const TRAIN_SIZE = Math.floor(TOTAL * 0.8);

// IDs increase with recording time. Assign membership before shuffling.
// Shuffle only the earlier training IDs. Validation stays in time order.
const trainIdx = tf.util.createShuffledIndices(TRAIN_SIZE);
const valIdx = Uint32Array.from(
  { length: TOTAL - TRAIN_SIZE }, (_, i) => TRAIN_SIZE + i,
);

async function* splitGenerator(idx: Uint32Array) {
  for (const i of idx) {
    const row = await readArchivedSample(i);
    yield { xs: tf.tensor(row.features), ys: tf.tensor([row.label]) };
  }
}

const trainData = tf.data.generator(() => splitGenerator(trainIdx)).batch(32);
const valData = tf.data.generator(() => splitGenerator(valIdx)).batch(32);
// Validation contains only later readings. Training order can change
// without moving a reading across the split.`}
</CodeBlock>

Choose the split for the job the model will do. We want to predict future readings, so validation uses a later period. A classifier that reads one row at a time can still exploit similarities between neighboring rows. Randomly mixing those rows across both sets can make the score too optimistic.

Keep examples from the same capture on the same side of the split. If their time windows overlap, leave a gap between training and validation. Module 6 shows this in detail. A random split can work when examples are independent and come from the same kind of data the model will see later.

Assign each row to a set once. Separate `.shuffle().take()` and `.shuffle().skip()` runs can shuffle differently and put a row in both sets. Compute preprocessing statistics from training rows only. In module 3, you will reserve a final test set until after model selection.
