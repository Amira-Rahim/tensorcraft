## Read the Error First

Here is the code that produced it. The intent: amplify each of the 64 channels by its own gain factor. Position by position, gain times reading.

<CodeBlock language="typescript" title="amplify-broken.ts">
{`import * as tf from '@tensorflow/tfjs';

// channelGains: 64 amplification factors. latestReadings: 64 raw values.
const gains = tf.tensor2d([channelGains]);      // shape [1, 64]
const readings = tf.tensor2d([latestReadings]); // shape [1, 64]

// BROKEN: this is not the multiplication you want.
const amplified = gains.matMul(readings);
// Error in matMul: inner shapes (64) and (1) of Tensors with
// shapes 1,64 and 1,64 and transposeA=false and transposeB=false
// must match.`}
</CodeBlock>

The error is precise once you can read it: `matMul` multiplies **rows into columns**, so it needs the left tensor's column count (64) to equal the right tensor's row count (1). But matching positions was the intent all along, and that is a different op with no inner-dimension rule at all. TensorFlow.js has both multiplications; the bug is reaching for the wrong one.

## Element-wise Operations: The Repair

<BridgeCallout bridge={frontmatter.concept.bridge} />

When you write `arr.map((x, i) => x + arr2[i])`, you're doing element-wise addition. `tf.mul`, `tf.add`, and `tf.sub` are the same idea across any number of dimensions, on the GPU. `gains.mul(readings)` is the one-word fix for the broken amplifier:

<CodeBlock language="typescript" title="tensor-ops.ts">
{`import * as tf from '@tensorflow/tfjs';

// The amplifier from amplify-broken.ts, repaired: matching positions,
// so matMul's inner-dimension rule does not apply. The shapes still
// have to be broadcast-compatible.
const amplified = gains.mul(readings);    // [1, 64], gain[i] * reading[i]

const sensor1 = tf.tensor([1, 2, 3]);
const sensor2 = tf.tensor([4, 5, 6]);

// Element-wise operations: same as map + zip
const sum = tf.add(sensor1, sensor2);     // [5, 7, 9]
const product = tf.mul(sensor1, sensor2); // [4, 10, 18]
const diff = tf.sub(sensor2, sensor1);    // [3, 3, 3]

// Chaining with method syntax
const result = sensor1.add(sensor2).mul(tf.scalar(2));
// [10, 14, 18]`}
</CodeBlock>

The shapes do not have to be identical. When they differ, TensorFlow.js lines the two tensors up from the last axis backwards and stretches any axis of size 1, or any axis the smaller tensor does not have at all, until it matches the larger one. That is why `.mul(tf.scalar(2))` reaches every element, and why subtracting a `[2]` tensor of column means from a `[5, 2]` batch takes each column's mean down its own column. This is called broadcasting, and it is why an element-wise op forgives a shape difference that `matMul` will not.

Which way the cost difference runs depends on the backend and the size. The hardware win is real on an accelerated backend, over large tensors already sitting on the device. On the CPU backend there is nothing to win: measured on tfjs 4.22.0 under node, a hand-written loop over 64 numbers ran about four times faster than `tf.add` plus its readback, and about twice as fast at a million of them. The ratio moves with the machine; the direction does not. A `[1, 64]` amplifier is not where the speed comes from. It is where the shape rules get learned, and those rules are what let the same two ops run over a whole archive later.

## When You DO Want matMul

So why does `matMul` exist at all? Neural networks are built on one operation: multiply matching entries, then sum them. Element-wise ops do the multiply. They cannot do the sum, because a sum reduces an axis and map plus zip never reduces anything. `matMul` fuses the multiply and the sum into one hardware kernel, run for every row of the left tensor against every column of the right. It comes with the one inflexible shape rule the error message was enforcing:

**`[m, n] × [n, p] → [m, p]`: the inner dimensions must match.**

The left tensor's column count must equal the right tensor's row count. When they don't, you flip one with `transpose()`, which swaps a tensor's rows and columns, turning `[3, 2]` into `[2, 3]`:

<CodeBlock language="typescript" title="matmul.ts">
{`// weights: [3, 2], input: [3, 1]
const weights = tf.tensor2d([[1, 2], [3, 4], [5, 6]]);  // [3, 2]
const input = tf.tensor2d([[1], [1], [1]]);               // [3, 1]

// weights.matMul(input) would throw:
//   [3, 2] × [3, 1]: inner dims 2 ≠ 3. No deal.

// transpose() flips [3, 2] → [2, 3]. Now the rule is satisfied:
//   [2, 3] × [3, 1] → [2, 1] ✓
const output = weights.transpose().matMul(input);
output.print();
// [[9],     ← 1+3+5: first column of weights, summed against input
//  [12]]    ← 2+4+6: second column`}
</CodeBlock>

Why care? Every dense layer you'll build is essentially `matMul(input, weights) + bias`, and the shape rule above is the most common source of dimension errors in ML code. The recurrent cells in module 6 reuse the same rows-into-columns rule, wrapped in more machinery. The error that opened this lesson will find you again the day you build your first network layer; next time you'll read it in one pass.

<DerivationDrawer summary="Why rows into columns: where the inner dimension comes from">
A matrix turns a list of numbers into another list, one weighted sum per output. Its shape says which sizes: a `[2, 3]` matrix reads three numbers and emits two.

Take `weights.transpose()` from the block above, `[[1, 3, 5], [2, 4, 6]]`. Feed it `[1, 0, 0]` and the answer is its first column, `[1, 2]`. `[0, 1, 0]` gives the second column, `[3, 4]`, and `[0, 0, 1]` gives `[5, 6]`. Each column is what one input slot contributes on its own, so any other input is those columns added up in the amounts you supply: `[1, 1, 1]` gives `[1 + 3 + 5, 2 + 4 + 6]`, which is the `[[9], [12]]` printed above.

Now run two matrices back to back. The one that goes first emits as many numbers as it has rows; the one that goes next reads as many as it has columns. Those two counts have to be the same number, and in `[m, n] × [n, p]` that number is `n`, sitting on the inside of the pair. That is the whole shape rule.
</DerivationDrawer>
