## Setting the Threshold

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="threshold-setting.ts">
{`// Compute threshold from normal data distribution
function percentile(values: number[], p: number): number {
  const sorted = [...values].sort((a, b) => a - b);
  const index = Math.ceil(sorted.length * (p / 100)) - 1;
  return sorted[index];
}

// Normal reconstruction errors from validation set
const normalErrors = computeAnomalyScores(autoencoder, validationData);

// 99th percentile: 1% of normal signals get flagged. That is a RATE,
// not an alert count. This archive records one reading per 33-second
// window, so 1% of it is 26 flags a day.
const threshold99 = percentile(normalErrors, 99);
console.log('99th percentile threshold:', threshold99);  // ~0.0048

// Aggressive threshold: 95th percentile
// 5% of normal signals flagged, but catches more subtle anomalies
const threshold95 = percentile(normalErrors, 95);
console.log('95th percentile threshold:', threshold95);  // ~0.0031

function classifySignal(error: number, threshold: number): 'normal' | 'anomaly' {
  return error > threshold ? 'anomaly' : 'normal';
}`}
</CodeBlock>

A percentile fixes a false-alarm rate, and what reaches a human is that rate times the volume. The archive records one reading per 33-second window: 2,618 a day, 18,327 a week. A cutoff at the 99th percentile flags one percent of the calm ones, so 26 a day and 183 a week. The week Nazari is angry about had 14. The live dashboard reads faster still, one snapshot a second from module 4, where the same percentile is 864 flags a day.

Read it backwards and the cutoff she is asking for is not in this data. Two false alarms a week out of 18,327 readings is one in nine thousand, past the 99.98th percentile. The validation slice is a tenth of the archive, 2,880 readings, and its single highest error sits near the 99.97th. There is nothing above that to measure. A percentile is where you start reading the error distribution. The sweep below is where the cutoff gets chosen.

## Evaluating the Threshold

<CodeBlock language="typescript" title="evaluation.ts">
{`interface Metrics {
  precision: number;  // of flagged signals, how many are real anomalies?
  recall: number;     // of real anomalies, how many did we catch?
  f1: number;         // harmonic mean: single score balancing both
}

function evaluate(
  errors: number[],
  labels: boolean[],  // true = anomaly
  threshold: number,
): Metrics {
  let tp = 0, fp = 0, fn = 0;

  for (let i = 0; i < errors.length; i++) {
    const predicted = errors[i] > threshold;
    if (predicted && labels[i]) tp++;
    else if (predicted && !labels[i]) fp++;
    else if (!predicted && labels[i]) fn++;
  }

  const precision = tp / (tp + fp) || 0;
  const recall = tp / (tp + fn) || 0;
  const f1 = 2 * precision * recall / (precision + recall) || 0;

  return { precision, recall, f1 };
}

// Sweep the candidates on the VALIDATION slice. Choosing a cutoff is
// choosing a setting, and settings are paid for with validation data.
const thresholds = [0.002, 0.003, 0.004, 0.005, 0.008, 0.010];
for (const t of thresholds) {
  const m = evaluate(valErrors, valLabels, t);
  console.log(\`t=\${t}: P=\${m.precision.toFixed(2)} R=\${m.recall.toFixed(2)} F1=\${m.f1.toFixed(2)}\`);
}
// t=0.002: P=0.34 R=1.00 F1=0.51  ← catches everything, many false alarms
// t=0.004: P=0.89 R=0.95 F1=0.92  ← good balance
// t=0.010: P=1.00 R=0.72 F1=0.84  ← no false alarms, misses some
// (three of the six rows shown; 0.003, 0.005 and 0.008 each score between
// their neighbours, which is what makes 0.004 the single peak)

// Lock the cutoff, then score it once on the held-out test slice. That
// second number is the one the report carries, and it tends to land a
// little under the validation number, because the validation score paid
// for this choice. Here that is the F1 winner; the next section is why
// this deployment does not stop at the F1 winner.
const chosen = 0.004;
const held = evaluate(testErrors, testLabels, chosen);
console.log(\`t=\${chosen} held out: P=\${held.precision.toFixed(2)} R=\${held.recall.toFixed(2)} F1=\${held.f1.toFixed(2)}\`);`}
</CodeBlock>

The sweep and the report read different slices on purpose. Six candidates scored on the validation slice are six decisions charged to it, and module 3's rule holds: the test slice stays out of reach until the cutoff is locked. Sweep on the test slice instead and the winning F1 is part measurement, part luck about which candidate suited those particular rows.

## When the Cost Asymmetry Moves the Cutoff

The table above has one F1 peak, at t=0.004, and it is tempting to read that row as the answer. It is the answer only when a false alarm and a missed anomaly cost the same. They almost never do. Run the same curve through two deployments and watch the threshold move in opposite directions.

In the first deployment the detector gates the capture pipeline, so a miss costs the mission: every real event it sleeps through is data the ship never records again. Take t=0.002, recall 1.00 at precision 0.34. Read that precision carefully, because it was measured on a slice holding enough anomalies to score against. Live telemetry is far calmer, so the week's false-alarm count is the false-positive rate times 18,327 readings, and it runs well above what the slice suggests. The capture pipeline can absorb that. A machine reads every flag, and no crew is being taught to ignore anything, so the threshold belongs low here.

Nazari's week is the second deployment, the one where a false alarm costs the detector its standing with the crew. Fourteen alerts, twelve of them cosmic background: precision 0.14 (2 of 14), and the real cost was never the twelve wasted checks. It was the reflex they were training. A bridge crew that learns the alert is usually noise stops standing up for it, and the miss that finally matters arrives pre-ignored. On the same curve, t=0.010 buys precision 1.00 at recall 0.72: zero wasted checks, and 28 percent of real anomalies missed (1 - 0.72). For the capture pipeline that trade is malpractice; for an alert channel whose one failure mode is being tuned out, it can be exactly right. Demir locks that one. Zero false alarms across the calm rows of the 2,880-reading validation slice is a measured result, not a promise about next week.

Both deployments run the same model on the same errors, and the F1 peak sits in the same place. The threshold went down in the first and up in the second. The F1 table cannot tell you which way to move it, because what decides is the cost of a miss against the cost of a false alarm, and neither number is in the error data.
