      function findBestThreshold(
        errors: number[],
        labels: boolean[],
        candidates: number[],
      ): { threshold: number; f1: number } {
        let best = { threshold: candidates[0], f1: 0 };

        for (const t of candidates) {
          let tp = 0,
            fp = 0,
            fn = 0;
          for (let i = 0; i < errors.length; i++) {
            const predicted = errors[i] > t;
            if (predicted && labels[i]) tp++;
            else if (predicted && !labels[i]) fp++;
            else if (!predicted && labels[i]) fn++;
          }
          const precision = tp / (tp + fp) || 0;
          const recall = tp / (tp + fn) || 0;
          const f1 = (2 * precision * recall) / (precision + recall) || 0;
          if (f1 > best.f1) best = { threshold: t, f1 };

## Setting the Threshold

<CodeBlock language="typescript" title="threshold-setting.ts">
{`// Compute threshold from normal data distribution
function percentile(values: number[], p: number): number {
  if (!values.length || !values.every(Number.isFinite) || !Number.isFinite(p) || p <= 0 || p > 100) {
    throw new Error('Expected finite data and 0 < p <= 100');
  }
  const sorted = [...values].sort((a, b) => a - b);
  const index = Math.ceil(sorted.length * (p / 100)) - 1;
  return sorted[index];
}

// Integration sketch: validationData contains reviewed-normal rows only.
// computeAnomalyScores and autoencoder come from the preceding lessons.
// Normal reconstruction errors from validation set
const normalErrors = computeAnomalyScores(autoencoder, validationData);

// 99th percentile: about 1% flagged on this normal sample, allowing for ties.
// Future rates can change. This archive records one reading per 33-second
// window, so 1% of it is 26 flags a day.
const threshold99 = percentile(normalErrors, 99);
console.log('99th percentile threshold:', threshold99);

// Aggressive threshold: 95th percentile
// About 5% flagged on this sample. The lower cutoff can catch more anomalies
const threshold95 = percentile(normalErrors, 95);
console.log('95th percentile threshold:', threshold95);

function classifySignal(error: number, threshold: number): 'normal' | 'anomaly' {
  return error > threshold ? 'anomaly' : 'normal';
}`}
</CodeBlock>

A percentile estimates the false-alarm rate on the normal readings you sampled. To estimate the number of alerts, multiply that rate by the number of readings. The estimate only holds if the rate stays the same after deployment.

The archive has one reading per 33-second window: 2,618 a day or 18,327 a week. At a 1% false-alarm rate, that is about 26 false flags a day and 183 a week. Nazari had 14 alerts that week. Module 4's live dashboard reads once per second. At that volume, the same 1% rate would produce 864 false flags a day.

Two false alarms a week among 18,327 normal readings would require a rate near 0.011%. A sample of 2,880 cannot estimate that tail reliably: one observation is already about 0.035% of the sample. Zero observed false alarms is still compatible with a nonzero future rate. Collect more representative data, use an explicit uncertainty bound, and consider grouping repeated flags into incidents. A labeled sweep below helps compare costs. It does not remove this sampling uncertainty.

## Evaluating the Threshold

For this sweep, report undefined precision or recall as zero, and F1 is zero when there are no true positives. This is an explicit reporting convention. The earlier helper returned `null` to keep an undefined ratio visible. A dashboard can still show that distinction.

<CodeBlock language="typescript" title="evaluation.ts">
{`interface Metrics {
  precision: number;  // of flagged signals, how many are real anomalies?
  recall: number;     // of real anomalies, how many did we catch?
  f1: number;         // harmonic mean: single score balancing both
}

function evaluate(
  errors: number[],
  labels: boolean[],  // true = anomaly
  threshold: number,
): Metrics {
  // Flag first, then count the three cells that matter. The fourth cell,
  // calm readings left alone, is the one none of these three scores reads.
  const flagged = errors.map((e) => e > threshold);
  const tp = flagged.filter((hit, i) => hit && labels[i]).length;   // caught
  const fp = flagged.filter((hit, i) => hit && !labels[i]).length;  // false alarms
  const fn = flagged.filter((hit, i) => !hit && labels[i]).length;  // missed

  const precision = tp === 0 ? 0 : tp / (tp + fp);
  const recall = tp === 0 ? 0 : tp / (tp + fn);
  const f1 = precision + recall === 0 ? 0 : (2 * precision * recall) / (precision + recall);

  return { precision, recall, f1 };
}

// Sweep the candidates on the VALIDATION slice. Choosing a cutoff is
// choosing a setting, so use validation data for that comparison.
const thresholds = [0.2, 0.3, 0.4, 0.5, 0.8, 1.0];
for (const t of thresholds) {
  const m = evaluate(valErrors, valLabels, t);
  console.log(\`t=\${t}: P=\${m.precision.toFixed(2)} R=\${m.recall.toFixed(2)} F1=\${m.f1.toFixed(2)}\`);
}
// Fictional mission report. The story supplies these results:
// t=0.2: P=0.34 R=1.00 F1=0.51: catches everything, many false alarms
// t=0.4: P=0.89 R=0.95 F1=0.92: good balance
// t=1.0: P=1.00 R=0.72 F1=0.84: no false alarms, misses some
// (three of the six rows shown. 0.3, 0.5 and 0.8 each score between
// their neighbours, in this fictional report)

// Do not read the test slice yet. Set the deployment objective and
// choose the cutoff on validation data in the next section.`}
</CodeBlock>

These checks use different datasets. The percentile comes from normal readings, one tenth of the archive. That set has no known anomalies, so it cannot measure recall.

The cutoff comparison uses 2,880 labeled validation rows. About one in twelve is an anomaly, five or six times the proportion in the full archive. That gives us enough anomalies to compare recall, but precision from this set will not directly describe the live stream. The next section explains why.

Keep the final test data separate. Comparing six candidates uses information from the validation set to make six choices. After choosing the cutoff, test it once on the untouched test set. Choosing the winner on that test set would make its F1 partly reflect luck on those particular rows.

## Cutoffs and the cost of errors

The F1 peak at t=0.4 answers one question: which candidate maximizes F1 on this validation slice? F1 gives precision and recall the same role in its formula. It does not count each false alarm and missed anomaly as one equally costly mistake.

<CodeBlock language="javascript" title="f1-and-cost.js">
{`// Two candidate cutoffs on the same 100 labeled examples: 20 anomalies.
const candidates = [
  { name: 'A', tp: 8, fp: 0, fn: 12, tn: 80 },
  { name: 'B', tp: 15, fp: 10, fn: 5, tn: 70 },
];
const comparisons = candidates.map((c) => ({
  name: c.name,
  f1: 2 * c.tp / (2 * c.tp + c.fp + c.fn),
  equalCost: c.fp + c.fn,
}));
// A: F1 0.571, 12 errors. B: F1 0.667, 15 errors.
// F1 prefers B. An equal cost per error prefers A.`}
</CodeBlock>

For a cost-based decision, define `cost = falseAlarmCost * FP + missCost * FN` and choose the validation cutoff with the lowest cost. Use data representative of deployment, or adjust estimates for its expected class frequencies. An alert-budget or minimum-recall constraint is another explicit objective. Decide it before comparing candidates, then check the chosen rule on the held-out test.

The crew's two deployments have different costs and constraints.

The first detector decides which captures to save. Missing an event loses data the ship cannot record again. At t=0.2, recall is 1.00 and precision is 0.34 on the validation set.

The live stream contains far fewer anomalies, so it can produce many more false alarms than that precision suggests. Estimate the count by multiplying the false-positive rate by the number of normal readings. The automated capture system can handle those extra flags. A low cutoff makes sense when missing a capture costs more.

The second detector wakes the crew. Nazari investigated fourteen alerts, twelve caused by cosmic background radiation. Precision was 0.14, or 2 of 14. Repeated false alarms also make the crew less likely to respond to the next alert.

On this validation curve, t=1.0 gives precision 1.00 and recall 0.72. It produces no false alarms on this set, but misses 28 percent of anomalies. The crew pager can use a different cutoff from the capture system, while still accounting for those missed events. Demir chooses 1.0. The fictional report has zero false alarms across 2,640 normal rows. The crew still needs to test it on later readings.

Both systems use the same model, errors, and F1 curve. One needs a lower cutoff and the other a higher one because their errors have different costs. The F1 table does not include those costs.

The crew alert has now selected its cutoff using validation data and its alert budget. Evaluate that rule on the test slice once. If the result is inadequate, report the failure. Tuning against this test would turn it into another validation set.
