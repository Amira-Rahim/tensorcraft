Alert fatigue is real, in production monitoring and in space. An error tracker that fires on every minor exception teaches the team to ignore it; Nazari just described the bridge-crew version. The threshold must balance sensitivity against specificity.

{`// Compute threshold from normal data distribution
function percentile(values: number[], p: number): number {
  const sorted = [...values].sort((a, b) => a - b);
  const index = Math.ceil(sorted.length * (p / 100)) - 1;
  return sorted[index];
}

// Normal reconstruction errors from validation set

// Aggressive threshold: 95th percentile
// 5% of normal signals flagged, but catches more subtle anomalies

console.log('95th percentile threshold:', threshold95);  // ~0.0031

## Evaluating the Threshold

<CodeBlock language="typescript" title="evaluation.ts">
{`interface Metrics {
  precision: number;  // of flagged signals, how many are real anomalies?
  recall: number;     // of real anomalies, how many did we catch?
  f1: number;         // harmonic mean: single score balancing both
}

function evaluate(
  errors: number[],
  labels: boolean[],  // true = anomaly
  threshold: number,
): Metrics {
  let tp = 0, fp = 0, fn = 0;

  for (let i = 0; i < errors.length; i++) {
    const predicted = errors[i] > threshold;
    if (predicted && labels[i]) tp++;
    else if (predicted && !labels[i]) fp++;
    else if (!predicted && labels[i]) fn++;
  }

  const precision = tp / (tp + fp) || 0;
  const recall = tp / (tp + fn) || 0;
  const f1 = 2 * precision * recall / (precision + recall) || 0;

  return { precision, recall, f1 };
}

// Try multiple thresholds and find the best F1
const thresholds = [0.002, 0.003, 0.004, 0.005, 0.008, 0.010];
for (const t of thresholds) {
  const m = evaluate(testErrors, testLabels, t);
  console.log(\`t=\${t}: P=\${m.precision.toFixed(2)} R=\${m.recall.toFixed(2)} F1=\${m.f1.toFixed(2)}\`);
}
// t=0.002: P=0.34 R=1.00 F1=0.51  ← catches everything, many false alarms
// t=0.004: P=0.89 R=0.95 F1=0.92  ← good balance
// t=0.010: P=1.00 R=0.72 F1=0.84  ← no false alarms, misses some`}
</CodeBlock>

## Same Curve, Opposite Costs

The table above has one F1 peak, at t=0.004, and it is tempting to read that row as the answer. It is the answer only when a false alarm and a missed anomaly cost the same. They almost never do. Run the same curve through two deployments and watch the threshold move in opposite directions.

**When the miss costs the mission.** Suppose the detector gates the capture pipeline: every real event it sleeps through is data the ship never records again. Take t=0.002, recall 1.00 at precision 0.34. At last week's rate of two real events, that is roughly six flags (2 / 0.34 = 5.9), four of them noise. Four wasted checks a week is the entire price of missing nothing, and the threshold belongs low.

**When the false alarm costs the detector.** Nazari's week is the second deployment. Fourteen alerts, twelve of them cosmic background: precision 0.14 (2 of 14), and the real cost was never the twelve wasted checks. It was the reflex they were training. A bridge crew that learns the alert is usually noise stops standing up for it, and the miss that finally matters arrives pre-ignored. On the same curve, t=0.010 buys precision 1.00 at recall 0.72: zero wasted checks, and 28 percent of real anomalies missed (1 - 0.72). For the capture pipeline that trade is malpractice; for an alert channel whose one failure mode is being tuned out, it can be exactly right.

Same model, same errors, same F1 peak. The threshold moved down in the first deployment and up in the second, and nothing on the F1 table can tell you which way to push it. The costs live outside the dataset.
