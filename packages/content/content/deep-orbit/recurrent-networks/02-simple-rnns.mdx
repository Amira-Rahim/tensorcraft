<Dialogue speaker="Ensign Demir">
So an RNN is just... a reducer? It takes the previous hidden state and the new input, runs them through a function, and outputs new hidden state? That is what I do every time I rebuild state by replaying an event log.
</Dialogue>

The cell itself is small: a weight for the previous hidden state, a weight for the input, a bias, a `tanh`. What makes it recurrent is the wiring: the output loops back in as the next step's hidden state. Small enough, in fact, to run by hand before anyone argues about analogies:

<CodeBlock language="typescript" title="reducer-with-memory.ts">
{`import * as tf from '@tensorflow/tfjs';

// One RNN step: newHidden = tanh(0.8 * prevHidden + 1.0 * input)
// (weights hand-picked for the drill, bias 0)
let h = tf.scalar(0);
for (const x of [0.5, 0.9, 0.5]) {
  const next = tf.tidy(() => tf.tanh(h.mul(0.8).add(x)));
  h.dispose();
  h = next;
  console.log(h.dataSync()[0].toFixed(4));
}
h.dispose();
// 0.4621
// 0.8537
// 0.8284  ← the same 0.5 that scored 0.4621 two steps ago`}
</CodeBlock>

<Dialogue speaker="Dr. Farah">
There is your answer, in the last line. The shape is right, and so is the part that surprised you: your reducer would also hand the same event two different results at two points in the log, because the state it is handed differs. That is the fold, and both of them have it. Same state, same input, same result holds for both as well. What your reducer has and this does not is a rule you can read: you wrote apply. The 0.8 and 1.0 were hand-picked for the demo; in a real cell they are learned from data. Nobody authors the transition function. The weights are the function, and the hidden state is the network's memory.
</Dialogue>

## The Learned Reducer

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="rnn-as-reducer.ts">
{`import * as tf from '@tensorflow/tfjs';

// Event replay: you write the state transition function
function signalReducer(state: { count: number; trend: string }, action: { value: number }) {
  const trend = action.value > 0.5 ? 'rising' : 'falling';
  return { count: state.count + 1, trend };
}

// RNN: the network LEARNS the state transition function
// At each time step:
//   newHidden = tanh(W_h * prevHidden + W_x * input + bias)
//
// W_h and W_x are weight matrices learned during training
// tanh squashes output to [-1, 1]
// prevHidden carries memory of all previous time steps

// Build a simple RNN in TF.js
const model = tf.sequential();
model.add(tf.layers.simpleRNN({
  units: 32,           // hidden state size (the shape of the state you carry)
  inputShape: [5, 3],  // 5 time steps, 3 features each
}));
model.add(tf.layers.dense({ units: 1, activation: 'sigmoid' }));

model.compile({ optimizer: 'adam', loss: 'binaryCrossentropy', metrics: ['accuracy'] });

// Input: [batch, timeSteps, features] = [32, 5, 3]
const x = tf.randomNormal([32, 5, 3]);
const y = tf.randomUniform([32, 1]).round();

// Shape drill only: this proves the [5, 3] pipeline runs, nothing more.
// The labels are random and the loss still falls every epoch, because
// 1,185 parameters against 32 samples can memorize noise. Run it to 100
// epochs and training accuracy lands at exactly 1.00 in about half of
// twenty runs, and within a few rows of the full 32 in the rest. None of
// that generalizes. The real run is tonight's, in the epilogue.
await model.fit(x, y, { epochs: 10 });

x.dispose();
y.dispose();`}
</CodeBlock>

You can read those weights straight off the model. `model.getWeights()` hands back three tensors for that layer: the input kernel, shaped [features, units], then the recurrent kernel, shaped [units, units], then the bias, one number per unit. The order is the library's rather than the formula's, since the lesson writes the recurrent term first and TF.js stores the input kernel first. A layer that has not been added to a model has none of them yet. Build a one-unit cell over a one-feature sequence and those three tensors hold one number each: the `recurrentWeight`, `inputWeight` and `bias` of the drill at the top of this lesson, drawn at random instead of picked by hand.

## How the RNN Processes a Sequence

<CodeBlock language="typescript" title="rnn-unrolled.ts">
{`// Unrolling the RNN: what happens at each time step:

// Time step 0: hidden = f(zeros, input[0])
// Time step 1: hidden = f(hidden, input[1])  ← remembers step 0
// Time step 2: hidden = f(hidden, input[2])  ← remembers steps 0-1
// Time step 3: hidden = f(hidden, input[3])  ← remembers steps 0-2
// Time step 4: hidden = f(hidden, input[4])  ← remembers steps 0-3

// The final hidden state encodes the entire sequence
// We pass it to a Dense layer for classification

// Return sequences: get hidden state at EVERY step (not just the last)
const modelAllSteps = tf.sequential();
modelAllSteps.add(tf.layers.simpleRNN({
  units: 32,
  inputShape: [5, 3],
  returnSequences: true,  // output shape: [batch, 5, 32] instead of [batch, 32]
}));
// Useful when you need the full temporal output (e.g., for stacking RNN layers)`}
</CodeBlock>

## The Vanishing Gradient Problem

Backpropagation through time is module 3's backward pass unrolled along the sequence. Every step it walks back through the cell, it multiplies the gradient by the recurrent weight and by the slope of `tanh` at that step. Whether the learning signal survives the trip depends on that one product, not on either factor alone. Below 1 it decays geometrically, which is the ordinary case: the slope of `tanh` is at most 1, and it falls to 0.42 at an input of 1 and 0.07 at an input of 2, so a saturated cell passes back almost nothing. Run the drill's cell with its 0.8 recurrent weight and readings near zero, and the gradient arriving 60 steps back is 1.5e-6 of the one that left the loss. The weights that would have to change to catch a long pattern never receive a usable instruction. In practice a simple RNN learns dependencies of roughly ten to twenty steps. Read that as a rule of thumb about the product rather than a property of the cell: what sets the reach is the recurrent weight and where on `tanh` the states sit, so it moves with the data and with the weights a run happens to land on.

Nothing bounds the recurrent weight, though, so the product can sit above 1 for a stretch of steps. Raise that 0.8 to 1.5, start the cell at zero and feed it readings near 0.001. The gradient grows on the way back instead of shrinking: at step 14 it is 173 times the one that left the loss. A spike like that is what gradient clipping is for. The norm of a gradient is its length: square every component, add them up, take the square root. Pick a ceiling, and on any step whose norm passes it, scale every component down by the same factor before the optimizer applies them. TF.js 4.22 has no clipping option on its optimizers, so that cap is one you write yourself.

The growth does not last, and what stops it is the same `tanh`. At a recurrent weight of 1.5 the cell state settles at 0.8590, and there the per-step factor is `1.5 * (1 - 0.8590 * 0.8590)`, which is 0.393. Past step fifteen this walk shrinks again, and by step 60 the gradient is 2.7e-16 of the one that left the loss. A one-unit cell does that for every weight above 1: the settled factor is 0.82 at 1.1, 0.39 at 1.5, 0.17 at 2. Explosion here is a burst of a dozen steps, not a sustained run. It also needs a state near zero to start from. With the recurrent weight at 1.5 and readings drawn anywhere in plus or minus 0.01, the step-60 gradient lands around 4e-17 in the median trial and under 1e-13 in nineteen trials out of twenty. The rare trial that sits near zero for its first steps holds the factor near 1.5 for longer and still ends six or more orders down; a trial that never collapses at all turned up three times in 200,000 simulated ones. Vanishing is the quieter failure, and it is the one this window has.

The pattern DEEP SCAN needs repeats a little over every 73 seconds, and the dashboard feed carries one sample per second. Reaching back 73 steps comes up just short of one full interval, so the dependency the model has to learn is 74 steps long. The archive's rows come 2.2 to an interval, one every 33 seconds, and each one's three features come from a single quarter-second window inside that capture. They can show that something repeats. What they cannot carry is the shape inside a pulse, and an 80-row window of them spans 44 minutes instead of one interval. The next lesson introduces the cell that was designed for exactly that gap. Tonight's run, in the epilogue, shows what happens without it.

## Challenge

The drill at the top of this lesson ran one cell by hand for three readings. Write that loop yourself, for any window and any weights, in plain JavaScript numbers and Math.tanh: the drill's tf.scalar version is for reading, and the graded loop has no tensors in it. One thing it grades is the carry: the same reading has to score one number early in a window and a different number later, and it can only do that if the state you hand from step to step is real.

Then build the library's version of the same cell, a one-unit `tf.layers.simpleRNN`, and read its three weights off the model. The grader runs your loop on those weights and puts it beside what the layer computes for the same readings, step by step. The two agree to about seven decimal places when your recurrence is the one TF.js runs, which is as close as a float32 layer and a float64 loop get. Nothing is memorizable here, because the layer draws its own weights at random every time it is built.
