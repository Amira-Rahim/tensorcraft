## Why One Reading At A Time Fails

<BridgeCallout bridge={frontmatter.concept.bridge} />

<CodeBlock language="typescript" title="feedforward-limitation.ts">
{`import * as tf from '@tensorflow/tfjs';

// This stateless feedforward call scores one reading without prior readings
// It sees: [0.5, 0.3, 0.7] → classify
// Then:    [0.8, 0.5, 0.9] → classify (no memory of previous)

// But the signal has TEMPORAL patterns, and they live in the moves
// between rows rather than in any one row:
// t=0: [0.5, 0.3, 0.7]
// t=1: [0.8, 0.5, 0.9]  every feature up from t=0
// t=2: [0.3, 0.1, 0.4]  every feature down from t=1
// t=3: [0.5, 0.3, 0.7]  back to the t=0 reading exactly ← THE PATTERN REPEATS

// Hand the model one reading at a time and each row is scored alone
// It cannot detect: "the signal rises, falls, then rises again"

// What we need: a model that reads the steps in order, reusing one rule at every step
// Input shape changes from [features] to [timeSteps, features]

// Preparing sequential input: create sliding windows
function createSequences(data: number[][], windowSize: number): number[][][] {
  const sequences: number[][][] = [];
  for (let i = 0; i <= data.length - windowSize; i++) {
    sequences.push(data.slice(i, i + windowSize));
  }
  return sequences;
}

// The rows the deployed classifier already scores: amplitude, frequency
// and phase min-max normalized into [0, 1] by module 4's pipeline, one
// row per time step. Lesson 5 works in the raw counts behind them, where
// amplitude runs to 2048 and the zero-crossing count to 63.
const readings = [
  [0.5, 0.3, 0.7],
  [0.8, 0.5, 0.9],
  [0.3, 0.1, 0.4],
  [0.5, 0.3, 0.7],
  [0.9, 0.4, 0.8],
];

// Create sequences of 3 time steps each
const sequences = createSequences(readings, 3);
console.log(sequences.length);  // 3 sequences
console.log(sequences[0]);
// [[0.5, 0.3, 0.7], [0.8, 0.5, 0.9], [0.3, 0.1, 0.4]]
// ^ This IS the pattern: up, then down. The series is back at the
//   t=0 reading by t=3 and climbs again from there`}
</CodeBlock>

Flattening a window into a dense input preserves order, making it a useful baseline. It assigns separate weights to each position and fixes the input length. An RNN reuses one transition rule at every step, so longer sequences do not require more recurrent parameters. That reuse can help with patterns at different positions, but does not guarantee identical responses after a time shift: the incoming state and surrounding context still matter.

<Dialogue speaker="Dr. Farah">
Look at what the slicing bought you. Row for row, nothing changed. The pattern only exists across rows, in the order they arrive: [rising, falling, rising] and [falling, rising, rising] are the same three values telling two different stories. Order carries information, and the model we have throws it away at the door.
</Dialogue>

Consider a byte-forwarding stream with no transform: reassembling its chunks out of order corrupts the file. That example preserves order without learning from it. A sequence model uses ordered values as input to a learned computation. Other JavaScript streams can inspect or transform their contents too; buffering alone is the limited comparison here.

## Sequence Shape: [batch, timeSteps, features]

<CodeBlock language="typescript" title="sequence-tensors.ts">
{`import * as tf from '@tensorflow/tfjs';

// Feedforward input: [batch, features]
// Shape: [32, 3]: 32 samples, each with 3 features
const feedforwardInput = tf.randomNormal([32, 3]);

// Sequential input: [batch, timeSteps, features]
// Shape: [32, 5, 3]: 32 samples, each a window of 5 time steps, each with 3 features
const sequentialInput = tf.randomNormal([32, 5, 3]);

// The extra dimension is TIME
// Think of it like:
// - Feedforward: a single photo (width × height)
// - Sequential: a video (frames × width × height)

// Or in JS terms:
// - Feedforward: one object handed to a function
// - Sequential: an array of five such objects, where the array order is data

console.log('Feedforward shape:', feedforwardInput.shape);  // [32, 3]
console.log('Sequential shape:', sequentialInput.shape);     // [32, 5, 3]

feedforwardInput.dispose();
sequentialInput.dispose();`}

## Challenge

`createSequences` above stops at the windows. Training needs two more things out of the same loop: a stride, so you choose how far the window jumps between samples, and a forecasting target for every window, the single reading that arrives immediately after it. That target also moves the boundary. A window whose next reading falls past the end of the archive has no answer to train against, so it never enters the set.

Then stack what survives. The arrays are nested lists to JavaScript and nothing more; the model reads shapes, so the windows go in as one tensor of [batch, timeSteps, features] and the targets as one tensor of [batch, features]. That third axis is the whole difference between this module and the four before it, and this is where you put it.
